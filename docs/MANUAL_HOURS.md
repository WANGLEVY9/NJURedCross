# 时长审核中的人员补录

献血车的“时长审核与导出”和普通活动的最终时长表均提供“手动添加人员”。操作人填写姓名、学号、院系、实际服务班次、三类时长、地点、日期、工作内容和补录依据，并确认已核对实际服务。邮箱可留空，学号始终按文本保存。

## 权限与审核

- 补录沿用目标活动的时长审核权限；写入前重新判定活动范围与审核资格，接口使用会话中的操作人，并校验 CSRF。普通活动最终表导出后不能继续补录。
- 服务器按姓名和学号匹配已有平台账号；身份冲突时停止。没有账号的人也可参与时长表补录，不会因此创建登录账号或授予权限。
- 补录写入网站活动报名总表和人工核验记录，保留补录依据、操作人和时间。不会伪造签到照片，补录凭据需要通过服务器签名校验。
- 献血车补录生成待审核明细，沿用原有独立审核、编辑、汇总、导出和入账规则。普通活动补录作为最终审核阶段的独立补充名单保留，不修改负责人已提交的初审来源摘要；审核人可继续修改明细或标为未通过。
- 同一班次已有该学号的有效报名或补录时，仍拒绝再次添加，避免重复计时。若仅有未录取记录、没有签到或时长证据，管理员可在核验实际服务后独立补录：原报名编号、未录取结果及处理说明保留，不会把该记录改成已确认而破坏初审摘要。身份或既有证据冲突时停止。跨班次多次服务继续按学号合并，台账保留逐场明细。

## 底表与故障恢复

献血车优先关联同日期、点位、时段中姓名学号一致且未被其他网站报名占用的源记录，其次使用空余岗位。没有空余岗位时新增一条已被本次补录占用的源行，不覆盖其他人的名额，也不制造新的空余报名名额。原未录取报名对应的失败源行，只在报名编号、姓名学号与账号均核对一致时更新为本次补录关联；其他人的占位、成功关联或停点仍停止同步。姓名、学号或关联冲突均不能覆盖。

底表写入后按网站报名业务标识重新读取确认。只有源行同步确认成功后才生成时长明细。普通活动的补录信息同样写入网站活动报名总表；最终导出时将核定的服务时长绝对写回补录报名行，保留“待录入”状态，不能据此表示已经录入第二课堂。

新增的临时补录源行在网站报名业务标识末尾保留 `-extra` 标记，平台生成后续周次时会排除这些临时名额；关联到原有空位的补录仍保留原岗位。外部独立维护的排班自动化若自行复制整周源行，也应排除这一补录标记，避免把临时人员变为固定配额。

每次补录有固定请求标识和内容摘要。报名、人工核验、时长明细、最终表保存任一环节响应丢失时，原请求重试会定位已有记录。浏览器会话保留未完成表单；服务器在私有活动状态 SQLite 中保存补录请求，刷新或丢失浏览器草稿后，也可从未完成补录恢复。未完成的普通活动补录会阻止最终导出，避免遗漏人员。

人工核验签名使用同一私有 SQLite 中持久化的独立密钥，不随会话密钥轮换失效。部署继续使用现有 `activity-lifecycle-<Base摘要>.sqlite`；日常私有状态备份需要包含该文件，不得把数据库、补录资料或密钥提交源码。功能不向外部业务库自动增列。


## 已改动原报名后的恢复

若人工把原未录取记录改成已确认，导致最终表提示「参与或签到依据已改变」，系统不会自动刷新摘要跳过初审。负责人或超管可在「时长审核 → 更多操作 → 重新打开初审」填写退回原因，再核对变化人员、完整预览并重新提交。入口在最终表加载失败时仍可使用，写入重新校验权限并记录审计；原有其他人员的初审与终审明细保留。已导出归档的活动仍禁止退回。

## 接近配置字段上限的最终归档

终审仍以 `FINAL:` 台账行保存逐场明细。若导出或邮件回执新增的流程状态会让活动配置超过 10000 字符，该流程状态转存到现有私有活动 SQLite 的 `activity_final_hours_states`，活动配置只保存状态与内容摘要引用；活动说明、岗位、名单及报名通知回执不删减。普通、小体积配置仍兼容原存储方式。

状态在活动配置提交前先持久化，后台发信只认已经绑定到活动的引用，不能提前发信。加载、归档下载、负责人邮件重试均读取同一份冻结状态，按活动 ID 与摘要校验；缺失私有状态时停止并提示恢复备份，不伪造已发送状态。日常备份必须继续包含 `activity-lifecycle-<Base摘要>.sqlite`。如果业务配置本身已经没有容纳最小引用的空间，仍在写入最终台账前拒绝，不提高字段上限或截断业务内容。


## 补录版本冲突与旧草稿

最终时长表的版本值按报名行 ID 排序生成，同一批数据仅返回顺序改变时不再误报冲突；实际明细、审核状态变化仍会拒绝旧版本写入。补录因版本过期被拒绝时，后端在创建人员前返回明确的 `manual_hours_version_conflict`。

打开最终表补录弹窗时先强制回源，避免使用展示缓存里的旧版本。“核对并重试”会再次读取最新表，核验当前账号仍可补录、活动尚未归档且原班次仍存在，再保留原请求编号和填写内容、更新版本值后核对提交。浏览器先前保存的失败草稿同样适用，不再反复重发过期版本；新版本不会丢弃原请求去创建重复人员。最新表读取失败时不发写请求，权限撤销、归档或班次改变时停止并保留原草稿。

# 时长入账与会员主页同步

终审通过并归档的最终表，以及旧流程中已批准且证据一致的明细，进入入账流程。负责人初审和 `RUNNING:` 明细不会入账；纸质到场确认无需伪造线上签到。普通活动、献血周和献血车共用该流程。

## 入账口径与目标

- 原「活动及时长汇总表」按姓名＋学号精确匹配，一人一行。**只增加尚未成功入账的服务时长**（培训、交通留在平台台账），保留历史累计和活动名称；新增「活动ID」列供机器匹配，活动名称仍沿用原有顿号拼接风格。
- 「网站志愿时长汇总表」从有效批准来源绝对重算，仍分列保存服务、培训、交通，不把初审或重复来源计算进去。
- 两张汇总表回读一致后，报名记录标记为「网站已入账」，报名表「志愿时长」保存三项合计。失败的状态回写可以安全重试。
- 个人主页每周一北京时间 06:00 起由后台任务检查更新；错过执行时会补偿。截止时间后批准的记录留到下一周；超管可以提前执行「立即同步个人主页」。
- 原「个人主页（编辑版）」每周一**只重算新建的「志愿时长（26-27）」学年列**（按平台已入账来源与已核对的外部历史基数、学年 2026-09-01～2027-09-01 重算）；不改旧「志愿时长」「志愿时长（25-26）」，也不覆盖任何学生自填字段。**「总志愿时长」公式已扩展为三列相加**（`{志愿时长}+{志愿时长（25-26）}+{志愿时长（26-27）}`），否则新学年时长不会计入总数；扩展时 26-27 列全为空，历史数值不变。
- 「网站个人主页表」同时更新，合计口径的摘要带 `hours-v2:` 前缀，读取时与旧版只计服务的记录区分。

本实现新增两列：「活动及时长汇总表」.活动ID、「个人主页（编辑版）」.志愿时长（26-27），由 `scripts/apply-hours-sync-schema.mjs` 单独迁移；并修正「总志愿时长」公式以纳入新学年列。不改既有列类型、选项、权限或原周期脚本。若连接没有写权限、字段不存在或缺少既有选项，停止对应步骤并报告；后台不会通过改设置来绕过。个人主页没有单独只读连接，或该连接指向另一个 Base 时，生产环境使用已经校验 UUID 的活动 Base 读取原主页，保证展示与入账使用同一数据源；不修改连接配置。

## 管理入口与用户展示

超管在「管理员中心 → 时长入账与同步 → 查看同步状态」查看结果、刷新、重试汇总与到期同步，或确认后立即同步个人主页。接口每次重新核对账号启用、验证及超管身份，写入还需 CSRF、同源和现有全局活动权限。普通成员不能调用全站同步或查看其他人的回执。

管理端已结束活动显示每人的汇总表、个人主页进度。会员中心参与记录与报名详情使用同一进度投影，展示三项核定时长及合计；待同步数不会额外加到官方总数。人工补录的 `manual:学号` 记录只向姓名、学号均匹配且已验证的本人显示，不赋予该用户修改原补录记录的权限。

## 重试、历史数据与备份

私有状态保存在运行状态目录的 `hours-posting-<Base指纹>.sqlite`，包含来源版本、写前值、目标绝对值、完成回执和进程租约。必须与原活动私有状态和业务表同一时间点备份、恢复；发布、回滚不得删除或重建它。文件不属于源码，也不得放入静态资源。

写入超时后先回读：等于预定目标则补记成功；仍等于写前值才重写同一绝对值；与两者都不一致则停止核对，不再次执行增量累加。数据库租约防止共享同一私有目录的两个网站进程同时入账；网站按人释放业务队列，避免一次大批量同步锁住全部前台操作。

原汇总表已含同名活动而没有本站回执时，不自动重复累计。超管核对实际人数、服务时长和原表记录后，可通过「核对原表已入账」补记回执；确认绑定当前来源版本及原表快照，变化后须重读。旧版冻结在活动配置中的最终明细可以只读补偿，不回写原配置。存在歧义的合并归档、重复人员、来源变化、冲销或丢失记录会暂停该人员同步，不影响其他人的有效明细。

原周期脚本仍按原有计划独立运行。NJUTable 普通行更新没有跨客户端原子比较交换；本站会做写前新鲜比较和写后校验，但不能锁住其他脚本或人工客户端。管理员应避免同时修改同一人的原汇总累计；发生冲突应先核对原表和私有回执，不能删除回执来强行重跑。原周期脚本若另行更新主页，展示时间仍会受到其原有计划影响，本次没有改动这些计划。

后台仅在生产活动模式启用，每分钟尝试补偿，并在终审归档后立即唤醒。HTTP 人工触发在生产中只排队，不等待整批外部请求；以刷新后的回执为成功依据。测试使用独立内存表和私有内存 SQLite，不写真实业务表。

## 底表反向修订与历史补同步

网站操作直接写 NJUTable；底表中已经批准的逐条时长如有改动，平台会暂停该人员的新入账，显示「底表修订待超管核对」。超管在管理员中心的同步状态里打开「核对底表修订」，查看原值、新值、原实际入账值和差额，填写原因并勾选核对后确认。系统按服务时长差额更新原汇总，绝对重算网站汇总和本学年时长，并回写报名表与修订人、修订时间；培训、交通继续分列保存。普通管理员无权确认。身份、活动归属或原审批依据变化时不能用此入口绕过核验。

修订先保存私有确认记录，再执行带写前值和写后回读的持久化任务。丢失响应、重启、重复确认不会再次加差额；底表在确认后又变动会暂停。原审批记录和历次超管修订原因均保留。归档文件根据已确认明细生成，修订后应重新下载；本流程不会擅自重发已经发送的邮件。

新建「26–27 学年」列已有数值但缺少本站同步回执时，不直接用网站小计覆盖。超管需通过「核对学年基数」说明原值中已包含多少本站服务时长；系统保留剩余历史部分，再加本次本站有效来源。后续底表累计值的调整会保留为外部余额，不反推到某场活动。只有原累计总数、没有日期和逐场批准依据的历史数据不会被虚构成网站活动明细。

历史补偿不限活动创建日期：已归档 `FINAL:`、旧配置内冻结的最终行，以及证据完整的旧 `SERVICE:` 均可补写。主页的自动补偿截止点按批准时间取北京时间周一 06:00；活动早于周一、但本周才终审的记录仍等下一周，超管「立即同步个人主页」可以提前执行。学年归属优先按实际活动日期，不会因为本周补审批而把往年活动归入 26–27 学年。

会员端沿用最新 main 的学年、排名读取和旧库回退规则。累计仍读取原「总志愿时长」公式结果，不擅自修改公式或把新学年值再次加到旧累计上。发布前需独立确认 main 的两列迁移已完成；生产同步在缺列或类型不符时停止，避免部分增量先写入。迁移脚本不随网页操作自动运行。

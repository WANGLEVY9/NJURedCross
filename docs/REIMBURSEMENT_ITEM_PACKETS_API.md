# 按项目整理报销材料：本地管理端接口

2026-10-12。仅用于隔离内存副本，未接远端写入、生产持久化或邮件。已接入本地初审、复审流程；人员轮换和真实账号配置继续等待负责人确定。

## 管理端操作

打开申请后，按稳定的支出项目 ID 分组展示原件，默认预览原始发票，可切换 PDF、图片原件；Word 下载核对。发票识别继续使用原件，补充材料不参与识别。核对原材料与金额后勾选确认，再手动点击“生成按项目合并材料”。生成不通过审核、不退回、不转给下一审核人、不登记付款；既有审批按钮与活动汇总能力继续独立运行。

每组顺序为发票 → 订单截图、订单和付款截图、付款截图 → 其他材料。同类材料保持上传顺序，PDF 内部页序、尺寸和旋转不变。订单及付款材料另生成一个 PDF 供下载；文件名称包含报销人、条目、金额、派生材料类型和组序号。原件名称、字节、来源哈希、原上传顺序和既有材料包均不重写。

整份申请共用的补充材料单独成组，不自动复制到每个项目。Word 在结果中明确列为另附原件，不转换、丢弃或声称已合入 PDF；纯 Word 组没有空 PDF 下载。历史资料缺少类型或可靠项目关联时，不能按文件名推断，生成会阻止并提示核查或退回补充。没有关联材料的支出项目在原件视图提示核对；程序不替负责人新增“一项必须有发票”的规则。

## 接口

以下接口均要求现有管理审核权限。所有响应和 PDF 均私有、禁止缓存；请求体不得传入人员名单、银行卡或修改原件。

- `GET /api/preview/reimbursements/requests/:id/material-packets`：读取当前版本的结果，没有生成则 `packets: null`。
- `POST` 同地址：传 `{ revision, bundleId, materialsChecked: true }`；成功首次生成返回 201，已有同一版本结果返回 200 和 `duplicate: true`。
- `GET /api/preview/reimbursements/requests/:id/material-packets/:revision/:groupIndex/merged`：下载项目合并 PDF。
- `GET` 同路径末段 `orderPayment`：下载订单及付款 PDF。

结果包括申请 ID、材料版本、材料包 ID、核对人、生成时间和各组的项目 ID、名称、金额、PDF 名称/地址/页数/来源页码及另附 Word 原件。来源页码同时保留原文件索引和哈希，便于对应原件。普通申请人不能调用生成、结果查询或派生件下载接口；原件访问权限保持原有账号归属规则。

生成与申请提交/审核共用本地队列。待补充状态不能生成；申请版本或材料包变化返回 409。补充重提后，新版本查询不会显示旧版本结果，旧下载地址也拒绝作为当前版本读取。失败不保存半成品，不改变申请历史或审核状态，不占用活动汇总名额。每轮最多 30 组版本结果，派生字节计入已有 500 MB 内存上限，生成独立工作线程最长 30 秒。

## 当前范围与后续

已接入本地二级审核与独立财务能力，见 [二级审核约定](REIMBURSEMENT_WORKFLOW_API.md)。新流程只允许初审环节生成材料，复审读取本版结果。人工付款登记、总表可选字段导出已实现。活动汇总读取本版已审核的项目合并件，按申请、项目及材料类型排序，共用材料仅附一次，Word 保持另附；没有在汇总时自动生成或替代初审结果。接口见 [活动汇总约定](REIMBURSEMENT_SUMMARY_API.md)。真实人员轮换和账号配置本轮不实现。

页面复制使用项目既有 `pdf-lib`，相关方法见 [PDFDocument.copyPages 官方文档](https://pdf-lib.js.org/docs/api/classes/pdfdocument#copypages)。

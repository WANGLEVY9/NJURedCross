# 普通活动名额与报名通知

## 数据职责

`网站活动流程表` 的普通班次容量与 `网站活动报名总表` 的有效报名记录共同决定剩余名额。报名总表只记录真实人员历史，不创建空白人员行；请假批准后原报名记录仍保留，再次报名生成新的报名编号。

`网站普通活动名额表` 是系统维护的名额清单：每个活动 ID 的第 N 个名额使用稳定的 `活动ID:N` 编号，记录日期、地点、时段、岗位、序号以及关联报名编号/行 ID。状态为“空闲”“已占用”“取消待审批”“已停用”。容量减少时保留多出的历史位置并停用，不删除。取消待审批仍占名额。献血车继续使用原排班底表，本表仅覆盖普通班次。

名额清单不是独立报名权威源。直接修改其占用状态不能新增、取消或阻止报名；应通过活动容量和平台报名/请假审核操作。后台每分钟在工作流写队列中重读并对账，允许短暂展示延迟，不在每次报名请求中重建全部名额。单进程队列并非 SeaTable 跨客户端事务；多实例部署前需引入统一写协调机制。

### 名额对应人员的最新资料

`姓名`、`学号` 为只供底表查看的文本投影：以名额的 `报名ID`、`报名行ID`、`活动ID` 核对报名总表，再按报名的 `账号ID` 读取独立身份库 `平台账号表.真实姓名/学号`。显示账号中的最新资料，不改写报名时保存的历史信息。仅这两个资料字段写入名额表，不复制账号库的其他字段。

生产后台启动时及每分钟在共享写锁内刷新，与名额生成和报名邮件开关独立。空闲、停用、已取消或找不到账号的名额清空姓名和学号；请假待审批仍显示当前人员。重复关联、行 ID 或活动不匹配、身份库读取失败时停止本轮写入，下一轮重试，不用姓名或学号猜测关联。直接在底表修改这两列会在后续刷新时被覆盖；外部手工编辑不受网站写锁保护。

两列由 `scripts/run-coordinated-script.mjs apply-place-profile-schema.mjs` 独立安装。先预览，再提供 `--apply --confirm=PLACE-PROFILES --digest=<本次预览摘要> --backup=<不存在的绝对私有目录>`；校验两个 Base UUID，备份原表结构和名额行，新增列后同步并回读核对。该维护不启用名额生成、报名通知或邮件，不修改报名记录、账号资料或名额状态。停止服务中的资料刷新即可停止同步；恢复展示字段可使用私有备份，账号库无需回滚。

## 报名审核与结果通知

普通活动（包括分组岗位、普通多班次活动）的新报名统一保存为“待筛选”，`是否报名成功=false`，不再自动确认。管理员明确批准后才提交为“已确认”；逐人批准立即提交该人的结果，不要求其他报名全部处理完毕。已有历史批准记录不因这一规则变更而退回待筛选，容量、重复报名与审核令牌校验继续生效。

`网站报名通知任务表` 保存通知意图、正文、目标邮箱、去重键、尝试次数与下次尝试时间，仅服务端与有底表权限的管理人员可访问。

- 启用 `PLATFORM_REGISTRATION_NOTIFICATIONS=true` 后，管理员逐人或批量批准提交成功即唤醒后台通知队列，不等待下一分钟扫描，也不在该审批请求中等待 SMTP。接口的 `mailPending=true` 表示通知待后台处理，不表示已经发送。显式保存草稿不触发通知。
- 普通活动的直接审核确认和献血车岗位正式确认，由 `reconcile(data)` 创建并处理通知任务。待筛选、岗位未同步、取消待审批不能发送成功邮件。
- 已发布的筛选名单及逐人即时批准使用同一持久化通知任务层；后台 `retryReviewed(data, {deliverRoster, statuses})` 恢复未发送任务、已知失败及发送回执，每分钟扫描作为唤醒失败或进程重启后的兜底。每轮默认轮转最多五个活动，每次 `deliverRoster` 最多尝试十封；未到重试时间的任务不阻挡后续邮件。正在调整的报名、请假待审批或已请假的报名不发送旧成功通知，尚未发布的草稿不发送通知。
- 幂等键沿用 `WF-RESULT:报名ID:yes/no[:名单版本]`。新报名编号代表新的报名，不复用被取消的旧记录。
- 已保存的任务先标记“发送中”，再调用 SMTP。成功接受后标记“已发送”；SMTP 接受不等于收件箱投递成功。
- 发送器明确标记可重试的失败允许指数退避，最多五次；超时、调用异常或进程中断等无法确认发送结果的情况进入“结果待核对”，不自动盲目重发。持久化成功回执可用于修复名单侧的邮件状态。`reconcile` 每轮最多尝试十个自动任务。
- 邮件不可用不会撤销报名；任务保留待发送。开发 console 通道不能作为通知成功凭据。
- 报名成功邮件含日期、时段、地点、岗位、报名编号及详情链接，说明取消须管理员批准，时长以核验后正式录入为准。

当前管理端尚无独立通知任务工作台；重试耗尽和结果待核对由运维核对任务表及 SMTP 接受证据，禁止简单批量重置任务。不得把通知表或正文通过公共接口返回。

## 请假审批通知

启用持久化通知后，`decideLeave` 在工作流写锁内完成业务校验，再调用 `prepareLeaveDecision(event, row, {approved, reason})` 预写通知意图，之后才更新请假决定。预写失败停止业务更新；预写本身不调用 SMTP。审批成功后唤醒后台，由 `reconcile(data)` 同时处理请假批准和驳回，无需另建发送任务或数据库字段。

任务以报名编号、请假申请时间和批准/驳回决定去重，并保存当次处理说明。记录仍为“待审批”时不发送，只有对应决定落库后才发送；后续报名审核修改处理说明不会改写当次邮件。请假批准仍保留原报名历史，邮件失败不回滚已提交的决定。重复申请采用新的申请时间，历史请假决定不自动补发。

后台快照必须与通知任务读取保持一致，不能用预写任务之前取得的旧快照将新任务判为“已取消”。启用前须验证这一并发场景，以及通知预写后业务写入中断的恢复路径。调用 `retryReviewed` 的外层不能持有工作流写锁或通知队列锁，避免反向获取锁。

## 开关关闭时的行为与当前核验状态

`PLATFORM_REGISTRATION_NOTIFICATIONS=false` 时，已审核名单（reviewed roster）的即时批准继续走既有 `deliverRoster` / `sendMail` 路径。普通/献血项目直接批准、拒绝及请假决定在提交后写入私有状态目录的 `activity-decision-mail.sqlite`，由后台立即发送；不依赖通知任务表初始化，不扫描补发历史决定。`mailPending=true` 表示已接受通知任务，不表示邮件已送达。关闭该开关不是关闭全部邮件。

本地决定任务的申请身份、请假处理说明和发送正文均加密保存。发送前重读完整权威记录；请假新申请或决定不匹配时取消旧任务。明确可重试失败最多三次；异常、未知发送结果与重启时遗留的发送中任务进入待核对，不盲目重发。业务决定和本地排队不是跨库事务，排队失败不会撤销已保存决定；操作人员仍需核对通知状态。已启用通知任务表时，批准/请假继续使用预写意图与原后台恢复路径；直接拒绝使用本地队列。

截至 2026-10-17，维护协调方报告的生产只读环境核验结果为：工作流处于 production 模式，`PLATFORM_REGISTRATION_NOTIFICATIONS=false`、`PLATFORM_ORDINARY_PLACES=false`。通知任务表、字段及安全 baseline 正在进行只读元数据核验，尚不能据此认定已具备启用条件。生产初始化和开关启用待 Owner 明确授权；本次文档更新不执行迁移、不修改生产配置、不发送真实邮件。

## 迁移和启用

先只读核验目标表、字段及 baseline，再运行 `scripts/migrate-registration-operations.mjs` 预览。使用正式服务端环境配置，工具校验工作流 Base UUID，仅输出数量和摘要。不得因表或 baseline 缺失而自动迁移；生产写入须取得 Owner 授权。写入要求 `--apply --confirm=REGISTRATION-OPERATIONS --digest=<当前预览摘要> --backup=<不存在的绝对私有目录>`，备份目录 0700、文件 0600，不进入 Git。

迁移只新增两张系统表、预留普通活动名额，并为已有已确认/已签到记录设置“历史未补发”基线，不修改报名总表，不调用 SMTP。重试须重新预览，不重复初始化历史基线。业务并发变更导致摘要或最后核对不符时停止，核对后再运行，不能覆盖新增报名。

完成授权初始化、验证安全基线及部署源码后，再按获准范围分别设置 `PLATFORM_ORDINARY_PLACES=true` 和 `PLATFORM_REGISTRATION_NOTIFICATIONS=true`。两个开关独立；通知需要迁移基线及生产 SMTP 配置，默认两个开关关闭。只支持当前单个 Node 服务实例，不允许多个 worker 同时消费。关闭相应开关可停止名额同步或通知任务表的后台消费，但 reviewed 同步邮件兼容路径仍可能发送；开关不能撤回已接受邮件，也不删除历史数据。

生产验证只读检查名额数量、占用关系、通知基线和服务发布清单。真实邮件验收使用明确获准的收件人，不创建虚假生产报名，不向历史报名者群发测试信。

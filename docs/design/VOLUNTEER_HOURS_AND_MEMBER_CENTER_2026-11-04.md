# 志愿时长入账与会员中心升级方案（待评审）

> 日期：2026-11-04　状态：P0 / P1 已上线；**P2 会员中心升级已实现**
> 效果图见 `docs/design/member-center-redesign-preview.html`。

## 一、业务诉求（来自 11-04 讨论）

1. 一个活动的志愿时长**录入并完成审核后**，应自动入账到对应志愿者；志愿者所有信息存放在 NJUTable 的「个人主页（编辑版）」。
2. 「活动及时长汇总表」/「个人主页（编辑版）」里红框标出的时长列，应在活动完成入账后**立刻更新**，且数值格式、活动名称风格与旧数据保持一致。
3. 业务希望「**直接写入汇总表，然后每周一同步**」，使过程可控；会员中心要能看到**每场活动的进度**并能**自查时长**。
4. 会员中心当前偏简陋，需要 UI/交互升级。

## 二、代码现状核查（结论：链路断在最后一公里）

| 环节 | 现状 | 结论 |
| --- | --- | --- |
| 录入 / 初审 / 终审（新版 `RUNNING:`、`FINAL:` 台账行） | `lib/events/running-review.js`、`lib/events/final-hours.js` | 已完成 |
| 终审导出 | `final-hours.js:250-267`：把 `FINAL:` 行置「已批准」，活动置「已结束」，生成工作簿并发邮件 | 已完成 |
| 入账（写汇总 + 个人主页） | `workflow.js:450-472` 的 `mirror()`：绝对重算后写 `WF.summaries` / `WF.profiles`，回写台账「已入账」、报名「网站已入账」 | **有实现，但只服务旧链路** |
| 入账触发 | 唯一入口 `POST /api/volunteer/workflow/hours/:id/post`，需人工点管理台「入账并同步个人主页」 | **新版链路接不上** |
| 每周一同步 / 后台汇总 | 全库无相关定时任务；`server.js` 的定时器只做对账、邮件、献血车排班、快照预热 | **缺失** |
| 会员中心时长数字 | `member-workspace.js:67-81` 读 `data.platformHours`，来自外部「个人主页（编辑版）」按姓名+学号匹配（`lib/events/volunteer-platform-hours.js`） | 依赖旧表，且只有两个总数 |
| 每场活动进度 / 时长自查 | `/api/portal/workflow/me` 只返回报名状态、`录入状态`、报名表 `志愿时长`，且**过滤掉 `RUNNING:`/`FINAL:` 行** | **缺失** |

### 断点根因

`workflow.js:1485` 的 `post()` 会对目标台账行执行 `assertReviewedLedger()`，该函数（`lib/events/hours-review.js:39-57`）要求幂等键必须是 `SERVICE:<报名行ID>`。新版导出的行幂等键为 `FINAL:<报名行ID>`，因此必然被拒绝；`mirror()` 又把同账号下所有「已批准」行一起校验，所以同一账号存在新版行时，**旧链路的入账也会被连带阻断**。这正是聊天里「底表状态都是待入账 / 逻辑没做好」的技术解释。

另外代码中**不存在「待入账」状态**（只是文案），台账实际停在「已批准」。

## 三、旧平台怎么做的（用现有 API Token 查证）

查询对象：`南大红会 志愿服务平台` Base（`SEATABLE_VOLUNTEER_API_TOKEN`），`GET /api-gateway/api/v2/dtables/{uuid}/metadata/` 与 `rows/`。

| 表 | 结构证据 | 作用 |
| --- | --- | --- |
| `志愿时长录入excel生成`（id `7iCi`） | 有「生成"志愿分工表"与"志愿时长表"」**button 列**、「志愿时长录入表」file 列 | 负责人录入活动内容，点按钮由自动化规则生成 Excel |
| `活动及时长汇总表`（id `sL50`） | 列：`学号 / 姓名 / 活动名称 / 志愿时长 / 个人主页（编辑版）(link)` 等；样例行 `_creator=Automation Rule`，活动名称为「25秋 爱心义卖、、9.22 餐厅志愿者…」拼接串 | 自动化规则按人写入「活动名称 + 志愿时长」汇总行，并用 link 关联个人主页 |
| `个人主页（编辑版）` | `志愿时长`(number)、`志愿时长（25-26）`(number)、`总志愿时长`(**formula：`{志愿时长}+{志愿时长（25-26）}`**)、`活动时长`(link 到汇总表)、`排名`、`是否已通知入会` | 每人一行；公式列自动求和；学年列人工/规则分区 |

也就是：**旧平台靠 NJUTable 端的「按钮 → 自动化规则 → 汇总表 → link/公式列」隐式联动**，没有平台侧的幂等键、任务状态、失败重试与审计记录。好处是配好规则后不用写代码；代价是：

- 谁在什么时间把多少小时写给了谁，不可追溯；
- 规则失败或重复触发会把时长写错，只能人工对照 Excel；
- 学年列靠规则分配，改学年口径要逐条改规则；
- 平台代码无法判断"是否已入账"，所以会员中心只能展示两个外部总数，看不到逐场进度。

> 注：SeaTable 的自动化规则定义不在当前 API 可读取的端点上（尝试 `automation-rules` 均返回 HTML/404）；结论由列类型、button 列、公式列、样例行的 `_creator=Automation Rule` 与截图交叉验证。

## 四、新平台推荐架构（显式、幂等、可审计）

核心原则：**平台是唯一写入者，NJUTable 只作为数据存储；所有跨表写入以持久化任务驱动，可重放、可对账。**

### 4.1 一张「入账任务表」串起三步

新增 `lib/events/hours-posting.js`，任务落 `jobs.sqlite`（复用现有队列），幂等键：

```
POST:<活动ID>:<报名行ID>          // 单人任务
SYNC:<学年>:<ISO 周一日期>         // 每周同步任务
```

终审导出成功后（`final-hours.js:exportFinalHours` 末尾）**就地入队**单人任务；任务执行按账号聚合，一次写入：

1. **平台侧（即时）**
   - `网站服务时长明细表`：`状态 已批准 → 已入账`、写 `入账时间`；
   - `网站志愿时长汇总表` / `网站个人主页表`：按该账号全部已入账明细**绝对重算**服务/培训/交通，写 `明细摘要`（checksum）与 `更新时间`（复用 `mirror()` 的幂等算法，扩展为支持 `FINAL:` 行）；
   - `网站活动报名总表`：`录入状态=网站已入账`、`志愿时长=服务时长`；
   - 用户端 `/api/portal/workflow/me` 立即能看到"已入账"与逐场时长。
2. **旧平台汇总表（即时，业务要求"可控"）**
   - `活动及时长汇总表`：按 `学号+姓名` 匹配，写 `活动名称` 与 `志愿时长`；数值列保持 number/2 位小数，活动名称沿用现有 `、、` 拼接风格，同时写入 `活动ID` 之类的稳定键（需新增列，避免同名活动串号）。
   - **不写公式列** `总志愿时长`（由 SeaTable 自行计算）。
3. **个人主页（每周一同步，也可手动触发）**
   - `SYNC` 任务周一 06:00（Asia/Shanghai）执行：按学年规则把汇总表时长汇总到 `志愿时长` / `志愿时长（25-26）`（新学年列命名需与业务确认），只覆盖时长类列，**绝不覆盖学生自填字段**（姓名、院系、联系方式等）。
   - 提供管理端「入账中心 → 立即同步」按钮，供活动结束后即时刷新；同步结果写 `同步日志`（时间、影响行数、checksum、操作人）。
   - `Persistent=true` 的 systemd timer + 进程内兜底：漏跑后启动即补，避免"周一服务正好在重启"。

### 4.2 与旧做法相比的改进

| 维度 | 旧平台自动化规则 | 新方案 |
| --- | --- | --- |
| 触发 | SeaTable 按钮/规则，平台不可见 | 终审导出成功后平台入队，状态可见 |
| 幂等 | 无 | 任务幂等键 + checksum + 绝对重算（重试不会重复累加） |
| 失败 | 静默失败 | 任务状态 `queued/running/failed/needs-attention` + 告警 + 手动重试 |
| 学年 | 规则内硬编码 | 学年配置常量（默认 9/1 分界），可审计 |
| 用户可见 | 只有外部总数 | 逐场进度 + 时长明细 + 同步时间 |
| 回滚 | 无 | 任务日志 + 明细摘要，可反向对账 |

### 4.3 需要确认的口径（评审问题）

1. 「每周一同步」是否指：**汇总表即时写、个人主页每周一重算**？若是，活动结束到周一之间，会员中心以平台侧"已入账"为准（即时），旧表总数显示上次同步值并标注时间。
2. 学年列名沿用 `志愿时长（25-26）` 还是要新建 `志愿时长（26-27）`？当前导航显示 26–27 学年。
3. 培训 / 交通时长是否也要写进旧平台红框列？旧 `活动及时长汇总表` 只有 `志愿时长` 一列，建议**只写服务时长**，培训/交通留在平台台账，避免口径不一致。
4. 旧平台 `活动名称` 的拼接风格（`、、`）是否必须完全保留？建议保留展示列，同时新增 `活动ID` 列做机器匹配。

## 五、会员中心升级（效果图见同目录 HTML）

设计目标：**一眼看到"我有多少时长、每场活动走到哪一步、什么时候同步"**，同时保持平台现有暖米色 + 红会红的视觉语言与原生 JS/CSS 架构。

- 顶部 Hero：头像/姓名/学号/学年/会员徽章，右侧累计时长大数字 + 学年进度环；
- 三张统计卡：累计志愿时长、学年时长、待入账时长（带状态色与"上次同步"时间）；
- 「我的活动进度」时间线：每场活动一行，含日期、名称、状态徽章（报名成功 → 已签到 → 初审中 → 已终审 → **已入账**）、服务/培训/交通时长、展开看明细；
- 「同步说明」条：明确"活动结束即入账到平台，每周一 06:00 同步到志愿服务平台"，显示上次/下次；
- 原有「个人资料 / 我的技能 / 温暖连接」重排为轻量胶囊导航与卡片，减少表单压迫感；
- 空状态、加载骨架、错误态与移动端（单列、时间线改纵向）都有对应样式。

配套接口：`GET /api/portal/workflow/me` 增加 `hoursTimeline`（逐场状态与时长）、`posting`（已入账/待入账汇总）、`sync`（上次/下次同步时间）；不新增第二个数据源，避免会员中心再出现"两个总数对不上"。

## 六、实施分期与验收

- **P0（修断点）**：`mirror()` 支持 `FINAL:` 行；终审导出成功后自动入队；台账「已入账」、汇总/个人主页/报名表即时更新。验收：一个活动终审导出后，无需人工点按钮，台账与三张表在 1 分钟内全部更新；重复执行导出不重复加时长。
- **P1（可控同步）**：入账中心页面 + 每周一 timer + 同步日志 + 手动同步；旧平台汇总表/个人主页按口径写入。验收：周一漏跑可补、同步日志可查、失败行可重试、学生自填字段零覆盖。
- **P2（会员中心）**：按效果图改造前端 + `/api/portal/workflow/me` 扩展。验收：志愿者能自查每场活动的状态与三项时长，桌面/移动端一致。

每阶段都补：单元测试（幂等、半成功重试、学年边界）、浏览器用例、以及一次生产环境小范围对账（抽查 3 个账号 × 2 场活动）。

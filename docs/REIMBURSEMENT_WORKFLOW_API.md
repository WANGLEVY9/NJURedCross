# 二级报销审核：本地接口与协作约定

2026-10-12。用户确认逐份申请复审、按活动分组查看；复审退回初审，由初审决定是否要求申请人补充。本地流程为提交 → 初审 → 复审 → 待打款 → 人工登记已打款；新增台账及可选列 Excel 导出。未连接真实报销库、真实账号权限、邮件或银行转账，所有操作只修改隔离内存。

## 状态与操作

| 状态 | 用户／管理端含义 | 允许的处理 |
| --- | --- | --- |
| `pending` | 待初审 | 初审送复审；初审退回申请人 |
| `final_pending` | 待复审 | 复审通过；复审退回初审 |
| `initial_returned` | 复审退回初审 | 初审重新核对后送复审；或退回申请人 |
| `returned` | 待申请人补充 | 申请人上传新材料并重新提交 |
| `approved` + `paymentStatus: pending` | 复审通过／待打款 | 可活动汇总；有打款登记权限者记录实际打款结果 |
| `approved` + `paymentStatus: paid` | 已打款 | 查看登记记录、台账及导出；不重复登记 |

新申请记录 `workflowVersion: 2`、`revision`（材料版本）、`stateVersion`（每次提交或审核流转递增）、`initialReview`、`finalReview`、`paymentStatus`。未复审通过时付款状态为 `not-ready`，复审通过后为 `pending`。生成材料与生成活动汇总不改变付款状态。

复审退回初审不改材料版本。初审可直接重新核对同版材料，再次送审；若需要申请人补充，必须先由初审退回给申请人。申请人不能在 `initial_returned` 阶段越过初审自行重提。申请人重提使用新材料包，材料版本递增，清除本版初审／复审结论，返回待初审。历史意见、操作人、时间、材料版本及状态版本均保留。

## 权限

本地服务接收服务端可信身份中的 `financePermissions`，可配置 `initial`、`final`、`view`、`payment`。不能从请求体获得权限，原有 `canReview` 物资管理员标记不自动授予财务审核权。

- `initial`：查看材料、生成项目合并件、初审送审或退回申请人。
- `final`：查看原件和初审合并件、逐份复审、维护活动资料并生成汇总、导出台账。
- `view`：查看申请、材料与已有汇总、导出台账，不生成材料、不审核、不改活动资料或付款状态。
- `payment`：仅查看复审通过的申请，记录实际打款结果；不能审核、生成材料或导出台账。需查看全量台账或导出时另配 `view`。

人员按固定职责配置，可换届／轮换；没有每笔申请临时指定审核人的表单。正式账号能力接入仍待负责人确定，不修改真实账号表或权限结构。仅本地预览的默认身份显式具备初审、复审、查看和打款登记能力，模拟会话不代表实际账号已授权。

“同一笔必须由不同人初审和复审”作为服务端 `requireDistinctReviewers` 配置。当前默认关闭，避免把尚未确认的人员规则硬编码；隔离验证使用开启配置与不同身份，验证限制确实生效。开启时复审通过和复审退回均不能由本版初审人执行。请求体不能覆盖此配置。

## 前后端对接

配置接口 `GET /api/preview/reimbursements/config` 增加 `workflow: { version: 2, permissions: [...], requireDistinctReviewers, paymentRegistration: true, ledger: true, exports: true }`，只返回本账号能力。管理端据此显示操作，后端独立核验权限与环节。前端兼容旧运行实例：能力未开启时隐藏新入口，不自动重启服务。

审核继续使用 `POST /api/preview/reimbursements/requests/:id/review`：

```json
{
  "action": "initial-approve",
  "revision": 1,
  "stateVersion": 1,
  "materialsChecked": true,
  "note": "已核对本版原材料"
}
```

操作为 `initial-approve`、`initial-return`、`final-approve`、`final-return`。两类退回必须填写意见；两类通过必须勾选人工材料确认。初审通过前必须手动生成本版按项目材料；OCR 或生成成功不会代替送审。复审通过只进入待打款。旧 `approve/return` 不能用于新流程跳过审核。

材料版本或状态版本不匹配返回 409，权限不足返回 403，缺少核对确认、材料包或退回意见返回 400。请求与审核、生成材料使用同一本地队列；即使材料版本相同，复审退回／重新送审后旧页面仍不能用旧状态版本通过。重复点击和并发审核最多一次成功，其他操作须刷新。

负责用户端的同学可继续使用现有提交、自己的申请列表、退回补充与重提接口。列表已返回新 `statusLabel`，只有 `returned` 显示补充重提入口；可进一步增加流程进度条。不要把 `initial_returned` 显示为要求申请人补充。`approved` 本身不代表到账；登记后 `paymentStatus: paid`、`statusLabel: 已打款`，并返回 `paymentRecord`。

## 打款登记与台账

管理端审核页及 `/console/reimbursements/ledger` 提供登记入口。必须已完成本版初审和复审、付款状态待打款、收款银行卡号符合现有基本格式。金额固定为本笔复审通过金额，不支持部分付款、改收款卡、撤销、退款或直接转账。经费卡号 `4301011309001041656` 仍只用于报销表，不能作为申请人的收款卡。

`POST /api/preview/reimbursements/requests/:id/payment`：

```json
{
  "revision": 1,
  "stateVersion": 3,
  "amount": "15.00",
  "paidDate": "2026-10-12",
  "reference": "凭证编号（选填）",
  "note": "登记备注（选填）",
  "confirmed": true,
  "idempotencyKey": "一次登记的唯一标识"
}
```

界面先核对收款人、银行卡号和金额，再确认实际打款完成。日期不得晚于当天（上海时区）；后端核验金额、权限、版本和当前状态。成功仅将 `paymentStatus` 变为 `paid`、递增状态版本并记录操作人、实际日期、登记时间、金额、凭证和备注；保留审核结论与原件。首次返回 201，同一身份同一标识同一内容重试返回 200，不重复记账；不同内容复用标识、旧版本或重复登记返回 409。每轮内存最多 500 次登记。

`GET /api/preview/reimbursements/ledger` 支持 `activityId`、`status`、`from`、`to`、`search`。日期筛选指费用发生日期；状态 `approved` 为待打款、`paid` 为已打款。权限按记录过滤，再计算申请、待打款、已登记打款笔数及金额。台账投影不带身份证和银行卡字段；需要打款核对时另用受权限保护的申请详情。

`POST /api/preview/reimbursements/ledger/export` 接收 `{ mode: "requests" | "items", columns: [...], filters: {...} }`，列白名单见 `public/app/shared/reimbursement-ledger-fields.js`。总表逐份申请一行，项目及发票明细逐项目一行；申请金额和打款金额仅在该申请首行出现，项目金额各计一次。六项发票信息仅使用已有文字层／OCR 缓存，多张发票逐份列出，待核对及冲突明确标注；不在导出时启动 OCR 或审批。最多 10000 行、26 列，响应为私有 XLSX（`Cache-Control: no-store`）。

界面可选择导出列，后端再次核验白名单，拒绝身份证和银行卡列。自由备注或发票原文不进行自动敏感内容识别；不能将结构化字段排除理解为全文脱敏。字符串始终写成 Excel 文本，不执行公式。旧缺少可靠项目关联的记录标为待核查，不按名称推断。

所有接口仍受本地回环地址、会话及写请求 CSRF 保护；台账导出也需要 CSRF。重启会清空登记和上传材料，当前没有真实持久化或生产权限绑定。

## 汇总与旧数据

活动汇总仅允许本版初审和复审结论都有效的 `approved` 申请。初审通过不纳入；旧一级通过不自动补造复审结论。生成汇总只占用对应材料版本的汇总名额，不登记付款。活动材料包现读取本版已审核的项目合并件，按申请及项目顺序排列，每个项目内部为发票、订单及付款、其他材料；共用材料仅附一次、Word 原件另附。预览和生成记录提供目录及原件对应页码。缺少本版派生件不自动生成，不回退到旧整份材料。

服务默认二级流程。`workflowVersion: 1` 只作为旧协议的显式兼容模式，供隔离旧合同测试使用；正常预览不启用。旧测试明确声明该模式以保留原件、识别、金额、退回等既有行为，新流程另有独立的权限、状态、并发及浏览器验证。没有真实数据迁移或将内存测试记录回写数据库的入口。

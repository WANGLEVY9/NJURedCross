# 管理端 NJUTable 加载故障（2026-10-28）

## 已确认的原因

生产基线为 `1a7a215d`。当前登录会话访问 `/api/notifications/overview`
返回 HTTP 503、`incomplete_operational_data`；不是 NJUTable 认证失败。
服务器仍能成功查询活动目录、详情和底表。

只读核对发现旧版 `活动报名总表` 已有 5,201 行，汇总读取却限制为 5,000。
完整性检查正确阻止了截断结果，但通知接口通过 `Promise.allSettled` 汇总后
传播该错误，导致总览指标和整条待办队列一起失败。

服务器日志还出现活动初审 GET 在约 6,000ms 被客户端取消、重试后成功的情况。
浏览器在收到响应头之前启动 6 秒停顿计时器，可能将正常冷查询误判为停顿，
重复消耗 NJUTable 查询额度；原有总读取期限为 12 秒。

## 修复边界

- 仅旧版志愿汇总将完整读取边界提高至 100,000 行，每页 1,000 行；保留越界失败，
  不把读取异常转成空列表或零统计。相同展示读取在 30 秒窗口合并，按表写入失效。
- 保留 listRows 的双向关联行 ID 证据。生产抽样确认 SQL 会将关联字段转换成显示文字，
  直接用 SQL 替代会破坏报名与签到身份核验。
- 新版活动详情、参与记录等仍按项目 ID 查询，没有改回全表扫描。
- 浏览器在响应头到达后才启动响应体停顿计时器；总期限仍是 12 秒，写入不自动重试，
  用户主动取消仍立即生效。
- 不修改生产配置、权限、底表数据或业务审批结果。

## 验证

发布前生产只读完整读取：5,201 条报名、1,267 条签到，约 4,028ms。
使用原有核验逻辑得出：源表已录入 1,911、待名单确认 2,886、需核验 22、
待签到核验 241、待核定时长 29、待录入 112；均非截断结果。

回归覆盖 5,201 行且末行仍进入待录入核验、关联 ID 保留、并发读取合并、
写后失效、100,000 行上限越界拒绝、慢响应头不重复请求、响应体停顿恢复、
总期限与主动取消不变。部署后须再核对 Actions、发布清单、运行文件哈希与真实登录页面。

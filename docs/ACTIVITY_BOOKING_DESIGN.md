# 活动发现与报名设计（P07–P10）

## 设计依据

活动广场需要在真实活动很少时仍完整表达参与路径。周历承担班次比较，不能使用全表位移吸引注意；详情承担核对与提交，应让身份、须知、容量和操作反馈各有位置。普通活动有直接确认/候补及多场次，与献血车的审核流程分别呈现。

## 页面与样式所有权

- `events.js` 根据聚合后的项目数标记 empty / featured / curated / list。单活动显示完整描述、时间地点和参与流程；2–4 项增加列表间距，5 项起收紧密度。保留搜索焦点、URL、状态播报和献血车聚合。分类明确标作“地区 / 专项”，沿用真实模型，校区独立。
- `calendar.css` 负责预约工作台、七列日期、密度、业务状态。长点位在桌面独立滚动，轨道和指示器保持等宽；图例与卡片使用同一套固定语义色。仅控件有过渡，筛选不再使七列整体飞入。保留周范围、选中班次、空日、今天、周末、返回焦点。
- `booking.css` 负责两类报名详情，迁出原 calendar.css 中的详情声明。献血车摘要在上方，参与流程在左，个人信息面板在右；足够宽高的桌面允许身份确认面板 sticky。普通活动使用完整标题区、介绍与可选场次、容量侧栏。
- `session-choices.js` 复用原生 radio 选择，保留 Tab / 方向键与焦点，不重建节点。普通活动的页面选择传入抽屉；候补预览、按钮文字和侧栏数量随所选场次更新。全活动统计单独注明。

## 业务边界

不修改后端接口、资格校验、容量、生产表或主题定义。献血车 POST 仍仅提交 consent，身份和校区仍由服务器绑定账号。须知确认在本页刷新时保留；提交中阻止重复动作；成功只宣告已提交待审核；出错保留班次与确认状态。个人信息读取失败有重试入口。

普通活动 POST 字段不变：姓名、邮箱、校区、备注、场次与 consent。姓名/邮箱仍只读，既有可编辑字段保留。结果编号、状态和二维码均来自响应，不由前端制造。

## 验证

浏览器合成用例覆盖 0/1/3/10 活动、五主题周历、49 个班次、空日/全满/筛选/周次/密度/返回焦点，献血车授权、资料缺失、错误、防重复提交，以及普通活动单/多场次、关闭、候补、确认、错误和凭证。截图数据来自独立 preview，不写入 NJUTable；线上仅检查公开页面，不能据此宣称真实报名已验收。

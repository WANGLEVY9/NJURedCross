# 活动信息修改的配置完整性与恢复

报名中的多岗位活动曾将完整修改请求、全部岗位补丁、报名补丁和历史活动内容嵌入
“报名页配置”。该列为 text；生产故障中，两条主活动配置读出长度均为 10000，
JSON 在字符串中间结束。失去 positionPlan、workspaceSubmission 等配置后，主活动
与岗位组可能分列，出现空名单和不可编辑的入口。字段被截断的具体平台环节仍须
结合 NJUTable 修订历史核实，不能仅凭长度推断由谁操作。

## 修复后的保存

- 完整请求、修改计划和修改前活动快照写入现有私有
  `activity-lifecycle-<Base摘要>.sqlite` 的 `activity_workspace_edits` 表，
  按活动行 ID 和原请求 token 定位。记录不可覆盖，恢复时验证内容摘要、操作者、
  token、版本和请求摘要。业务表只存短引用；活动配置中只保留有限条历史摘要。
- 首次发布/创建及本次活动信息修改路径写入前检查 JSON 和 10000 字符边界。
  修改计划中每个岗位、处理中与完成后的主配置均在任何业务写入前预检。
  原始岗位配置本身超出边界时明确拒绝，不截短内容或丢弃岗位来继续。
- 修改主配置后直读回核，值不一致或 JSON 不完整时停止，不凭写入 ACK 宣告完成。
  原操作者使用“核对保存结果”恢复原计划；缺失或不一致的私有回执不得重建覆盖。
  已有完整的旧版内嵌回执仍可继续核对，并转存为私有回执。
- 目录对损坏配置明确标记异常，管理端提示从完整备份恢复，而不是展示空名单并
  继续保存。对损坏活动的报名和主要写入入口明确拒绝。不会猜测、自动补全历史 JSON。
- 普通多班次报名以项目的报名开关和截止时间为准；岗位里的历史截止快照不再
  二次否决已延长的项目截止。单岗位活动继续使用自身截止，定时发布、班次开始、
  审批、名额、名单关闭等校验保留。

## 编辑读取、批量保存与中断核对

- 编辑表单复用本请求的活动权限证据，只加载本项目的岗位、签到、时长门禁，
  不再为打开表单先加载名单和献血车全源，再重复读取编辑权限。
- 新修改仍在写队列内重新取权威活动快照；参与记录限定为本项目，跨活动时间
  冲突按本项目报名人的账号与学号查询。只有相关报名引用虚拟献血车场次时才
  读取献血车源。完整性、容量、请假、权限与版本校验保持。
- 原请求恢复先按活动行 ID 查询；已完成直接返回，不读名单、签到、时长表。
  处理中按私有回执定位项目、岗位、报名记录；未变字段跳过，岗位与报名采用
  每批最多 100 行的绝对值更新。新岗位同样批量创建，恢复按原活动 ID 查重。
- 所有岗位、报名显示字段和移除岗位必须回读匹配，才允许完成主配置与恢复
  项目报名开关。部分批次失败、响应丢失或成功响应漏写时保留原回执，重新核对
  仅继续剩余补丁。不能删除回执或另建同名活动来解锁。
- 浏览器以服务端核验完成的保存响应为准，页面刷新失败单独提示。核对时若
  远端尚无恢复引用，但版本与原 token 仍匹配，可重交完全相同的请求，由服务端
  校验私有计划与参与记录；版本变化时停止，不覆盖别人的修改。

合成回归覆盖 16 岗位、120 条报名、延迟依赖、批量半成功、静默漏写、进程重建、
未变名单免写，以及保存后刷新失败与写入前中断。真实业务表不写合成记录。

修改中断后名单审核可能继续推进。恢复时保留主记录和岗位的最新 `rosterReview`，
不得把旧计划中的审核和通知状态写回去；计划本身及其摘要保持不可变。

## 历史截断记录的维护工具

`scripts/recover-legacy-workspace-edit.mjs --parent=<原活动行ID>` 默认只读预演。
仅支持旧请求的完整内容、摘要、原岗位 ID 均可提取，且下一版所有岗位已经有效
批准、重算计划与现有岗位逐字段一致的情形；其余情况停止，不能猜测批准数据。
通过预演后，维护执行还需要 `--apply --expected-digest=<预演摘要>` 和独立私有
`--backup-dir=<绝对路径>`。工具核对生产 Base，取得现有共享写锁，备份原业务记录、
计划及活动私有 SQLite 后才写入，并回读核验。不要将这些备份提交源码。
SQL 与普通行接口的关联列表示不同，核验岗位使用与备份相同的读取接口。

2026-10-27 已完成的数据恢复（独立于代码发布）：

- 10.31 会员大会：原父记录恢复为第 4 版、`complete`，配置 2772 字符；
  原两岗位和 73 条报名全部未变，私有回执摘要、批准摘要和当前编辑权限均通过核验。
- 10.29 献血周：按原私有回执完成第 3 版；16 岗位及恢复时的 152 条报名全部未变，
  包括原保存后更新的名单审核状态。10.30 保持 `complete`。
- 以上操作未替换线上运行代码，也未主动重启服务。读取与批量保存优化仍需另行发布。

## 发布、备份及旧数据处理

此变更无需修改 NJUTable 列类型；私有 SQLite 在应用打开时增建回执表。
源码发布和真实数据恢复仍为两项独立操作。本地测试仅使用合成业务表。

备份和恢复必须包含整个活动状态 SQLite；回执包含活动历史与报名补丁，应留在
已有私有状态目录，不能提交 Git、打入发布包或公开下载。处理中引用依赖该库，
不得删除回执来解锁。旧代码不能读取新版处理中引用：回滚前先用支持此格式的
版本完成核对，或保留新版本与对应私有库用于恢复；不能用旧版强行继续保存。

本变更不会自动修复已经截断的生产主记录。获准维护后应：

1. 备份原始损坏记录、项目表、全部相关岗位、报名及私有状态。
2. 从可信完整快照/提交草稿和实际岗位核对恢复方案，保留原活动、岗位、报名 ID；
   无完整来源时停止，不以截断字符串补括号代替恢复。
3. 核对并完成原修改结果；由负责人确认新截止时间。检查项目门禁、岗位关联、
   审批摘要与报名记录的一致性，不自动重新批准、重建活动或重发邮件。
4. 验证目录归组、名单、编辑权限与公开报名可用状态；合成报名测试继续留在隔离环境。

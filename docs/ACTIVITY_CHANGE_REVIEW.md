# 报名中活动变更审核

## 入口与适用范围

管理端活动工作区统一保留「活动信息查看」「活动信息修改」「更多操作」三个入口。
审批、报名截止、时长导出、复制等操作位于「更多操作」中。
「待配置」记录同样提供查看与修改入口，修改用于补全源表资料并提交原活动申请。

独立活动处于「报名中」、原批准摘要有效时，负责人、补充负责人或全局管理员可以提交变更申请。
已有待审或应用结果待核实的申请时，先查看、处理这份申请，不能重复提交另一份。
岗位项目、普通活动班次、献血车及源表自动生成班次不通过这个入口独立改写。

已有报名记录时，日期、时段和时长规则不能改变，容量不能低于当前占位人数。
已有签到或时长记录时，停止改写活动批准版本；页面限制之外，服务端也重新检查。

## 操作过程

1. 点击「活动信息修改」，从服务器读取当前正式活动及版本摘要。
2. 修改后点击「预览变更对比」。服务端校验并返回完整差异，包括可能重新生成的报名通知。
3. 核对后点击「提交变更审核」。正式活动和报名记录保持原样。
4. 对应审核人查看变更申请和差异，选择通过或填写原因退回。审核权限每次重新检查。
5. 通过后沿用原活动 ID、保留报名记录，更新申请版本、批准版本和批准摘要。

自己提交的变更不能自行审核，现有全局管理员审核例外继续适用。
正式活动在预览、提交或审核期间发生变化时，旧版本申请不能直接覆盖新内容。
本版本不增加变更通知邮件，也不自动修改既有报名、签到和时长数据。

## 私有存储与部署

正式活动仍以 NJUTable 为权威来源。变更申请及审核进度单独保存在 SQLite 中。
文件位于服务器已有的 `PLATFORM_WRITE_STATE_DIR`；开发环境未配置时使用项目 `.write-state/`。
文件名为 `activity-changes-<Base UUID 的 SHA-256 前 16 位>.sqlite`，不同 Base 的申请隔离。

沿用已有私有目录的权限与持久化配置，不需要 Redis、Kafka、新 API Key 或 NJUTable 增列。
生产环境应使用持久化目录，不能指向公开静态目录或发布时被清空的临时目录。
源码部署、依赖安装和代码回滚均不得删除该目录。申请文件不得提交到 Git。

备份时应使用 SQLite 一致性备份，或先停止服务再完整备份私有状态目录；
不要在运行中只复制 SQLite 主文件后宣称获得一致快照。
恢复、迁移服务器时，正式活动数据库与私有申请状态均须核对。

## 应用结果待核实

申请状态包括待审核、正在应用、已通过、已退回。
审核先记录「正在应用」，再更新正式活动；变更编号、原摘要及审核人和正式活动补丁一起写入并重新签署批准摘要。

如果写入响应中断，申请保留「正在应用」，不能超时后自动解锁或盲目再次写入。
原审核人可通过「核对应用结果」检查正式活动中的变更编号、原摘要及有效批准签名；
核对成功只补记申请结果，不再次增加活动版本。
不能确认结果时交管理员核对：保留 SQLite、活动当前行及日志，不手动把状态改回待审或删除申请。

同机写入协调和版本检查不等于 NJUTable 跨客户端原子条件更新。
外部客户端直接改表、跨服务器并发写入仍需统一写入口或额外协调；本功能不宣称提供跨系统事务。

## 验证

使用合成数据运行单元、存储、服务、正式流程适配和接口测试：

```powershell
node --test "tests/activity-change*.test.mjs"
```

电脑和手机交互测试：

```powershell
npm.cmd run test:browser -- tests/browser/activity-change.spec.mjs
```

浏览器预览采用内存申请存储，重启后清空；不加载生产凭据，不连接真实 NJUTable，也不能代替生产备份恢复验证。

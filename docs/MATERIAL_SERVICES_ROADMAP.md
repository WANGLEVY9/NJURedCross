## PDF 预处理与发票检查

2026-10-12 管理端新增按项目原件核对与手动生成：原件按支出项目 ID 分组，优先预览原始发票，PDF/图片可切换，Word 下载核对。核对确认后生成项目合并 PDF，顺序为发票 → 订单及付款 → 其他材料，订单与付款另合为一个下载件。整份申请共用材料单列，Word 明确另附，历史缺少可靠关联不猜测。结果绑定材料版本，重复生成复用，失败不影响审核状态；不自动审批、付款或流转。具体接口和范围见 [按项目材料接口](REIMBURSEMENT_ITEM_PACKETS_API.md)。后续已接入本地二级审核、台账导出和人工付款登记；真实人员权限绑定与持久化待确认。

2026-10-09 发票信息提取更新：管理端自动展示购买方名称、购买方识别号、开票方名称（销售方）、发票号码、开票日期、实际金额（价税合计）六项。优先使用 PDF 文字层及坐标，保留左右购销栏和竖排标签；无法可靠提取时用本地 OCR，并局部复核竖排购销标签、识别号及金额。号码和识别号始终保留字符串，不转浮点数；实际金额只取价税合计，不取未税小计或单价。不确定、低质量或多个候选值明确提示人工核对，不替代审核，也不自动填入申请金额。

用户端材料分为“发票”和“补充材料”两处上传。2026-10-10 起，发票仅接受 PDF；补充材料支持 PDF、Word（DOC / DOCX）、JPG、JPEG、PNG，共用原有数量及字节限制。图片生成审核用 PDF 页面，Word 保留原件并提供下载，不伪造 PDF 页码。支出项目填写报销类别；每份发票须关联有效项目，补充材料可关联项目或整份申请。提交后发票自动命名为“报销人-报销类别-报销条目-发票.pdf”，补充材料为“报销人-报销类别-报销条目-补充材料-序号.原扩展名”，合并 PDF 也按申请人、类别、条目命名。保留原始文件名、原件字节、哈希及有效合并页码。管理端只识别发票，六项结果默认展开；PDF 和图片连续预览，Word 明确提示分别下载核对。活动汇总保留 Word 原件链接，PDF 合集与汇总表明确说明另附 Word，不声称已合并 Word 内容。重复发票号码提示核查，不自动累计或删除材料。旧上传与旧申请协议继续兼容，旧材料未分类时仍按原流程处理。

本次实际样本验证：当前用户提供的同一张电子发票，在原 PDF 和转为纯图片的 PDF 上均提取出六项一致值（购买方南京大学、价税合计 87.00 元），并检出疑似红章。该结果只证明本样本通过，不代表所有版式的准确率；私有原件与诊断产物不纳入源码提交。

检查目标为“抬头是否为南京大学”和“是否检测到红章”，页面优先展示这两项结果。只从购买方名称判断抬头；红章只检测外观，不识别章内文字。2026-10-10：审核预览保留原图，不再叠加红章位置蓝框，缓存和新识别结果均只展示文字结论；原件和合并件内容不变。识别不清保留“无法判断/请人工核对”，不把未检出直接认定为没有红章。

参考 PDF24 的文件排序、合并、下载思路，使用本地 `pdf-lib` 复制页面、生成图片预览页与 `pdfjs-dist` 渲染、提取文本，不嵌入 PDF24 在线服务。当前按整个文件排序，尚未提供单页旋转、裁剪、删除、压缩等工具。

保留每份原 PDF，合并件为审核用派生文件，记录每个原件对应的合并页码。合并不替代原件，不声称保留电子签名有效性。加密或不可解析 PDF、包含可填写表单的材料明确拒绝，要求申请人提供已确认内容的普通 PDF。

用户端仅选择、排序并上传原件，填写申请后直接提交；个人记录只提供原件下载，不显示合并预览、合并下载或辅助检查工具。后台上传处理负责校验文件、保留原件和生成 PDF/图片审核用合并件。管理端连续堆叠预览 PDF 与图片页面，按可见范围加载画布并限制驻留数量，无需点击下一页；原 PDF 页面尺寸保持不变，Word 仅提供原件下载。

管理端加载待审核申请后自动串行检查全部页面，在申请列表显示进度与概览，在审核窗口显示逐页字段及抬头、红章结论，不需要点击启动识别。新提交通过同源标签页消息触发刷新，重新切回管理端也会刷新；关闭管理端会停止启动后续页面，再次打开从服务端已有缓存继续。识别失败明确列出，不当作抬头不符或无章。尚未提供关闭浏览器后继续运行的后台任务队列；当前只在本地管理端会话中调度，缓存随本地服务重启清空。

对文字型 PDF，结合文字坐标、购销栏目和名称标签定位购买方，不把文中其他位置出现“南京大学”视为抬头匹配。无法定位或扫描件，自动用 `pdfjs-dist` 和 `@napi-rs/canvas` 渲染原件页面，再用 `tesseract.js` 与本地 `chi_sim` 模型提取带坐标的文字，并对可定位的字段做局部识别。只去除长直红色表格线，保留红色字段标签，印章检测使用未处理的彩色页面。模型来自已安装依赖，不在运行时请求 CDN 或外部 AI。安装依赖后可离线识别。中文模型也能识别部分基础英文，不代表完整英文材料支持。

字段来源、原始证据与 OCR 文字可查看；字段引擎评分低于 65 时标为待人工核对，评分不代表经验证的准确率。复杂版式、旋转、低清晰度及名称识别错误可能导致无法定位或错误提示。红章检查基于红色区域与圆形/椭圆轮廓，先分离长直表格线，容许少量轮廓断裂与内部文字，内部最多保留 5 处候选区域，预览不显示蓝框；不是印章文字识别或真伪鉴定。红色圆形图案可能误检，矩形章、褪色章、严重断裂或遮挡轮廓、黑白扫描可能漏检。识别不写入原件或合并件。

每页识别使用独立子进程，最长 45 秒；本地队列串行执行，最多 3 个待处理页面。结果按材料包与页码保存在私有内存，重复请求复用结果，失败允许重试。审核人只能访问已提交材料的识别结果；申请人与其他账号不能互读。低质量或识别失败时仍可下载原件人工核对，提交与审核流程不依赖识别成功。

所有识别仅为提示，不自动通过或拒绝申请。审核页不再单列购买方名称、印章人工核对选择；审核通过前只要求确认已逐份核对原材料与申请金额，审核意见可选，退回补充须填写原因。购买方名称与疑似红章的自动检查继续展示，供人工参考，不作为审核通过的强制条件。审核通过不等于付款完成。

下一步需用脱敏的真实发票验证版式与识别效果，再决定是否增加版面定位、旋转矫正或其他识别方案。是否接入外部 AI、材料传输范围与凭据配置须在方案确定后实现。红色像素只能作为候选区域，不能直接证明存在有效印章。电子票据是否需要红章应由审核人员按实际要求核实，程序不统一强制“无红章即无效”。

### 共用台账与操作区分

统一台账指共用库存计算和出入库流水，不意味着合并或改动远端四张物理表。现有入库入口已扩展为轻量的“出入库登记”，保留入库/出库选择，并按业务原因展示必要字段：

| 方向与原因 | 库存变化 | 必须记录或核对 |
| --- | --- | --- |
| 入库：采购、捐赠或调拨 | 增加确认入库件数 | 类别码、数量、来源、单据或说明、操作人、时间 |
| 出库：借用备货 | 减少本次实际取出件数 | 类别码、数量、关联借用申请、领取人或去向、值班操作人、时间 |
| 入库：借用归还 | 增加实际收回件数 | 原借用申请及原出库物资、归还件数、损耗件数、操作人、时间 |
| 出库：独立领用或消耗 | 减少确认出库件数 | 类别码、数量、去向、操作人、时间；沿用现有非借用流程 |

归还即使从“入库”入口进入，也须调用关联原借用申请的归还逻辑，不能当作普通采购入库。只增加实际收回数量，损耗只结算借用责任、不增加库存；拒绝超出待归还数量的操作。采购补货也不能抵消他人的未归还记录。

值班人员取出并确认出库时扣减一次库存，志愿者之后领取不得再次扣减。流水记录实际操作的管理人员，借用申请保留借用归属；二者不能混为一个身份。未领取而收回的备货需要关联原出库，避免用普通采购入库掩盖未结清借用。额外的领取确认步骤尚未确定，不据截图自动增加。

页面保持简洁：选择方向与类型 → 借用业务选择原记录 → 自动带出或扫码核对物资 → 填写数量 → 显示操作前后库存 → 确认登记 → 返回回执。登记后沿用同一库存与流水视图，支持按方向、原因、物资、操作人和日期筛选。对重复提交保留幂等保护，未知码先提示登记，不直接入库。

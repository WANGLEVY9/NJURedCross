# 物资服务四项功能与本地第一版

需求日期：2026-10-07。只在本地开发；物资 API 已恢复，真实库仅允许读取，开发写操作只在本地模拟。暂不接邮箱通知和场地业务。

## 本地入口与当前范围

2026-10-08 负责人确认：用户端四项顺序为物资借用 → 物资归还 → 财务报销 → 场地借用；采购和捐赠入库移至管理端。管理导航前四项对应同序，“出入库登记”保留为管理工具。

- 物资借用：保留申请、出库与归还，马甲提交后自动通过，其他物资继续人工审批；自动通过不等于已出库，实际出库才扣库存。
- 物资归还：用户端 `/materials/return`，管理端 `/console/materials/returns`。选择自己的已出库原借用单、实际件数与照片，管理员核对通过后记入同一台账；支持分次归还、重复提交防护、状态同步恢复。历史借用单的账号关联待可靠权限适配，不能靠同名或学号文字自动认领。
- 财务报销：用户端 `/reimbursements`，管理端 `/console/reimbursements`。本地上传、PDF 合并、下载原件与合并件、材料预览、文本检查提示、扫描件逐页 OCR、疑似红章标框、提交、退回补充与重新提交、人工审核、记录留痕；新增 `/console/reimbursements/summary` 活动报销汇总。
- 场地借用：用户端 `/materials/rooms` 与管理端 `/console/materials/rooms` 均可进入建设中占位页，不实现表单或审批逻辑；管理页沿用物资管理权限检查。

2026-10-09 管理首页调整：待审批、待出库、借出中、逾期未还按此顺序显示为四个紧凑的操作入口，点击筛选对应申请；待出库计数与实际可执行出库动作的申请一致。低库存入口筛选具体物资。库存品类、台账库存放在简洁的数据栏。移除首页的本地环境蓝色提示和顶部“全部借用申请”按钮，服务本身仍保持远端只读、本地内存模拟。任务队列每组预览至多三单，提供查看全部入口；申请列表与库存列表增加状态筛选，数据刷新保留当前筛选，可通过列表状态筛选恢复全部申请。
- 出入库登记：沿用 `/console/materials/intake`，先选入库/出库与业务原因，扫码枪键盘输入或手工输入现有类别资产码，回车定位，核对库存、数量和必要关联，再确认登记。普通补货、借用备货、借用归还和领用/消耗接入同一台账。扫描本身不修改库存。扫码枪须能读取系统现有标签；一维/二维能力、标签尺寸和编码规范待硬件与管理方案确定后核验。

运行 `npm run preview:materials`，访问 `http://127.0.0.1:3122/console/materials/intake` 或 `/reimbursements`。启动时只读加载真实物资 API 的完整快照；后续登记只操作克隆后的本机内存，远端适配器不传入可写业务服务。缺表、分页重复、容量超限或读取失败则停止启动，不回退到演示数据。每张表上限 10000 行，完整分页校验后才建立副本。`npm run preview:materials:synthetic` 为显式离线合成模式。副本不实时刷新远端，重启才重新载入并清空本地改动。

本地模拟会话同时演示申请人和管理员，不代表真实权限配置。全部新报销接口均在 `/api/preview/reimbursements` 下；报销未接入生产 `server.js`、SeaTable 或 SMTP。附件只保存在私有内存，不写入 public 或 Git；重启服务清空。每次最多 10 个 PDF、单个 30 MB、总计 100 MB、100 页，本轮材料总占用上限 500 MB。

## PDF 预处理与发票检查

检查目标为“抬头是否为南京大学”和“是否检测到红章”，页面优先展示这两项结果。只从购买方名称判断抬头；红章只检测外观，不识别章内文字。位置蓝框为辅助信息。识别不清保留“无法判断/请人工核对”，不把未检出直接认定为没有红章。

参考 PDF24 的文件排序、合并、下载思路，使用本地 `pdf-lib` 复制页面与 `pdfjs-dist` 渲染、提取文本，不嵌入 PDF24 在线服务。当前按整个文件排序，尚未提供单页旋转、裁剪、删除、压缩、图片转 PDF 等工具。

保留每份原 PDF，合并件为审核用派生文件，记录每个原件对应的合并页码。合并不替代原件，不声称保留电子签名有效性。加密或不可解析 PDF、包含可填写表单的材料明确拒绝，要求申请人提供已确认内容的普通 PDF。

用户端仅选择、排序并上传原始 PDF，填写申请后直接提交；个人记录只提供原件下载，不显示合并预览、合并下载或辅助检查工具。后台上传处理仍负责校验 PDF、保留原件和生成审核用合并件。管理端连续堆叠预览所有页面，按可见范围加载画布并限制驻留数量，无需点击下一页；下载文件仍为保留原始页面尺寸的多页合并 PDF。

管理端加载待审核申请后自动串行检查全部页面，在申请列表显示进度与概览，在审核窗口显示逐页结果和红章候选框，不需要点击启动识别。新提交通过同源标签页消息触发刷新，重新切回管理端也会刷新；关闭管理端会停止启动后续页面，再次打开从服务端已有缓存继续。识别失败明确列出，不当作抬头不符或无章。尚未提供关闭浏览器后继续运行的后台任务队列；当前只在本地管理端会话中调度，缓存随本地服务重启清空。

对文字型 PDF，从显式“购买方/购方 → 名称”字段提取名称。文中其他位置出现“南京大学”不视为抬头匹配。无法定位或扫描件，自动用 `pdfjs-dist` 和 `@napi-rs/canvas` 渲染原件页面，再用 `tesseract.js` 与本地 `chi_sim` 模型提取文字。模型来自已安装依赖，不在运行时请求 CDN 或外部 AI。安装依赖后可离线识别。中文模型也能识别部分基础英文，不代表完整英文材料支持。

购买方提示与 OCR 文字可查看；引擎评分低于 65 时标为待人工核对，评分不代表经验证的准确率。复杂版式、旋转、低清晰度及名称识别错误可能导致无法定位或错误提示。红章检查基于红色连通区域与近圆形轮廓，最多标记 5 处候选蓝框；不是印章文字识别或真伪鉴定。红色圆形图案可能误检，矩形章、褪色章、断裂或遮挡轮廓、黑白扫描可能漏检。蓝框只叠加在预览页面上，不写入原件或合并件。

每页识别使用独立子进程，最长 45 秒；本地队列串行执行，最多 3 个待处理页面。结果按材料包与页码保存在私有内存，重复请求复用结果，失败允许重试。审核人只能访问已提交材料的识别结果；申请人与其他账号不能互读。低质量或识别失败时仍可下载原件人工核对，提交与审核流程不依赖识别成功。

所有识别仅为提示，不自动通过或拒绝申请，也不预填人工核对项。最终审核要求人工确认原材料、购买方名称与印章核对结果；例外情况必须写明依据。审核通过不等于付款完成。

下一步需用脱敏的真实发票验证版式与识别效果，再决定是否增加版面定位、旋转矫正或其他识别方案。是否接入外部 AI、材料传输范围与凭据配置须在方案确定后实现。红色像素只能作为候选区域，不能直接证明存在有效印章。电子票据是否需要红章应由审核人员按实际要求核实，程序不统一强制“无红章即无效”。

## 扫码出入库：负责人已确认的业务方向

2026-10-07 用户提供的负责人讨论截图明确了以下事项，替代此前“追踪粒度暂未确定”的状态：

- 值班管理人员晚上提前取出物资并登记出库，志愿者随后到空教室自行领取。
- 采购入库、借用出库、归还使用同一套库存台账；负责人认可统一入口，同时希望避免操作混淆。
- 同一类相同物资使用同一个码，按数量管理，不为每件零碎物品分别编码。单件追踪不作为本轮实施目标。
- 出入库页面可先选择入库或出库，再扫码定位物资、填写数量并确认。

类别码定位一条物资种类记录，扫描本身不改变库存。同类现存 10 件时，出库 3 件只减少 3 件、剩余 7 件，不能把整个种类标记为全部借出。商品条码和类别码的映射、打印格式以及扫码枪的一维/二维能力仍需核验，不假定购买扫码枪后即可识别现有标签。

### 共用台账与操作区分

统一台账指共用库存计算和出入库流水，不意味着合并或改动远端四张物理表。现有入库入口已扩展为轻量的“出入库登记”，保留入库/出库选择，并按业务原因展示必要字段：

| 方向与原因 | 库存变化 | 必须记录或核对 |
| --- | --- | --- |
| 入库：采购、捐赠或调拨 | 增加确认入库件数 | 类别码、数量、来源、单据或说明、操作人、时间 |
| 出库：借用备货 | 减少本次实际取出件数 | 类别码、数量、关联借用申请、领取人或去向、值班操作人、时间 |
| 入库：借用归还 | 增加实际收回件数 | 原借用申请及原出库物资、归还件数、损耗件数、操作人、时间 |
| 出库：独立领用或消耗 | 减少确认出库件数 | 类别码、数量、去向、操作人、时间；沿用现有非借用流程 |

归还即使从“入库”入口进入，也须调用关联原借用申请的归还逻辑，不能当作普通采购入库。只增加实际收回数量，损耗只结算借用责任、不增加库存；拒绝超出待归还数量的操作。采购补货也不能抵消他人的未归还记录。

值班人员取出并确认出库时扣减一次库存，志愿者之后领取不得再次扣减。流水记录实际操作的管理人员，借用申请保留借用归属；二者不能混为一个身份。未领取而收回的备货需要关联原出库，避免用普通采购入库掩盖未结清借用。额外的领取确认步骤尚未确定，不据截图自动增加。

页面保持简洁：选择方向 → 扫码定位 → 填写数量与必要关联 → 显示操作前后库存 → 确认登记 → 返回回执。登记后沿用同一库存与流水视图，支持按方向、原因、物资、操作人和日期筛选。对重复提交保留幂等保护，未知码先提示登记，不直接入库。

## 真实 API 的接入与后续生产事项

管理端活动报销汇总已补齐：维护活动资料、选择同一活动的已审核且未纳入申请、支出明细预览、相同项目与备注合并、金额大写、活动费报销表及完整 PDF 材料包下载。汇总保留活动与申请版本快照，成功后占用所选版本，支持后续补充批次和已有记录重新下载。缺少活动关联或明细的旧申请不自动归类。

用户端的活动关联与逐项支出明细由另一位同学负责，本轮不改其页面；提交服务已兼容新增字段与旧协议。对接字段、版本规则、示例及模板边界见 [活动报销汇总接口](REIMBURSEMENT_SUMMARY_API.md)。离线完整闭环使用显式命令 `npm run preview:reimbursement-summary`（3135，全部合成数据）。审核通过和生成汇总都不代表已付款；正式原模板、持久化、权限与通知仍待后续接入。

当前先完成真实物资数据的只读分页、字段与编码映射核验，写入能力继续隔离在本地。以下为未来生产方案评估，开发阶段不执行建表、结构修改或写入：报销申请与材料版本存储适配器、账号归属、独立财务审核权限及审核人、永久附件存储、审核并发控制、原件哈希、附件访问鉴权和容量策略。邮箱通知以后统一接入申请提交、审核完成和退回节点。

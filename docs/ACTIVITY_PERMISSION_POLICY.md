# 活动工作区权限与操作

## 立项、协作与审批人员（2026-10-23）

活动草稿基本信息区分三类人员：立项负责人固定为草稿创建账号，协作负责人可多选，审批人可多选。协作候选沿用当前地区、中心内有效负责人的权限范围；立项人与协作人共同写入正式活动负责人列表。复制成新活动时，复制者成为新草稿的立项负责人。

审批人默认勾选对应地区、中心的有效主席，以及名单中唯一匹配“金中宸”“袁金雨”的有效终审账号。姓名只用于默认勾选，不授予任何角色；未配置、同名或角色失效时明确提示，不猜测账号。可以调整审批人，保存与提交均重新核对稳定账号 ID 和当前角色证据，提交后绑定所选名单。保持任意一位通过即生效；未被选中的总权限账号也不能代替本次审批人审核。发布、报名处理和时长审核仍沿用各自的权限检查。

默认值只在人员字段尚未配置时填入；重新打开已保存的申请不会覆盖手选结果。切换地区或中心后重新加载候选、重置协作选择及审批默认值。旧数据保持可读，不批量迁移已有申请；编辑草稿采用新人员字段后，不能移除或改写立项负责人。新增活动配置与草稿 JSON 字段，不增加 NJUTable 表或生产迁移。

人员候选通过 `GET /api/volunteer/workflow/workspace-drafts/project-people-options?region=...&category=...` 一次返回，读取同一份当前可信名单，不读取个人档案。草稿详情、保存、预览、复制与交接核对按主键读取；创建和复制重试按 `owner_id + request_id` 唯一索引查找。草稿目录仍沿用列表查询，此优化不代表所有现有查询都已改造。账号快照策略见运维指南，写操作继续重新核验角色。

## 本轮问题与修正

旧活动的组织权限与新工作区的地区 JSON 名单分别判定，导致平台超级管理员能进入活动管理，却无法加载负责人或提交新版活动。地区主席团的旧规则也没有细分南京分管中心，且仅一次审批。

现在，外层活动 API、草稿权限、负责人选择、终审、发布和时长操作使用同一份服务端地区角色证据。平台总权限来自实时账号表的 `super_admin` 身份，不从姓名、页面传参或 Excel 单元格推断。名单文件缺失时，已验证且启用的超管仍可选择自己为负责人，保存、预览和代提交；普通账号不会因此获得权限。

## 活动角色

| 角色 | 范围 |
| --- | --- |
| R01 | 南京综事中心活动发起与管理 |
| R02 | 南京博爱中心活动发起与管理 |
| R03 | 南京生命中心活动发起与管理 |
| R04 | 苏州活动发起与管理 |
| R05 | 南京二级终审，必须明确勾选分管类别 |
| R06 | 苏州二级终审 |
| R11 | 已有平台总权限账号的活动全范围操作，两地均可处理 |

执行主席、指导组组长按实际身份配置 R05 全部类别及 R06；已有平台总权限身份也可跨范围处理。专项的一级审批归属没有擅自推断，需在对应南京一级审核账号上明确勾选专项范围。只有实际配置的一级审核人和超管可作为新活动负责人，负责人支持多选。

选中的每位负责人均可在有效地区与类别范围内共同编辑草稿、处理报名、签到和时长录入。任一成员停用、角色或范围被撤销后，该成员不再获得管理权限，不影响其他仍有效的成员。多人信息会保留到正式活动及各岗位，不因复制或编辑退化成单人。为了兼容旧业务字段，底层保留首个账号并把其余账号存入共同负责人配置，界面不区分主次。

最终时长附件发给全部负责人，并冻结各自收件地址及独立去重键。失败重试只处理未成功的收件人；成员或邮箱改变后须核对原任务，不会把已归档附件改发到新地址。

R07–R10、R12–R14 属于财务、运维或宣传，不会被当作活动审批权限。该入口不改变账号的基础平台身份；新增 R11 必须先在既有账号管理中核验总权限身份，不能借活动角色配置升级普通账号。

## 配置入口与存储

启用且邮箱已验证的超管，在「活动管理 → 管理工具 → 活动权限与负责人配置」选择平台账号 ID、角色及分管类别。姓名仅为显示信息。普通管理员不显示配置按钮，直接调用接口也会被拒绝。

配置保存在服务器私有的 `.write-state/activity-workspace-roster.json`，也兼容已设置的 `PLATFORM_ACTIVITY_WORKSPACE_ROSTER_FILE` 路径。文件不纳入源码、发布包或公开测试。界面保存采用版本检查、串行写入和原子替换；发生网络异常时禁用继续保存，需重开核对。

旧地区名单保持读取兼容。新角色配置保留旧名单中其他账号的绑定；为某账号配置新角色后，用明确的新范围替代该账号的旧范围。已进入旧单级审批的申请保持原流程，新配置下的新申请走两级审批，避免静默重写历史审批记录。

## 新申请流程

1. 创建草稿，设置地区、类别、负责人及活动/岗位信息。校内、校外均自由填写地点，不要求校区下拉框。
2. 保存后点击「预览并提交」，以阅读版式查看保存的版本；编辑时不实时展示预览。
3. 预览底部点击「提交审核」。服务器仍校验版本、预览摘要、字段完整性和实时负责人资格。
4. 主任团提交即完成发起环节，不再增加主任团初审。提交后直接等待对应地区、类别的分管主席终审；旧两级待审批记录使用原终审名单继续处理。
5. 终审通过后选择立即或定时发布。普通审核人不能审批自己负责或编辑的申请，平台总权限可代处理。每次写入均重新核验账号与地区类别范围。

以上终审针对活动发布申请。活动发布后的志愿者报名，由活动负责人处理录取/未录取并直接进入结果通知队列，不需要主席再次终审或批准发信。邮件是否实际发出，以已启用的邮件服务和发送状态为准。

报名通知不再自动包含志愿时长，时长配置、核对与导出仍保留。旧版自动生成通知在继续编辑/保存时更新格式；人工编写的通知不会被自动重写。

## 验证重点

- 未配置地区文件时的真实超管证据，与伪造 `role` 传参区分。
- 跨地区、跨中心、未终审先发布、角色撤销、版本冲突与重复操作拒绝。
- 旧审批兼容、已有报名和时长记录不被改写。
- 校外多岗位从保存、阅读预览到提交的闭环；通知隐藏时长，实际数值保留。

源码中只有合成账号和规则，没有权限矩阵中的真实姓名、邮箱或学号。真实人员需在配置页面按账号 ID 核对绑定。

## 进行中阶段的信息修改与时长初审（2026-11-02）

「进行中」页面的「活动信息修改」由 `canEditWorkspace()` 裁决，保存时再由 `planWorkspaceLiveEdit()` 复核同一组条件：状态为报名中或进行中、活动尚未开始、没有时长台账、时长初审未提交、最终表未导出、当前账号具备该项目发布权限。

签到不再是编辑的硬性前提。活动开始前已有志愿者签到时，负责人与管理员仍可修正活动说明、地点、人数与岗位安排；签到行按报名行 ID 关联，编辑不改写签到证据。时长台账仍是硬门槛——一旦有时长入账，改写活动安排会与已核定时长脱节，继续拒绝。活动开始后依旧不能改写时间安排。

时长初审（负责人初审、上传及预览时长表）打开时，按「岗位自身配置 → 活动行时长字段 → 活动级默认」自动带出服务、培训、交通三项；进行中列表的时长列在尚未初审时展示这组预设值并标注来源，避免逐人手填或留下 0/0/0 的空表。上传名单后以表内数值为准，带出的值可逐项修改。审核页的三项时长仍以初审提交值为准。

时长初审的授权口径（2026-11-03 复核）：仅当前可信名单中的本项目负责人（含共同负责人）及超级管理员可操作；仅有地区主席团终审资格、但未负责本项目的账号不能代做初审。项目内任一实际负责场次通过授权即可进行项目初审，读取、保存、导入、预览、提交及响应丢失后的重试均采用同一判定；写入时重新读取权限，撤销后立即失效。

授权按**项目**判定，不再逐场次取交集：项目内任一目标场次通过即可（`running-review.js` 的 `context()`）。献血周这类 16 场次项目常由多人分担，逐场次取交集会让没有任何一个账号能提交整份初审——界面表现就是「待初审」的下拉与「上传时长表」全部灰掉，且没有任何提示。

初审控件禁用时必须说明原因：`GET /running-review` 现在返回 `canRecordReason`，工作区在筛选栏上方以提示条显示；此前页面把 `loadReview` 的失败静默吞掉，权限不足、项目状态不一致、审批绑定缺失三种情况在界面上完全一样。

初审明细的存放位置（2026-11-03 调整）：逐人明细写进「网站服务时长明细表」的独立行，幂等键前缀 `RUNNING:`，与旧时长流程的行互不干扰；活动的「报名页配置」只保留 `status / entryCount / submittedAt / sourceDigest / previewToken` 等流程状态。此前明细整包写进该文本字段，而它有 10000 字符上限：一条初审记录约 231 字符，四十余条就会撞顶，NJUTable 静默截断后整行配置永久不可读，16 场次、三百余条参与记录的献血周因此完全无法初审。改为一人一行后不再受单字段容量限制；判定类信息（通过／不通过、证据是否核验、签到链接、终审结论与备注、补录标记）压缩成带版本号的 JSON 写进行的「备注」，时长本身走数值列。
终审同样落台账（`FINAL:` 前缀，与初审行分开）：一个报名行对应一条终审行，导出时转为「已批准」，下载与发信都按行现场重建工作簿，活动配置只保留 `status / token / filename / mail` 等流程状态。此前整份 `rows` 写在配置里，一条约 324 字符，三十余行就会撞顶，献血周三百余人时初审刚通过就会在终审环节失败（并伴随「最终时长表最多200条明细」）。上传及预览时长表与终审编辑的单批上限同步放宽到数百条，`running-review` 与 `final-hours` 的请求体上限提到 1 MiB 以容纳整份名单。

**终审按学号合并（2026-11-03）**：同一学号在同一项目里报了多个场次时，时长审核页与导出表合并成一行——三项时长相加，工作地点／日期／工作内容去重后换行拼接，结论从严（任一不通过即不通过），`memberIds` 记录被合并的报名行。同一场次的重复报名只计一次，落库时其余重复行清零，保证入账按行累加不会重复计时。合并只发生在展示、导出与归档下载：台账仍是每个报名行一条，证据与来源摘要不动；编辑合并行时只有改动过的字段写回成员行，未改动场次保留原始明细。`FINAL:` 行不再与人数一一对应，`entryCount` 记的是合并后的人数。

`RUNNING:` / `FINAL:` 行与旧流程隔离的守卫：旧台账导出（`exportHours`）不包含它们；旧审批（`approveEntry`）、复核修改（`editReview`）、退回（`returnHours`）对它们直接拒绝并提示到活动工作区处理；参与者「我的时长」不展示它们；请假策略的「已有台账证据」不把它们算作正式证据。历史项目若配置内还留着 `entries` 或 `rows`，读取时按「台账优先、配置回退」兼容，下一次保存即迁移到台账行。

## 审批自审与绑定校验（2026-11-02）

审批人资格由 `workspace-approval-routing.js` 的 `assertReviewer()` 裁决，返回的 `canSelfReview` 决定「负责人能否审批自己经手的申请」。此前该值写作 `row.role==='global' || !approval.levels`，而 `approval.levels` 在生产代码里没有任何写入点，`!undefined` 恒为真，等于对所有人放开自审——一个既是项目负责人、又是本地区该类别终审人的账号可以自己提交、自己批准、自己发布。

现行口径：**主席团成员（`presidium`）和全局角色（超管）可以自审**。主席团成员即使同时被列为活动负责人，也可以审批自己的申请；普通主任（`director`）仍须由另一名有资格的审核人批准。

自审资格同时依据活动负责人身份（`eventResponsibleIds`）和当前可信名单中的角色。地区审批下，审核人为修正说明而保存过活动内容，仍可正常审批；legacy 侧的旧口径「编辑者不能自批」保持不变。

审批绑定校验拆成三档可定位的错误，避免界面只显示一句「审批绑定已失效」：`workspace_approval_binding_missing`（缺 mode）、`workspace_approval_binding_mismatch`（地区或类别不一致）、`workspace_approval_binding_stale`（版本过期，刷新重提即可）。

阶段名单 `approval.levels` 仅用于选择本次申请的审核人，不改变审批阶段数：现有口径仍是单级终审，`twoStage` 恒为 false。`workflow.js` 的两阶段分支保留，但终审名单缺失时会显式返回 409，不再因 `undefined.ids` 在审批中抛异常。

「活动信息修改」按钮禁用时通过 `approvalAccess.canEditReason` 显示具体原因（不是工作区活动 / 活动已开始 / 初审判已提交 / 已有时长记录 / 无发布权限等），不再是一个无提示的灰按钮。

## 活动结束与来源排班

管理端「更多操作」按当前账号的地区、类别和负责人权限显示删除或结束入口，不以是否由新版草稿创建作为前提。未发布且无参与记录的活动可删除；已有参与记录时保留记录并提前结束。涉及待审批或已提交时长审核的活动仍由对应二级审核人处理。

来源排班项目的管理端结束决定保存在私有 `activity-lifecycle-<base摘要>.sqlite`，独立于自动重新生成的场次。底表同步、应用重启不会重开已结束项目；不清除底表报名人，也不删除平台报名、签到或时长。该文件需要随其他 `.write-state` 数据备份。现有献血车按月份组织项目，结束确认适用于整个月份；同月后来同步的新场次也保持关闭，下月项目不受影响。其他排班专项继续以各自的项目标识划分，不依赖活动名称。结束是主动关闭项目，不改变尚未结束的排班专项可并行审核报名、通知、签到及分批处理时长的规则。

## 管理员只读查看

所有可进入管理端的账号均显示活动管理导航。`platform_admin`、`super_admin` 以及经最新组织/活动权限证据允许进入管理端的账号可浏览全部正式活动目录及活动基本信息，不以是否具有该地区/类别的管理权限作为可见性条件；私人草稿仍遵守原有归属权限。无管理权限的活动以只读形式显示，修改、更多操作等按钮禁用。只读活动信息接口只返回活动安排、地点、工作内容、人数、时长配置与通知等白名单字段，不返回报名名单、签到凭据、时长明细、审核人账号或写操作 token。原有管理 API 和所有写入继续独立校验最新地区、类别、负责人权限。

## 独立的新建权限

新建活动由单独的 `canCreate` 与 `creationScopes` 能力决定，不取决于当前是否有可管理的活动或目录中是否存在卡片。弹窗仅列出可信权限证据允许的地区和类别；提交仍由后端重新校验。尚未迁入新角色配置的中心主任，继续使用经过账号、姓名、学号和组织成员表精确核验的原中心权限；明确配置过的账号使用新规则。删除角色绑定后保留 `managedAccountIds`，防止已撤销权限通过旧组织身份自动恢复。

角色配置旁的 `.configured` 标记需要一起备份；曾保存过新角色配置后若主配置文件缺失，将提示恢复，不会按未配置状态重新授权。

## 超管主动提前结束

平台总权限可主动结束尚未结束的活动，无需先完成报名处理、签到或时长审核。操作保留所有参与记录及已有导出附件。旧活动地区/类别等字段不完整时，结束操作先核验最新可信的全局身份，不因旧审批信息缺失而拒绝超管；普通管理人员仍按当前地区和类别范围核验。处于进行中但遗留最终导出标记的活动也可提前结束，不会改写冻结附件。读取结束权限只查询当前项目的报名、签到与时长证据；菜单明确显示加载及拒绝原因。已结束或已移除的活动不重复执行；响应丢失使用原请求核对。

结束权限按请求读取一份最新可信名单，再用同一快照校验该项目的全部场次，避免场次数量增长导致重复远程读取。快照不跨请求缓存；确认结束的写请求仍重新读取名单、活动和参与证据，权限撤销与版本冲突继续生效。

终审通过后，向当前启用、邮箱已验证的所有活动负责人发送审批通过通知和报名通知正文。发布方式尚未选择时明确标为待选择；设置立即或定时发布后发送确定的方式、北京时间和完整通知，使用持久通知队列按审批版本、负责人和发布设置去重。仅新审批提交写入邮件标记，不向历史活动批量补发。


初审与终审表格支持勾选记录、全选当前显示名单及批量审核。切换岗位、筛选或版本更新会清理不再显示的选择；不通过须填写原因。批量初审保留每人的现有/岗位预设时长，保存后仍须完整预览并提交主席团；批量终审仅改结论与原因，导出继续受主席团/超管的终审权限、实际工作明细、版本及归档锁定约束。线上签到凭证为选填，纸质签到由负责人确认，审核不会伪造线上签到。


旧配置迁移到台账时，初审与终审的部分保存、最终表人员补录均保留其余历史明细；部分迁移的初审行按报名行 ID 合并读取，台账优先。初审版本 token 绑定实际明细内容及修订信息，时间戳相同的并发修改也会被拒绝；提交重试按报名行 ID 排序比较，不依赖底表返回顺序。

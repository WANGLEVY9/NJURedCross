## 已核验与配置位置

用户提供的 NJUTable Token 已完成只读鉴权及表结构核验，对应库中已有“财务审核表”和“报销记录表”。没有读取真实账号记录或财务记录，也没有修改原有业务 Token。

本机专用凭据在被 Git 忽略的 `.env.reimbursements-local`。该文件仅是配置，不会自行启用生产存储。后续服务器由运维在私有环境配置同名变量，不上传此文件。

专用初始化脚本 `node --env-file=.env.reimbursements-local scripts/bootstrap-reimbursement-box.mjs` 默认只读；加 `--apply` 时仅能创建 `/报销材料`。脚本要求预期资料库 UUID、先检查同名目录，遇到同名文件或异常目录响应停止。目录已存在时跳过创建；创建响应丢失时只回读确认，不盲目重复创建出“报销材料 (1)”。它不上传文件、不调整其他目录，也不使用全库目录初始化脚本。

## 已实施的财务表结构

已有财务字段继续复用。用户已授权新增稳定 ID、材料版本、操作重试与历史恢复所需结构；下列 2 张表及 9 列已实施并回读验证。没有修改已有列类型、单选选项或业务记录。

1. “财务审核表”补充：`平台申请ID`（text）、`平台版本`（number）、`平台状态`（text）、`平台投影摘要`（text）、`原件引用`（long-text）、`合并件引用`（long-text）。原有姓名、学号、邮箱、银行卡号、金额及审核时间/审核人等字段复用。
2. “报销记录表”补充：`平台汇总ID`（text）、`平台投影摘要`（text）、`材料引用`（long-text）。活动汇总映射到该表；生成汇总不设置“款项到位”，不冒充已经付款。
3. 新增“平台报销事务表”：`事务ID`（text）、`序号`（number）、`前序摘要`（text）、`摘要`（text）、`内容`（long-text）、`写入时间`（date）。保存申请、材料版本、两级审核、操作凭证、活动资料、汇总草稿/终审占用关系及邮件通知任务的元数据变更。
4. 新增“平台报销数据块”：`块ID`（text）、`摘要`（text）、`内容`（long-text）、`写入时间`（date）。将较大的元数据拆为最多 48000 个 ASCII 字符的小块；其中是元数据，不保存 PDF/图片/Word 文件二进制。

可用 `scripts/preview-reimbursement-storage.mjs` 检查缺表、缺列和类型差异。脚本只调用鉴权与 `getMetadata`，没有行查询、Box 请求、建表或写入入口；通过 Node 的 `--env-file=.env.reimbursements-local` 显式加载本机专用配置。完整字段定义见 `lib/reimbursements/table-schema.js`。

新增脚本 `scripts/apply-reimbursement-schema.mjs` 默认只读预览；显式加 `--apply --confirm=ADD-REIMBURSEMENT-SCHEMA` 才新增缺表缺列。它核对目标库、字段冲突和重复名称，变更前保存结构备份，逐步回读核对；未知结果不盲目重试，不修改已有业务行。当前真实库已完成初始化，重复预览应返回空计划。

## 保存、恢复与失败处理

正式接口启用后，Box 将原件、申请合并 PDF、按项目材料、活动报销表和活动材料包保存于 `/报销材料/对象/<哈希前两位>/<SHA-256>.bin`，按内容哈希寻址。下载名称继续沿用已有统一命名；Box 文件路径不作为浏览器公开下载地址。下载由站内接口检查归属或财务权限，设置 `no-store`，读取后核对字节数和 SHA-256。列表不下载历史文件。本轮没有迁移本地内存中的测试记录或上传用户此前提供的参考文件。

2026-10-24 完整接线检查：`server.js` 的正式服务将专用 Box 适配器交给 Table 服务与材料编码器；同一条存储链覆盖原件、申请合并件、项目材料、活动表及完整 PDF。邮件后台也通过该服务读取已保存的本版 PDF，不从临时浏览器链接或其他模块下载附件。所有带凭据的 Box 请求和上传链接均限制为配置的 HTTPS 同源地址并禁止自动重定向；异常目录响应停止上传，不能误判为空目录后创建副本。

财务表“原件引用”中的文件显示名与站内统一下载名保持一致，上传原名继续保留在材料元数据中供核对；不重写文件字节或改变哈希地址。隔离闭环会逐项核对报销行的姓名/金额/条目、材料引用与实际对象，并用 Excel 读取库重新打开总表及明细导出，核对表头和逐项金额。

Table 集成及桌面/手机浏览器测试现在使用真正的 `createReimbursementBox`，只将外部 Seafile HTTP 传输替换为隔离服务。覆盖多种材料原字节、下载命名、实例重建、两级审核、通知附件、活动排序、草稿/通过分离、打款登记、退回重提及上传应答丢失。真实 Box 本轮只读核对资料库、指定目录和上传链接协议，没有上传测试文件；不能把合成闭环表述为已完成真实财务库或真实邮箱的上线验收。

NJUTable 没有被当作支持跨表事务的数据库。文件上传确认后，先写元数据分块，最后追加一条包含分块摘要的事务记录作为提交标记；没有提交标记的分块和 Box 对象不属于已提交业务，不自动删除这些远端对象。恢复时检查连续版本、前序摘要和分块完整性，重放所有业务 Map；分叉、损坏或分页不完整时停止处理。冷启动或重建实例时按序恢复平台事务历史，每批最多 100 条事务、256 个被引用数据块；单次补读超过 50000 条事务时停止，不静默截断。常驻实例保留校验后的状态，后续仅检查最新两条事务并补读新增部分，不重复下载旧历史或未引用的数据块。

现有服务器跨进程业务写锁保护写请求，报销实例另有进程内队列和版本检查。这里依赖**同一服务器共享私有运行目录**的部署；多主机写入需另定协调机制。私有目录仅保存 `reimbursement-write-fence.json` 这一未确认写入的恢复标记，不用 SQLite 保存报销主数据，也不在本机持久保存附件。标记只有操作 ID、版本/摘要或投影表名，不包含银行卡、申请内容或 Token；恢复和备份运行状态时应保留它。

远端追加结果不明时，用同一个事务/平台 ID 核对；无法确认则保留标记并停止后续写入，不能在重启后盲目重建。事务已接受但财务表展示尚未同步时，业务历史保留；随后只有核对到原 ID 的投影才恢复写入。真实失败、持续不可见或重复 ID 需管理员先核对，不能擅自清除标记。

“财务审核表”和“报销记录表”是方便财务查看的投影，事务记录是本版流程恢复的依据。只处理有平台 ID 的行，不自动导入或覆盖历史财务记录。投影检测到人工改动或重复 ID 时停止覆盖；直接改表不等于完成平台审核。已有单选流程、协作人和 NJUTable file 列保持原样；Box 引用不伪装成 Table 原生 file 值，当前通过新增引用字段及平台状态展示。后续如需双向编辑或映射既有单选选项，另行确认。

## 接口、权限与上线条件

正式前缀 `/api/reimbursements`；本地预览继续 `/api/preview/reimbursements`，不迁移测试记录。管理员可用只读 `/api/reimbursements/readiness` 查看配置和表结构状态；不会返回 Token。前端只有会话公布正式存储能力时才打开新入口。

新申请绑定登录账号真实姓名、学号和已验证邮箱，用户表单和审核详情不再填写或展示银行卡号；历史字段仅作兼容。普通用户只能访问自己的记录；审核不继承物资模块权限。按活动举办校区分配固定初审（苏州李婉荣，其余邹孟窈）及终审（顾语涵）；服务器按这些姓名唯一匹配其现有有效账号，缺失/重名不自动授权，不接受表单姓名越权，人员轮换设置页不做。超级管理员具备初审、终审、查看和打款登记全部财务能力；Owner 本轮批准的指定管理员仅增加物资与全部财务能力，不提升为全站超级管理员。普通物资管理员不会因此取得财务审核权。新申请使用逐份初审、活动终审流程，见 [审核流程](REIMBURSEMENT_WORKFLOW_API.md)。审批、生成及人工打款登记不执行银行转账。报销通知任务已接入既有发信通道；正式开关默认关闭，合并代码不调整生产配置。

上传保持一次最多 10 份、单份 30 MB、总计 100 MB、预览不超过 100 页的限制；持久实例逻辑材料配额 5 GiB、5000 个批次、10000 份申请、2000 次汇总。没有自动归档删除或生产备份实施。上线前需确认表结构、专用 Box 凭据、中文字体、财务人员权限及备份/恢复方案，再统一提交发布并明确启用开关。**填写 Box Token 本身不会自动完成这些上线步骤。**

## 生产运行依赖

2026-10-24 用户授权补齐后的回读结果：上述 11 处结构差异已消除，原有列定义保持不变，未写入业务记录。固定审核姓名自动匹配现有有效账号；姓名缺失或重名时保持未匹配，邮件收件人还需已验证邮箱。正式服务器环境配置、发布启用与真实业务/邮箱验收独立于本次建表，不因表已补齐而自动执行。

PDF/OCR 所需包已列为生产依赖，避免发布端 `npm ci --omit=dev` 后缺包。正式服务提供受限的 `/vendor/pdfjs/` 浏览器资源路由，仅放行 PDF.js 主模块、worker、字符映射、字体和 WASM；不会暴露任意 node_modules 文件。中文活动报销表默认使用随代码提供的授权字体，不再依赖 Linux 安装系统字体；仍支持 `REIMBURSEMENT_FONT_PATH` 覆盖。本轮没有执行依赖安装脚本、部署或真实业务迁移。

邮件继续复用现有发信通道；Nodemailer 固定为 10.2.1，修复上游已披露的收件地址解析问题，保持原有邮件与附件回归。

## 查询范围与刷新预算

2026-10-22 收窄：报销存储不调用 `listRows`，也不在查询失败时回退全表扫描。SQL 只允许固定的四张财务子表、显式列、`WHERE` 和 `LIMIT`。事务用序号游标增量读取；数据块用引用哈希批量 `IN`；投影按受影响的平台申请/汇总 ID 查询和回读，不读取无关历史财务行。实例冷恢复后的首次写入会按平台 ID 核对已管理投影，随后只处理发生变化的记录及其依赖。

页面状态复用 1.5 秒展示快照，活动目录另复用 5 秒结果；命中不会延长有效期。并发读取合并；写操作和提交前的版本校验强制刷新，不借展示缓存授权。收件人按绑定账号 ID 查询最多两行，仅取联系信息，不读取账号全表、密码或密码哈希。

事务表按追加协议使用。运行中增量校验会核对头部及新记录，不持续重读已校验的旧记录；历史行被人工修改时，冷恢复或另行完整性核查才会验证那段历史。不能把实时头部检查说成每次都完成了全历史审计。真实 SQL 执行耗时、服务端索引与规模表现尚未进行生产测量；目前证据来自合成查询次数及返回行数。

物资目录 GET 也纳入现有按表失效的展示缓存，借用资格和提交/出库校验仍走新鲜读取。其他模块已有 `catalog` 的生产调用统计未在本轮复现，不将本轮优化描述为已解决整站所有查询问题。

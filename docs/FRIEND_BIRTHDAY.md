# 写给挚友：下一次生日的一次性祝福

生日投稿增加 `friend`（写给挚友），与随机匹配、祝福仓库并列。作者仍须加入生日祝福计划，填写昵称、最多 200 字正文、挚友邮箱及生日月日，并确认提交；不要求挚友注册。仍计入每人最多 3 条投稿，但不换取随机祝福额度，不会进入一对一或仓库抽取池。

## 日期、审核与投递

- 按北京时间计算下一次生日，保存完整的计划投递日期；当天投稿仍可安排当天，日期已经过去则安排下一年，2 月 29 日安排下一个有效闰年。不采集出生年份。
- 投稿与编辑均进入既有人工审核。已通过的稿件不能修改，可在发送前删除以取消；退出计划、被拉黑或停用账号也会阻止新的发送。
- 计划生日当天，从 `WARMTH_DELIVERY_HOUR`（默认北京时间 08:00）之后每分钟检查。服务重启后恢复扫描；当天较晚审核通过也可在后续扫描发送。过期未发送的稿件不在其他日期补发，也不会下一年再次发送。
- 新任务由生日模块启用、SMTP 可用、具体稿件审核通过共同触发。无需新增服务器变量，不受控制随机/仓库批量匹配的 `WARMTH_DELIVERY_ENABLED` 开关影响；该开关的既有匹配行为保持不变。
- 邮件直达挚友，仅发送一次，不创建站内收信。发件记录使用 `WARMTH-FRIEND:<投稿ID>:<计划日期>` 幂等键，复用现有 SQLite 邮件状态库。SMTP 结果未知时不盲目重发，应在现有邮件任务中核对；不承诺跨系统事务或绝对送达。
- 作者在自己的祝福详情查看邮箱、生日、计划日期和邮件状态；管理员审核详情可查看目标。不会通过其他成员的列表、祝福库抽取或收到的祝福接口公开目标信息。

## SeaTable 追加字段

仅在「温暖连接投稿表」追加三个 `text` 字段：`挚友邮箱`、`挚友生日`、`计划投递日期`。投递回执复用「温暖祝福投递表」：来源为「写给挚友」、站内状态为「仅邮件」、收件人学号为空；收件人标识使用邮箱摘要，不存原始邮箱。祝福库增加「写给挚友」分类，无需追加列。

缺少这三个字段时只阻止新类别提交和自动投递，已有生日祝福与早安晚安继续可用；检查不会自行修改表结构。

先预览，再按确认后的计划补列，完成后再次预览应没有缺项：

```sh
node --env-file=.env.schema scripts/apply-birthday-schema.mjs
node --env-file=.env.schema scripts/apply-birthday-schema.mjs --apply --confirm=CREATE-NJU-RC-BIRTHDAY-SCHEMA
node --env-file=.env.schema scripts/apply-birthday-schema.mjs
```

这是生产表结构修改；本功能开发与测试只执行预览，不写生产数据、不发送真实邮件。上线前先补列，再推送代码。

## 验证

节点测试覆盖 200 字边界、目标校验、月日与闰年、北京时间跨日、一次性发送、审核/退出门禁、回执丢失后的幂等恢复，以及缺列时旧功能继续可用。浏览器测试覆盖桌面/手机的新建与编辑、目标必填、日期选择和内容计数。后台投递测试只使用合成邮箱与模拟发送器。

# 活动管理测试反馈核查与后续计划

核查日期：2026-10-13。会议参与者：金中宸、袁金雨、王泰杰。实施负责人：王泰杰。
核查以当前 main 的真实代码与隔离回归为依据；会议描述不自动等于已复现的根因。本文不授权修改生产报名、请假、审批或计时规则。

## 反馈与现状

| 反馈 | 当前证据与结论 | 后续处理 |
| --- | --- | --- |
| 白屏、卡顿、表加载失败 | 前轮线上浏览器仍出现 12 秒超时，而服务器部分活动 GET 在约 0.5–3.8 秒返回 200；不能把服务端成功当作客户端成功。 | P0：用本轮关联日志区分 TLS/传输、NJUTable、排队、解析与渲染。 |
| 服务器价格低，配置不足 | 用户确认新加坡国际型轻量服务器、2 核、1GB、200Mbps 峰值；采样未见 CPU 饱和、OOM 或进程崩溃。价格不是根因证据。 | P0：先比较地域/线路、CPU/内存与依赖耗时，再决定升配或迁移；不得承诺换机必定修复。 |
| 请假后不能重新报名 | `lib/events/workflow.js` 的 `register` 对普通活动只拦截占位状态；献血车/非普通活动则被同人历史记录拦截。普通活动的获批后重报已有 `tests/ordinary-groups.test.mjs` 回归。 | P1：统一“有效报名”判定，保留旧请假历史，新报名用新 ID；验证源岗位同步与最后名额并发。 |
| 请假驳回后应变空表释放岗位 | `decideLeave` 当前获批才释放，驳回保留报名；符合通常取消审批含义。会议措辞与此相反，尚需业务确认。 | 不直接清空历史表。确认后画出状态转移表，再实施。 |
| 审批显示失败 | `decideLeave` 顺序执行源岗位释放、网站报名更新，随后 API 写审计；不是跨表事务。部分成功后网络超时是代码层风险，尚未以该次生产操作日志复现。 | P0：记录关联耗时；P1：幂等操作号、阶段结果、失败后对账，不自动重试业务写入。 |
| 请假审批邮件未到 | `workflow-api.js` 的 leave-approve/reject 调用状态变更和审计，没有对应结果邮件派发；报名成功通知不等同于请假结果通知。 | P1：审批持久化后生成独立通知任务；发送失败不把审批结果改为失败。 |
| 报名邮件缺少群号、注意事项 | 有报名通知草稿编辑，但 `registration-notifications.js` 与 `roster-review.js` 使用独立固定邮件文本，并未完整复用通知草稿。 | P1：活动级邮件模板、预览、版本、群号与注意事项；最终确认名单前锁定版本。 |
| 缺少现场签到 | 新 workflow 已有照片提交、签到时间门禁、人工及批量核验；旧 events 路径另有二维码/摘要凭证。不是完全没有签到，而是两套流程未统一。 | P1：以当前 workflow 为主线，统一入口；二维码不得仅把报名 ID 当授权凭证。 |
| 合并签到和时长 | 已有 `checkinAndReview`、批量 `checkin-review` 与时长工作台；核验、核定、批准、入账仍是不同业务动作。 | P1：整合到同一工作区；不能以 UI 合并跳过审批或给时长待定活动自动记时。 |
| 手机混乱、字体不一致 | 本轮没有对全部手机页面完成新的视觉验收；既有桌面主从工作区不等于移动现场流程已优化。 | P2：按任务简化信息层级，360/390/768px 真浏览器验收。 |
| 替换“ng table”前端 | 所指产品、许可、集成模式尚不明确；无证据表明换框架能修复跨境网络、缺表或多次远程调用。 | 暂不替换原生 JS/CSS；先明确产品链接并做隔离验证。 |

## P0：可观测性与稳定性（先做）

- [x] 统一服务端 HTTP 完成/断开日志，所有路由携带随机请求 ID；路径去参数、去业务 ID。
- [x] SeaTable、SMTP、NJUBox、OSS、外部内容读取的依赖耗时；业务队列等待、密码计算及后台任务分类。
- [x] 浏览器 API 耗时/错误上报与请求关联；限速、抽样、同源校验、2KB 上限、故障不递归上报。
- [x] 每 30 秒采样 RSS/堆内存、CPU、事件循环延迟和活动请求数；JSON 日志进入既有服务 journal。
- [ ] 上线后按实际用户操作窗口汇总浏览器、应用、依赖及 Nginx p50/p95/max；确认具体慢路径，不能凭单次均值验收。
- [ ] 对超时后“已提交还是未提交”提供操作结果查询；限制重复点击但不假报失败/成功。
- [ ] 完成隔离压测，数据/SMTP/文件服务全部用合成隔离资源，不向生产表或真实邮箱施压。
- [ ] 对候选地域做相同负载、相同 API 的对照；单独报告公网链路、服务器→NJUTable 与计算瓶颈。

## 性能验收协议（待业务确认）

“每分钟 100 人在线”混合了并发人数与到达率。建议基线：100 个同时在线会话，渐进升压，持续 10 分钟，思考间隔 3–8 秒；70% 浏览、20% 查询、10% 报名/取消申请等写入。另测 100 人/分钟进入的突发场景，二者分别报告。

建议门槛：无崩溃/OOM、无超卖与重复入账、非预期 5xx <1%；页面切换可交互 p95 ≤1s，缓存命中只读 API p95 ≤1s；外部依赖冷读和写入单独设 SLA，不能用骨架屏出现冒充数据加载完成。现阶段未取得“100 人并发通过”结果。

## P1：业务流程闭环

1. **请假与重新报名**：确认获批/驳回语义；新旧报名记录独立；取消前后名额对账；已签到/入账禁止误释放；覆盖同班次重报、重复审批和并发抢最后名额。
2. **操作幂等与补偿**：记录审批阶段；跨表部分成功可查询、修复；重试不重复释放/通知；展示“审批已保存，通知待处理”。
3. **统一通知编辑与回执**：群号/群链接、集合地点、负责人联系方式、注意事项；文本/HTML 同内容；模板变量校验、转义、预览和版本；SMTP 接收不等于收件箱投递。普通直确认与批量名单两条路径统一使用同一模板契约。
4. **签到凭证与工作区**：随机、限时、绑定活动及报名的凭证；服务端摘要验证、核验权限、重复签到幂等、操作留痕；手机扫码和人工检索并存。
5. **签到—时长联合操作**：同屏查看与编辑服务/培训/交通时长；项目跨班次汇总；核定、审批、入账分权不变；待定时长不得补成 0 或默认 2 小时；导出与底表逐行对账。

## P2：移动端与一致性

- 活动 Explorer 在手机上变为目录/详情分步，不把桌面多栏整体缩小；筛选可收起，主要操作固定且可触达。
- 请假/名单/签到呈现不同状态，错误就地反馈；保留搜索、选择、滚动位置与筛选参数。
- 使用现有 tokens、组件、字体与密度规范；正文可读、长名称换行、控件对齐；键盘、焦点、触控目标和低动效覆盖。
- 验收范围：未登录返回、空态/满额/错误态、大量活动、审批中、请假获批/驳回、弱网、二维码不可用、时长待定。

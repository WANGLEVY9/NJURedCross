# 部署、回滚与运行维护

## 注册和登录并发隔离（2026-10-21）

`/api/auth/` 不再等待业务共享写锁。身份请求使用 `identity-maintenance.sqlite` 的共享读锁并行执行；同邮箱操作与同学号注册/资料变更仍由单 Node 进程内的键锁互斥，两个校园邮箱后缀不能并发认领同一学号。SMTP 发送保留在对应用户流程内，不占用全站业务写锁，也不阻塞其他学生注册。身份表分页每页 500 行，减少往返读取。

身份读取按列定向：注册学号查重、账号绑定行与验证码读取使用 `readIdentityRowsByField` 定向查询（表与列白名单、值拒绝引号与控制字符、分页读到完整），客户端不支持 SQL 或按键不可用时回退到既有完整分页读取；语义不变，读取不完整仍停止操作。注册不再重复回查账号、不再预检验证码冷却（由 `issue()` 统一判断并返回相同 429）。

协调维护脚本先取得业务写锁，再取得身份维护独占锁，确保与在线身份操作不重叠。维护超时停止脚本，不跳过锁。仍只支持单 Node 实例；多实例前必须建立邮箱、学号与凭据更新的跨进程协调。旧版已复制到服务器的维护脚本可能不含新门禁，账号维护须使用包含此修复的脚本版本。

发布无需数据库结构迁移或调整环境变量；重启自动建立本地协调文件。此修复不会自动修复历史部分成功的注册，也不会批量补发验证码。继续关联 requestId、30 秒预算与依赖日志；连接提前断开且日志状态为默认 200 时不能计为注册成功。

### 会员中心志愿时长外部源（2026-10-22）

会员中心"活动志愿时长"来自只读外部 Base「南大红会 志愿服务平台」（`SEATABLE_VOLUNTEER_PLATFORM_API_TOKEN` / `SEATABLE_VOLUNTEER_PLATFORM_BASE_UUID`），读取其「个人主页（编辑版）」的「总志愿时长」「志愿时长（25-26）」两列，按"姓名＋学号"与身份库账号匹配（账号缺学号列时回退校园邮箱前缀，自助注册强制前缀＝学号）。实现见 `lib/events/volunteer-platform-hours.js`。

- 外部索引按 `PLATFORM_VOLUNTEER_PLATFORM_CACHE_MS`（默认 300000 毫秒，0 关闭）在进程内共享缓存，单飞重建；外部读取失败只影响本字段，接口其余部分正常。
- 匹配不到、同名同学号外部行冲突、外部表读取截断时一律返回空，前端显示破折号并提示联系管理员，不得显示伪造的 0。
- 未配置该 Token 时字段保持为空，不阻塞会员中心其他内容；该 Token 只读权限即可，不入仓库。
- 会员报名进度区仍显示本站入账流水；`/api/portal/workflow/me` 的 `profile` 字段保留供报名记录页使用，新增 `platformHours` 供时长卡使用。

## 活动管理的读取与缓存（2026-10-22）

活动管理最贵的一次开销是 NJUTable 的**整表分页读取**（跨境、每页一次往返）。当前分层：

- **分页并发**：`lib/http/paged-rows.js` 按自适应波次（1→2→4→…）并发取页，仍按偏移顺序校验与拼接，遇到短页即停；最后一波可能多读几页（并发完成，不增加等待时间）。上限用 `PLATFORM_PAGED_READ_CONCURRENCY`（默认 8，1–16）。
- **展示读窗口**：管理端投影 `PLATFORM_MANAGEMENT_READ_MS`（默认 30000）。过期后**先回旧值并后台重取**，窗口为 `PLATFORM_DISPLAY_STALE_MS`（默认 min(TTL, 15000)，0 关闭）。**写入仍按表立即失效**——失效即丢弃，不拿旧值兜底，因此写后读取一定看到写入结果。
- **账号表快照**：花名册/负责人名单复用 `PLATFORM_ACCOUNTS_SNAPSHOT_MS`（默认 60000）的单飞快照；名单文件每次都读，所以管理员刚改的配置立刻生效；账号表写入时快照立即失效。登录、会话与身份判定仍直读权威源，不复用该快照。
- **写入路径**：`applyWorkspaceLiveEdit`、时长入账 `mirror` 等循环只整表读一次（入账还会把新建的镜像行回写进快照），表结构读取有 60 秒进程内缓存。

排查时关注遥测里 `dependency seatable` 的**次数与 p95**：命中缓存时同一路由不应持续产生新的整表读取记录；若 catalog 的 p95 仍接近客户端 12 秒预算，优先核对跨境链路，而不是继续放宽缓存窗口。

### 登录报"密码错误"与"登录尝试过多"（2026-10-21）

排查登录类反馈时先分清三种返回：`401 用户名或密码错误` 表示账号未解析到或密码不符（账号不存在、邮箱后缀选错、别名未命中都会走这一条）；`429 登录尝试过多` 表示被限流；`403 email_verification_required` 表示账号未验证。账号是否登录成功只看身份审计 `identity.login`（成功才写），失败登录不落审计。

已知两个易踩点：

1. 别名解析曾只对 `member` 角色生效，管理员用学号或姓名登录会解析不到而报密码错误；现已对所有角色生效，重名或重复学号仍按歧义返回 409。
2. 限流曾按 IP 计 5 次即封 15 分钟，同一校园网/宿舍网出口下，一台设备连续输错会把同网其他设备一起挡住；现按"IP＋账号"计 5 次，纯 IP 阈值 25 次，登录成功只清该邮箱计数。

会话有效期 8 小时，Cookie 为 `SameSite=Lax`：从微信/邮件等外部链接打开仍保持登录；跨站写入仍受 SameSite 与 CSRF 令牌双重约束。

### 手机端注册失败与配置读取（2026-10-21）

`GET /api/auth/registration-config` 失败只说明本次读取没成功，不等于注册关闭。此前注册、找回密码、修改密码三个页面在配置读取失败时把 `enabled` 置为 false 并禁用提交按钮，弱网手机端因此显示"注册通道暂未开放"且无法提交，必须刷新；换到网络稳定的 PC 端即恢复正常。现改为：只有服务端明确返回不可用才停用按钮；服务端仍按 `available()` 返回 503 `registration_unavailable`，不会绕过任何服务端门禁。

排查此类反馈时先看服务端入口日志：配置接口记为 `/api/auth/:id`；浏览器遥测 `outcome` 为 `network`/`timeout` 且 `requestId` 为空表示请求未到达应用，属客户端链路问题，不要据此判定服务不可用。

### 待验证账号邮箱换绑（2026-10-21）

学生注册时选错校园邮箱后缀（如研究生误选 `@nju.edu.cn` 而非 `@smail.nju.edu.cn`）会留下未验证账号并占用学号：换正确后缀注册被"该学号已关联账号"拦截，对正确邮箱找回密码又因无对应已验证账号而不发信。处理方式是换绑该未验证账号的登录名与邮箱，然后由学生本人重新获取注册验证码。

使用协调入口执行（默认空跑预览；确认输出后加 `--apply` 写入并回读核验）：

```bash
node scripts/run-coordinated-script.mjs rebind-pending-email.mjs \
  --account=<现有登录名或邮箱> --email=<完整新校园邮箱>
node scripts/run-coordinated-script.mjs rebind-pending-email.mjs \
  --account=<现有登录名或邮箱> --email=<完整新校园邮箱> --apply
```

脚本仅限角色为 member、状态启用、邮箱未验证的账号，且新邮箱后缀须为校园域名、前缀与账号学号一致、未被其他账号占用；已验证账号不能通过此脚本换绑。

以明确 Git 提交和文件清单为发布单位，记录配置版本、Node/npm 版本、lockfile、表结构版本与静态资源哈希。源码、环境配置和数据迁移独立管理。

## 运行拓扑

| 项目 | 值 |
| --- | --- |
| 运行目录 | `/opt/njuredcross` |
| 服务 | `njuredcross.service`（systemd） |
| 反向代理 | Nginx，终止 HTTPS |
| 发布记录 | `/var/lib/njuredcross-deploy/release.json` |
| 照片目录 | `/var/lib/njuredcross-evidence` |
| 运行状态目录 | `.write-state`（邮件、物资、写锁、`jobs.sqlite` 队列） |

当前典型环境为单个 Node.js 服务、systemd 和 HTTPS 反向代理。完整 Node 服务默认监听所有网卡，部署时通过防火墙/代理限制直接访问；仅界面 preview 绑定回环。身份使用私有 Base，生产设置 `NODE_ENV=production`，启用 HTTPS/Secure Cookie。

判断运行版本以 `release.json` 为准，它记录提交号、变更文件与全部运行文件哈希。服务器上的 Git HEAD 单独不足以证明运行代码版本：运行目录由发布树复制加增量更新而来，HEAD 只反映历史部署动作。核对时把 `release.json` 与运行文件哈希一起看。

`/api/health` 受保护：匿名访问返回 401 是接口边界，判断服务是否可用请连同 `systemctl status` 与页面实际响应一起看。

## 发布流程

1. 选定提交，记录服务器当前文件和差异，备份配置、待替换文件及必要数据。
2. 使用匹配的 Node 版本和 `npm ci --ignore-scripts`，完成 `verify` 和依赖审计。
3. 在隔离环境核验 SMTP、SeaTable、NJUBox 与业务流程；依赖重大升级尤其需要集成验证。
4. 如需迁移，先预览、验证 UUID 和列类型、备份，再按工具执行并检查结果。
5. 替换审核后的文件；后端和依赖变化需重启进程，静态文件按请求读取。
6. 检查服务状态、实际版本、HTTPS、公开接口、会话与权限；核对资源哈希。
7. 记录结果与可恢复的前一版本。业务验收失败时执行对应回滚，不把推送当上线。

## main 自动部署

Owner 可直接推送 main；其他开发者继续使用主题分支和 PR。main 的删除与强推规则适用于所有人。GitHub Actions 的 `Deploy main to production` 任务在六类质量检查全部通过后运行（Node 22/24/26 × Linux/Windows 共六组）；较旧提交若已被更新的 main 替代，由最新提交部署其全部累计变更。

服务器另有一个十分钟兜底同步 timer：它只部署 `Quality gate` 已成功的最新
main，并在 Actions 部署失败或延迟时调用同一个发布接收器。安装、状态与回滚
边界见 [main 分支十分钟同步](MAIN_SYNC_AUTOMATION.md)。

`scripts/package-release.py` 只打包已跟踪的运行源码（server.js、package/lockfile、lib JavaScript、public 资源），排除隐藏文件、.env、数据库和生产日志。服务器通过独立且限于部署命令的 SSH 密钥接收；主机公钥固定校验，不关闭 SSH 主机验证。密钥保存在 GitHub Actions 加密 Secrets 中，生产 NJUTable Token 不上传到 GitHub。

接收器 `scripts/receive-release.py` 安装在 `/usr/local/sbin/njuredcross-ci-deploy.py`，校验路径、压缩包、文件哈希与 JS 语法，仅替换发生变化的文件。每次备份在 `/opt/njuredcross-backups/main-*`；部署状态与完整运行文件哈希记录在 `/var/lib/njuredcross-deploy/release.json`。只删除上一次部署明确管理、而新提交已移除的运行文件。前端变更无需重启：交付层会按 `index.html` 与 `public/styles/**/*.css` 的文件指纹刷新 HTML shell 和样式 bundle；后端变更重启服务；依赖变化执行 `npm ci --ignore-scripts --omit=dev`。

部署后检查 systemd、HTTPS 页面、运行文件哈希和 .env 未变化。失败恢复已替换文件、依赖和服务，部署状态不前移。此代码回滚不涉及数据库，也不撤销外部业务操作。照片、私有 Base 和环境配置始终独立保留。修改服务器接收器或轮换部署密钥时，需要由 Owner 显式维护外部安装文件和 Secrets。

本地验证接收器：`python3 -m unittest discover -s tests -p '*_test.py'`。查看发布状态：GitHub Actions 的部署任务，以及服务器上的 `release.json`。

## 连接重置与加载超时

不要把浏览器 `ERR_CONNECTION_RESET` 直接等同于 Node 崩溃或 NJUTable 故障。先对齐客户端故障时间，再核对 systemd 重启、内核 OOM、Nginx 上游错误、TLS 连接和 API 耗时。
2026-10-13 晚间排查时，2 核主机负载约 0.02，可用内存约 294MiB，Swap 未使用，根分区使用 22%；未发现该窗口内的崩溃或 OOM。本机应用约 2ms、本机 HTTPS 约 68ms，公网采样约 1.1–3.6s。这是单点样本，不是 SLA，不能证明所有客户端链路正常。

原 Nginx 仅启用 HTTP/1.1。2026-10-21 起站点已启用 HTTP/2（`listen 443 ssl http2;`，备份在 `/opt/njuredcross-backups/nginx-20261021-http2/`），手机弱网下 60+ 静态资源不再挤在 6 条 HTTP/1.1 连接上排队。`ops/nginx/njuredcross-site.conf` 与 `ops/nginx/njuredcross-timing.conf` 提供 nginx 1.24 的 HTTP/2 和分段耗时配置，独立于应用自动部署，不能未经审阅覆盖其他站点配置。回滚：恢复 `site.before` 后 `nginx -t` 并 reload（HTTP/1.1 客户端不受影响，可安全回退）。
操作前备份站点配置；先安装 `conf.d` 下的日志格式，再安装站点，运行 `nginx -t` 后平滑 reload；测试失败恢复备份。不要关闭 TLS 校验。
本次原配置保存在服务器 `/opt/njuredcross-backups/nginx-20261013-connection/site.before`。回滚需恢复站点文件、移走本次新增的 timing 配置，再检验、reload。

新日志 `/var/log/nginx/njuredcross-timing.log` 记录路由类别、状态、协议、字节数、总耗时及上游耗时，不记录账号、IP、Cookie、查询参数、正文或业务行 ID；沿用 Nginx 每日轮转、14 份保留策略。

- 总耗时高但上游低：检查客户端接收、公网出口和链路。
- 上游耗时高：结合 API 排查身份源、业务 Base 和应用读取链。
- 499：客户端中止，不能单独判定服务端崩溃。
- 浏览器失败且日志无对应完成请求：检查 DNS、TLS、代理和网络路径；尚未完成的请求也可能未写日志。
- CPU/内存长期饱和才优先升级计算规格；公网带宽、突发型 CPU 积分和依赖服务瓶颈需分别核实，升级 CPU 不等于升级公网带宽。

前端只读 GET 在连接中断、响应不完整和 502/504 时最多重试一次，两个尝试共享 12 秒上限。401/403、业务冲突及业务写入不通过此机制重试。持续故障仍显示可重新加载的错误，不将其伪装成空表。

## 全链路耗时诊断

生产环境默认启用 `PLATFORM_TELEMETRY`（显式 `false` 关闭）；非生产需显式 `true`。JSON 日志写标准输出，由 `njuredcross.service` 的 journald 接收，不新增第三方上报服务，不写 NJUTable。journal 保留量由主机配置管理，排障前应核实剩余磁盘和保留策略；Nginx timing 日志另按既有 14 份日轮转。

- `http`：所有入口的脱敏路由、方法、状态、总耗时、断开标志、活动请求数、依赖次数/累计耗时。返回 `X-Request-ID`，Nginx 配置同步更新后亦记录该 ID。
- `dependency`：SeaTable SDK 请求（包括认证）、SMTP、NJUBox、OSS、外部内容、队列等待、密码计算及后台任务分类。默认最多 10000 条诊断记录/分钟/进程，丢弃数量进入下一条 runtime；并行调用的累计耗时可能大于请求墙钟耗时，不要相减计算网络时间。
- `browser`：共享 JSON API 边界的完成耗时、失败类型、服务端请求 ID 与每次尝试独立的 clientTrace。超过 1 秒及错误尝试优先上报，快速成功抽样 5%，每标签最多 20 条/分钟；写入仍只执行一次，日志不会自动重发业务操作。文件下载、原生导航、渲染耗时不在该浏览器指标内，服务端仍覆盖所有入口。
- `runtime`：每 30 秒输出 RSS/堆内存、进程 CPU、事件循环 p95/max、活动请求数与日志丢弃量。CPU 百分比按单核计，可能超过 100%。

Fetch-only 适配器标为 `headers`，只计响应头到达时间，读取正文仍包含在外层 HTTP 耗时中；SeaTable/有界外部请求计至正文消费完成。共享请求、缓存和后台任务可能没有一一对应的 HTTP 父请求；不能把重复利用的依赖计成每位用户一次调用。HTTP finish 代表应用已交给传输层，不证明浏览器已完整收到。

浏览器上报端点 `/api/telemetry/client` 仅 POST、同源、2KB、3 秒读取预算、按 IP 每小时 12000 次限制，并受全局日志限额控制。客户端数据标为不可信，严格白名单取字段；不得据此更改业务状态。跨站、超限和非法格式被拒绝；日志写入失败不得使报名、审批或读取失败。新日志不含 Token、Cookie、邮件正文、学号、邮箱、原始查询参数、文件名或 SDK 异常正文。旧业务审计记录保持独立。

在本地仓库目录排查最近半小时（时间按服务器本地时区确认；汇总脚本不包含在生产运行包内）：

```bash
ssh -S /private/tmp/njuredcross-config.sock root@47.82.5.176 "journalctl -u njuredcross --since '30 minutes ago' -o cat --no-pager" | node scripts/summarize-telemetry.mjs
```

汇总脚本只接受已知诊断结构，最多统计 100000 条，不回显其他应用日志；输出各路由/服务 p50、p95、max 和失败数。浏览器抽样/限流统计不能直接作为全站错误率，压测报告应使用请求发生端的完整计数。

关联顺序：浏览器 clientTrace → HTTP clientTrace/requestId → dependency requestId → Nginx requestId。未收到响应头时浏览器没有 requestId，仍可按 clientTrace 查应用入口；连应用入口日志都没有时检查 DNS/TLS/代理/传输路径。新增 nginx requestId 格式需单独备份配置、`nginx -t`、reload，应用发布不会替换 `/etc/nginx`。

会议缺陷分类与后续验收见 [活动反馈待办](ACTIVITY_FEEDBACK_BACKLOG_2026-10-13.md)。

### 底表同步献血车报名控制

活动管理按自然周（周一至周日）归组，项目名形如「11.2-11.8 市血液献血车志愿服务活动」，默认进入「场次报名管理」。每场按日期、点位、时段确定，提供可反复切换的「结束报名 / 开放报名」；按日期或点位搜索筛选后，还可对列出的场次使用「批量结束报名 / 批量开放报名」；也可选择「整周结束报名 / 整周开放报名」。单场操作只影响所选场次，批量操作只影响当前筛选出的场次，整周操作会统一当前周次的场次。批量请求携带场次 `_id` 列表（上限 500），由服务端在一次事务中逐场递增版本；空选择、重复场次、混入非献血车班次一律拒绝，权限与单场一致并在写入时重新核验。

生产读取 `SEATABLE_BLOOD_SOURCE_TABLE` 指定的底表（未配置时为「市献血车汇总」），测试默认「市血液献血车排班表（汇总底表）」。创建、点位、容量和时段继续读取 NJUTable；开关保存在现有私有 `activity-lifecycle-<Base摘要>.sqlite` 的 `source_registration` 表，不写业务底表，无需 NJUTable 增列。单场开关使用实际表名加场次业务标识作为键，源行增加或替换不重置开关，不同来源表之间不共用单场决策。周次决策缺失时沿用改版前的月度决策作为默认值；周次自动化的配置、发布时间与执行回执保存在同目录 `blood-week-<Base摘要>.sqlite`。备份/恢复私有状态目录须包含这些 SQLite 文件。

结束报名后，该场退出活动广场并拒绝直接链接的新报名；重新开放不覆盖底表停点和自然结束状态。已有报名、签到与时长流程继续可用。「结束活动」仍使用既有不可逆月度结束记录，不能通过报名开关重开。权限沿用地区和类别的项目报名管理规则，写入时重新核验；整周决策和现有场次在一次 SQLite 事务中提交，过期版本拒绝覆盖较新决策，审计记录包括范围、状态及版本。生产验证只读，不自动开关真实场次。

- 报名名单包含独立请假状态与原因；进行中工作区另列“请假申请与处理记录”。审批仍使用既有身份、CSRF、活动归属和结果通知队列，不新增人工发送动作。

# 页面加载与数据刷新

## 加载链路

活动列表来自 NJUTable，展示数据不应随着每次路由进入重复扫描。公共活动快照此前保鲜 10 秒、预热间隔 30 秒，间隔中的请求需要重新等待外部表读取；献血车投影还存在串行读表和重复解析。浏览器的未压缩模块、样式和列表 JSON 也增加了首次访问的传输成本。

本次调整采用以下边界：

- 服务端公共活动快照保鲜 10 秒，之后最多 20 秒可先返回已有快照并后台更新；超过时限或首次无快照时等待真实读取。预热每 10 秒执行，同一快照的更新请求合并，失败不会延长旧快照寿命。
- 献血车来源展示缓存从 60 秒缩短至 30 秒，活动表、来源表和报名表并行读取。来源缓存与活动投影缓存叠加时，外部直接改表的展示可能存在约 60 秒延迟，另加实际请求时间；不能将快照名额作为报名成功依据。
- 浏览器仅复用四类匿名投影：活动列表、首页概览、公共工作流活动和内建功能能力。内存缓存保鲜 15 秒，活动广场可先展示 45 秒内的已有列表并重新请求；不写入持久存储。业务写操作前后清空浏览器快照，晚到的旧请求不能重新填充缓存。
- 成功的业务写操作清空服务端展示缓存。登录、退出等认证操作不再使公共目录缓存失效；认证及业务写入继续读取权威数据。
- 公共文本资源和白名单公共 JSON 支持 gzip；保留 ETag 与资源重新验证，发布后不会因长期静态缓存停留在旧代码。账号、会员资料、个人祝福收件箱等私有 JSON 不进入公共响应压缩白名单。

## 页面检查范围

| 页面 | 加载方式与调整 |
| --- | --- |
| 主页、活动广场 | 公共数据与会话读取并行提前启动；公共列表跨路由复用；返回广场时已有列表先呈现，再更新 |
| 献血车日历 | 日历独立于个人报名和心愿清单加载；个人信息未读取完成前不启用报名；定时和手动刷新更新数据，写入后先更新个人状态再重绘 |
| 会员中心 | 会员记录、祝福投稿和收件箱并行读取；会员记录先呈现，不等待祝福服务；私有资料不新增浏览器结果缓存 |
| 内建广场 | 功能能力读取提前启动并复用；实际投稿、生日计划和收件箱保持服务端权限检查 |
| 宣传、物资广场 | 保留现有异步数据区域；共享模块预加载、文本压缩；库存和业务申请不套用公共活动快照 |
| 管理端 | 保留按路由加载模块与权限检查；共享资源压缩，业务读写及审核不使用公共结果缓存 |

会员工作流摘要仅读取活动、报名、时长明细和个人汇总四张所需表；管理员审核与业务写入仍保留完整证据读取。

## 验证

回归覆盖缓存并发合并、失效时在途请求、过期与更新失败、gzip 内容一致性及拒绝协商、静态文件更新、私有响应边界和会员读表范围。桌面与移动浏览器验证活动快照先展示、日历不等待个人摘要、心愿清单取消后更新，以及现有导航、权限和献血车 UI。

线上测速必须区分首次完整文档加载、重复完整文档加载和站内路由切换。网络、外部表响应和缓存状态会影响单次耗时；页面标题出现不能替代业务列表加载完成。发布后应同时验证服务器发布文件哈希、生产配置保持不变及公开页面实际加载，不能用本地通过或 Git 推送代替部署验收。

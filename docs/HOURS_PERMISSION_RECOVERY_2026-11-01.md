# 时长审核权限修复与发布核对

## 已确认的代码问题

时长审核的 HTTP 门禁、逐条台账审核和整表退回回调此前调用了活动立项的 `assertReviewer`。地区路由的该方法只接受“待审核”活动；活动进入进行中后，合法审核人也可能收到状态拒绝。地区目录描述同时没有投影 `hoursAccess`，导致页面回退到旧版指定审核人规则，与服务端的地区时长审核规则不一致。

`74b424a6` 主线已包含超管页面入口优先判断。本次继续修复服务端的实际操作路径：使用共享 `assertHoursReviewAuthority`，优先调用 `assertHoursReviewer`，兼容仅实现旧式 `assertReviewer` 的旧路由；缺少可用授权方法返回 503。地区目录的 `hoursAccess.canReview` 与地区时长审核授权采用同一规则。

本次不迁移生产账号、权限名单或业务表。角色仍取自服务端最新有效账号及地区名单；普通管理员仍受地区和类别限制，撤权后写操作被拒绝。整表提交状态、活动审批绑定、版本和防自审等业务限制继续独立检查。

## 回归与覆盖率

新增回归覆盖已审批活动的逐条时长审核及整表退回、HTTP 路由选择正确授权方法、撤权后无写入、超管和不同类别管理员的权限投影。

写锁测试会强制终止合成工作进程。该进程此前继承测试运行器的 `NODE_V8_COVERAGE`，有机会留下空覆盖率文件并导致整个报告失败。现在仅移除这组合成工作进程的覆盖率目录环境变量，保留测试进程的覆盖率收集；HTTP 覆盖率阈值仍为行 90%、分支 80%、函数 90%。覆盖率任务并发限制为 2，减少有界导入工作进程因资源争用超时的偶发失败。

## 稳定性与上线核对

页面权限仅用于展示，所有实际写入仍经服务端授权。未来增加审核入口时，应复用时长审核规则，并同时覆盖页面能力、API 门禁和工作流内部授权，避免只修按钮或只修单个接口。

部署沿用 main 的 CI 质量门禁和原有接收器。发布前刷新 origin/main，保留其他协作者的提交；拒绝非快进推送，不强推。发布后核对 Actions 的部署任务，以及服务器 release.json 的提交号和运行文件哈希。最终验收应包含有效超管、已授权普通审核人、其他地区或类别账号和已撤权账号。该文档记录代码修复依据，不代表生产验证已完成。

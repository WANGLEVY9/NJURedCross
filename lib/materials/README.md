# 物资写入凭证与同机协调

物资申请的出库、归还操作使用持久化凭证，记录请求内容、流水、
申请关键字段的操作前快照、固定更新目标和执行阶段。

## 恢复规则

- 同一幂等键不能用于不同的账号、数量、物资或请求内容。
- 首次写入流水前，必须先保存操作凭证和写入尝试阶段。
- 恢复时重新完整读取流水和申请，不依赖旧缓存。
- 已有唯一且匹配的流水时，可以继续更新申请。
- 申请已达到目标且其他关键字段仍匹配时，确认完成，不重复写入。
- 写入尝试后找不到流水、出现重复流水、内容冲突、读取被截断，
  或申请关键字段发生变化时，停止自动恢复，要求人工核对。
- 同一申请或物资存在未完成凭证时，阻止相关新操作。

恢复接口：

`POST /api/materials/operations/:operationKey/recover`

需要有效会话、物资管理权限、CSRF，以及原操作账号。
接口根据已保存的计划恢复，不接受新的数量或照片。
当前尚未提供控制台恢复按钮；接口不能替代人工核对未知写入结果。

## 同机共享写锁

write-coordinator.js 使用独立 SQLite 文件协调写入。
同一台服务器上的参与进程必须使用同一个本地锁文件。

HTTP 写请求、后台密码重置任务和逾期提醒任务接入共享锁。
等待超时或请求取消后，不开始新的写入；任务结束后释放锁。
锁数据库与凭证数据库分开，锁事务不承载业务数据。

这不是跨服务器分布式锁，也不是 SeaTable 跨表事务。
直接修改底表、其他未接入协调器的脚本和其他服务器仍可能产生冲突。
全局写锁会串行执行参与的写任务，包含它们等待外部服务的时间。
扩大部署规模前，需要重新设计协调方式和性能验证。

每个共享写锁协调器实例默认最多接纳 64 个未完成请求，
包括正在执行和等待锁的请求。超额请求在打开 SQLite 连接之前
返回 503 write_lock_busy，不执行任务。

成功、任务失败、连接打开失败、等待超时或取消后归还接纳名额。
这是单个协调器实例的容量保护，不是跨进程或跨服务器总量限制，
也不构成生产吞吐量或高峰容量验收。

## 本地状态与运维

PLATFORM_WRITE_STATE_DIR 指定状态目录，本地开发默认 .write-state。
生产必须显式配置持久化私有目录，并保证参与进程使用同一路径。
状态目录不得放在 public 下，不得提交到 Git。

未完成凭证不能随意删除。删除或丢失凭证后，既有流水不能自动重建
可信执行计划，需要人工核对。凭证库应纳入受保护备份；
SQLite WAL 模式应使用一致性备份方式，不应只复制正在运行的主文件。
恢复备份前停止参与写入的进程，随后核对凭证与 SeaTable 的实际状态。

## 验证范围

回归测试使用模拟数据、临时数据库和本机子进程，覆盖请求冲突、
阶段持久化、失败后恢复、权限与 CSRF、未完成操作阻断、
进程间互斥、任务失败及进程退出后的锁释放。

合成测试通过不代表真实 SeaTable 故障恢复、生产部署、
跨服务器协调或备份恢复演练已经验收。

## 已复现的问题与修复顺序

### 1. P1：数据源认证错误被误认为平台登录失效

位置：[server.js](../server.js#L2492)、[客户端 API](../public/app/core/api.js#L142)。

现网异常边界将无业务 statusCode 的 SeaTable 401/403 转为 HTTP 503，返回 `seatable_auth_failed`；候选代码直接转发 401/403。使用相同的合成上游失败注入真实 api() 函数：现网版本返回 503，新版返回 401 或 403。浏览器收到任意 401 会清除会话状态；403 也会被解释为平台权限问题，写请求可能尝试刷新会话并重试。

影响：Token 被撤销、服务授权异常等故障会表现为用户突然掉线或无权限。刷新到期前认证不能保证授权永远成功，因此此边界不能省略。

修复：保留现网的业务错误与上游错误区分，将上游认证错误转为 503 和专用错误码；平台自身的登录/CSRF/权限 401/403 保持原义。增加真实 api() 异常路径和客户端会话保留回归。这是相对现网的回退，来自此前源码与现网不同，不是本次 HTTP 模块抽取直接产生的新差异。

### 2. P1：并发报名可能超额或重复确认

位置：[共享报名函数](../server.js#L1076)、[确认与写入](../server.js#L1096)、[公众入口](../server.js#L1664)、[管理员入口](../server.js#L2170)。

共享函数先读报名、计算容量，再 appendRow；两条入口没有共同的串行锁或事务。对真实共享函数构造容量为 1 的活动，同时提交两个不同邮箱，结果是两条「已确认」和两次写入。复现只使用模拟内存表，没有真实报名。

影响：即使当前为单进程，也会因为异步 I/O 交错超额确认；相同邮箱同时提交也可能绕过查重。这是既有报名逻辑，本轮重构没有消除，不能把身份/资料流程的进程锁当作活动容量保护。

修复：单实例至少让两条入口共用按规范活动 ID 的锁，在锁内重新读取、核算和写入；候补递补、取消及相关容量修改应共同考虑。多实例须使用数据库约束/事务或分布式锁。增加并发容量、同邮箱重复、公众与管理端同时提交的回归。

### 3. P1：读到 5,000 行上限后仍用不完整数据决定写入

位置：[分页上限](../server.js#L237)、[报名读取](../server.js#L1083)、[查重及容量](../server.js#L1096)。

listAllRows() 在第 5,000 行停止并设置 readMeta.truncated，但报名状态机不检查该标记。构造 5,001 条记录，把当前邮箱已有确认记录放到第 5,001 条，再提交同一邮箱：函数仍写入重复记录并返回「已确认」。库存 materialBundle() 同样把有限的流水重建结果用于库存判断，应一并核对。

影响：总体台账超过上限时可能重复报名、超额确认或使用不完整库存。现有线上活动报名表 COUNT 查询为 1 行，因此本次没有证据表明此边界已在该表实际触发；这不否定已经复现的代码缺陷。

修复：写入校验需要精确查询目标活动/场次/邮箱或资产，并保证相关数据完整；如达到安全上限，明确拒绝写入，不能把截断数据当作完整事实。统计接口可以保留截断标记，但需在界面呈现。增加 >5,000 行、跨页查重和流水不完整的回归。此改动来自此前待发布分页逻辑，不是本次重构新增。

### 4. P1：错误权限配置会扩展为所有管理员权限

位置：[权限标准化](../lib/permissions.js#L6)。

normalizePermissions() 按「过滤后有效权限为空」回退完整权限，混淆了「历史空列」和「非空但全部非法」。输入 `event_typo`，实际得到 materials/events/outreach/community/data/settings/accounts 全部权限。

影响：受限管理员因拼写或格式错误可能获得完整权限。普通 member 仍返回空权限，此问题不会直接把普通用户提升为管理员。现网私有账号表中权限列存在，已检查的两个管理员权限列都为空；没有发现当前错误的非空权限配置，因此这是发布权限收口时必须修正的拒绝策略，而不是已确认发生的越权事件。

修复：仅真正未配置的历史账号使用兼容规则；对非空但无合法范围的配置拒绝启动/登录或返回无权限，不能授予全部权限。对有部分合法范围和非法项的处理也应明确约定。补空配置、仅非法项、拼写错误和受限账号真实 API 拒绝路径测试。

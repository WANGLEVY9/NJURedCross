# 大型公开服务型平台综合评审（2026-11-22）

## 评审范围与结论

本次以公开服务网站的验收视角评估当前 `main`（`be852e78`）：前端门户与运营控制台、Node.js 单体后端、SeaTable / NJU Box / SMTP 外部依赖、缓存与后台队列、安全与隐私、部署与观测。检查方式包括源码与架构文档阅读、`npm run check` / `check:links` / `check:security` / 遥测边界 / 生产依赖审计、线上安全响应头与匿名权限边界采样，以及既有工程性能报告的 trace 结论。未做认证后压测、未访问真实业务表、未改动生产配置。

总体判断：**作为校园公益 Beta 平台，工程成熟度明显高于普通原型；安全边界、发布可追溯性、测试覆盖和观测链路已经形成闭环。若按“面向公众持续服务”的标准，当前最大风险不是单点漏洞，而是单体单实例、外部权威数据源读放大、超大前端模块和人工维护契约共同造成的容量与演进瓶颈。**

## 已验证有效的设计

- **权限与隐私边界**：匿名访问 `/api/portal/me`、`/api/notifications/overview`、`/api/volunteer/workflow`、`/api/health` 均返回 `401` 且不返回业务数据；公开 `/api/public/events` 返回 200。服务端会话包含角色、过期、CSRF、撤销列表和凭据版本校验；写操作独立校验 CSRF，客户端提交的角色/账号不参与权限裁决。见 [server.js](../server.js)、[lib/http/response.js](../lib/http/response.js)、[docs/API.md](../docs/API.md)。
- **统一响应策略**：线上 `/events` 实测带 CSP、`Referrer-Policy: no-referrer`、`X-Content-Type-Options`、`X-Frame-Options`、`Permissions-Policy`、`Cache-Control: no-store`；反代补 HSTS，TLS 终止与上传体大小/超时有明确配置。CSP 对 `connect-src` 只额外放行配置的 Box 直传源，避免硬编码多个第三方域。
- **错误与超时语义**：`apiFailure` 区分只读请求、写入结果不确定、上游 401/403 与限流；`withRequestBudget` 对普通请求 30 秒、上传 180 秒，超时明确提示“写入结果可能需要核对”，不诱导盲目重试。
- **读缓存边界**：`displayRead` 只在展示读上下文命中缓存，鉴权、写入、身份库读取直连权威源；写后按表失效，缓存只保存行投影，不保存会话、权限结论或响应体。浏览器只缓存匿名公共投影，私有资料禁用公共压缩白名单。
- **队列与发布**：通知、对账、投递进入本地 SQLite 持久队列，具备去重、租约、退避和重启恢复；CI 六组 Node/OS 矩阵、浏览器分片、跨引擎、时区、HTTP 边界、发布包校验、服务器文件哈希与公网 smoke 构成完整门禁。发布包白名单排除 `.env`、隐藏文件、数据库和 `scripts/` 运维工具。
- **观测**：`traceId/spanId/parentSpanId` 覆盖 HTTP、依赖和后台任务；`requestId` 与 Nginx timing、浏览器上报可关联；日志有独立 journald namespace、脱敏字段白名单和按 trace 收敛工具。此前生产样本已确认持续 `queue/wait` 明显下降，长尾可定位到具体外部 I/O。
- **依赖与源码门禁**：本次检查 1448 个 JS 模块、195 个 Markdown 文档、ESM 具名导入、源码安全模式、遥测边界均通过；生产依赖 301 项，`npm audit --omit=dev --audit-level=high` 为 0 公告。

评审期间远端新增“报名中导出名单”功能后，报名工作区表格一度把报名人邮箱作为常驻列显示，触发既有“表格不回显私有字段”回归。导出端点本身受活动范围、负责人校验和审计保护，因此本轮保留受控 xlsx 导出，同时恢复默认表格不显示邮箱，并在 `docs/API.md` 明确“邮箱仅用于导出联络、不作为常驻显示列”。这体现了公开平台应持续区分「授权导出」与「屏幕默认可见」两类数据暴露面。

## 发现与风险（按优先级）

### P1｜单实例与进程内状态限制横向扩容和故障隔离

架构文档明确“单实例部署”，进程内缓存、限流、会话撤销、写协调器、邮件/物资锁和 SQLite 队列都只保证单进程语义；`docs/ARCHITECTURE.md` 也列出多实例前必须重做的项目。当前 2 核小规格下这是合理的成本取舍，但对公开服务意味着：一次后端重启、事件循环长阻塞或主机故障会同时影响门户、控制台、静态分发与后台任务；无法用第二个实例分担突发流量，也无法在部署时做到真正零中断。部署桥接只能缓冲重启期间请求，不提供多活。

建议：短期保留单实例，但把“容量上限”写成明确 SLO 与告警（CPU、事件循环延迟、队列积压、SeaTable 错误率、5xx/429、磁盘与journald保留），并准备冷备或可快速重建的镜像；中期把会话撤销、限流计数、后台租约迁到共享存储，再把无状态 HTTP 层与后台 worker 拆开。迁移顺序应先解决共享状态，再启用多实例，避免双倍后台任务和缓存不一致。

### P1｜SeaTable 作为权威源带来整表读放大与长尾

既有 trace 报告显示：30,000 行有界样本中 `seatable/read` 独占耗时合计约 790 秒，单次最大 2.24 秒；通知总览、志愿者工作流、个人中心等请求的关键路径常由多次整表读取构成。当前缓存把“重复读”合并了，但写操作、权限证据、审批、名单、时长和导出仍要求完整权威读取；后台 `queue/run` 的 21 秒长尾包含 627 个依赖，其中 495 次读、75 次写多为 15–20ms 串行小请求。

建议：先建立按路由/表的“读取预算”指标（每次请求读取表数、行数、外部往返次数），再按业务语义做定向查询、字段投影和批次化；对通知/对账批次设置固定预算与断点，避免一个队列任务跑几十秒。不要把报名名额、审批状态、时长入账建立在不具备变更流的长期镜像上；跨表一致性仍需读权威源，除非先设计可验证的 CDC/Outbox。

### P2｜`server.js` 仍承担过多路由与装配职责

入口约 7,496 行，导入 100+ 模块并在顶层完成账号、Base、队列、定时器装配；业务路由按前缀回退链委派，物资、宣传、温暖连接等仍有大量逻辑留在入口。文档写明按“物资 → 宣传 → 温暖连接”继续拆分。优点是部署简单、无需框架；代价是任一模块启动失败会影响全站，局部重构的回归面很大，且单点测试难以覆盖全部装配顺序。

建议：继续按 `lib/<domain>/api.js` 抽取，但每一步保留现有 `ctx` 注入与 HTTP 语义，并补“域路由未匹配返回 false → 统一 404”的回归；同时把定时器、队列、认证刷新分成可独立启停的装配函数，为未来 worker 拆分和本地集成测试铺路。

### P2｜前端无构建使模块体积和网络瀑布成为首屏风险

`public/app` 自有 JS 合计约 2.83 MB，CSS 约 1.01 MB；最大单文件包括 `font-faces.css` 214 KB、`admin.css` 162 KB、`activity-center.js` 94 KB、`outreach.js` 89 KB。项目采用原生 ESM、按路由懒加载、样式 bundle、文本压缩、少量发布版本指纹和 ETag，避免引入构建链；但共享模块 URL 长期不变、首屏仍可能形成多级 import 瀑布，管理端大型页面首次加载会受模块数量和 SeaTable 数据双重影响。浏览器 Resource Timing 目前也不能精确拼成单条 API Trace。

建议：不急着引入复杂框架；先用现有浏览器遥测建立按路由的首屏预算（文档字节、JS/CSS 字节、模块请求数、最大模块、LCP/INP 抽样），再对最大的管理端页面做代码分割和字体子集化。若保留无构建，至少为所有首屏模块建立 immutable 版本化 URL，并验证发布后不会同时存在两个模块实例；若引入构建，必须先解决当前“同一模块静态与动态 import 并存”的状态分裂约束。

### P2｜公开写入与上传链路依赖多服务的一致性

影像/附件支持浏览器直传 NJU Box、服务端复核后落表，避免大文件穿过 2 核主机；中转上传保留 180 秒预算并提示写入结果待核对。这是合理设计，但链路涉及浏览器、本站票据、Box 上传直链、SeaTable/OSS 与本地 SQLite 收据，任何一步超时都要靠幂等键和人工核对收敛。公开写接口虽有分桶限流，但限流是进程内 Map，单实例重启即清零，无法抵御多实例或分布式刷写。

建议：把每个上传状态的“票据、字节、落表、收据”做成可观测状态机，并在管理端提供按幂等键核对未确认写入的工具；限流迁到共享存储前，至少在反代层补基础连接/请求速率限制和 429 观测。对 `NJUBOX_SERVER_URL` 做启动时严格校验，避免 CSP 放行意外源。

### P2｜测试极多但契约仍主要靠人工维护

483 个 node 测试、164 个浏览器用例和 CI 矩阵很强，但 `docs/API.md` 明确“不是完整 OpenAPI 契约”；接口数量大、路径分散在 `server.js` 与多个域路由中，新增接口的鉴权/CSRF/限流/观测很容易靠审查记忆保证。现有 `check-telemetry-boundaries.mjs` 和 HTTP 边界测试能拦截部分裸传输，但不是机器可读的接口清单。

建议：生成或维护一份按路径、方法、权限、CSRF、限流桶、请求体上限、缓存策略、观测阶段的机器可读路由清单，由 CI 与运行时注册比对；这比直接生成完整 OpenAPI 更贴合当前原生架构，也能防止路由拆分时遗漏保护。

### P3｜运维与观测仍有边界

- 日志保留目标 7 天/256 MiB、Nginx timing 14 份；有界样本适合排障，但不足以做季度容量趋势或安全事件追溯。需要把脱敏聚合指标导出到独立保留周期，原始日志仍短保留。
- 公网 smoke 是 `continue-on-error: true` 的非阻塞任务，浏览器视觉布局也是非阻塞；质量门主要靠 CI 内测试，不保证每次公网出口抖动都能阻断发布。部署回执已记录 `localHealth/publicHealth`，但应考虑对关键页面 200、CSP、HSTS、登录边界设置硬门槛。
- 安全策略说明“志愿维护者、不设固定响应时限”；对公开服务建议补充轮换周期、备份恢复演练频率、事件分级和联系人冗余，避免治理文档与运维现实脱节。
- `ops/nginx/njuredcross-site.conf` 仍写有旧 IP `47.82.5.176` 作为 server_name；线上实际为 `47.116.184.159`。配置文件注释说明是历史兼容，但应确认新机是否仍需要旧 IP，避免资产变更后留下错误归属或证书/Host 校验歧义。

## 建议路线

1. **立即（不改变架构）**：补容量/SLO 与告警；把公网 smoke 的关键安全头和匿名 401/403 边界改成硬校验；为目标 10–20 条核心路由建立首屏与外部读取预算；修正或确认 Nginx 旧 IP；补备份恢复与凭据轮换演练记录。
2. **下一阶段（低风险代码收敛）**：按 trace 结果继续减少整表读和串行后台小任务；给队列批任务设置固定条数/时间预算；把路由清单、观测阶段、限流桶和请求体上限做成 CI 可比对数据。
3. **中期（为扩展做准备）**：拆分 `server.js` 剩余域路由和启动装配；把会话撤销、限流、后台租约迁到共享存储；对前端最大模块做代码分割、字体子集和统一的 immutable 版本策略。
4. **长期（容量跃迁）**：SeaTable 读模型优化或可验证变更流、无状态 HTTP 与后台 worker 分离、多实例与灰度/回滚、独立指标仓库和事故复盘机制。每一步都需先定义合成故障回归和回滚点，不以推送代替生产验收。

## 本次验证边界

未登录执行只读检查与公开接口采样，未访问真实业务表，未做认证后管理端压测，未复查全部服务器配置；依赖审计仅覆盖 `npm audit --omit=dev --audit-level=high`，不等于完整 SBOM/供应链审计。结论用于确定改造优先级，不替代正式安全渗透测试或容量验收。

# 物资管理模块：完成度审计与剩余工作

更新时间：2026-09-08

## 结论

物资管理模块已经具备可体验的真实 SeaTable 闭环：库存汇总、申请、审批、出库、归还、二维码定位、出入库流水、阈值预警、照片留痕和逾期邮件适配器均已接入。当前真实数据仍以 `工位物资表` 的 100 条库存记录为基线；`物资流水表` 只有新系统真实操作后才会产生事件，不会把历史汇总数量伪造成逐笔流水。

本轮补齐了四个会影响真实使用的缺口：

1. 流水增加结构化的 `流转去向` 和 `损耗数量`，差额追踪不再只能依赖申请用途或备注。
2. 同一资产编码的写操作增加进程内串行锁，并在锁内重新读取库存和申请状态，降低重复出库、并发超借的风险。
3. 多次出库/归还照片采用追加写入，不覆盖已经留存的照片。
4. 归还时用“实际归还数量 + 损耗数量”判断是否已经结清借用单；全量归还但存在损耗时，申请会结束但保留异常状态，进入异常关注。

## 仍未完成或需要上线前加强的工作

### P0：上线前必须完成

- 配置真实 SMTP，并在测试邮箱上验证逾期邮件、失败重试和发件人策略；当前未配置 SMTP 时明确不发送。
- 把本地账户从明文密码迁移到 `scrypt`/Argon2，并为五个管理员补充职责角色和最小权限；当前所有账户仍是平台管理员角色。
- 对 SeaTable 写入失败做可恢复的 outbox/待处理机制。当前已经能把“流水已写入但申请状态同步失败”标记到流水异常说明，但还不能自动重试或提供人工重放按钮。
- 在部署多个 Node 进程或多台机器时，把当前进程内锁替换成集中式锁或数据库事务；现在的锁只覆盖单个 Node 进程。
- 完成集成测试：真实测试申请的审批、出库照片、归还照片、部分归还、损耗结清、重复请求、并发请求、SeaTable 失败和邮件失败。

### P1：业务完善

- 一条申请目前以一个库存资产编码完成出库/归还；多种物资的申请需要拆成申请明细表，逐项核对数量、照片和归还状态。
- 给申请建立明确的“申请明细 ↔ 库存行”关系，不能长期只依赖管理员在表单里选择资产编码。
- 为历史 202 件数量差额补充来源核对流程；在没有原始事件证据前，不应自动生成历史流水。
- 增加分页、导出、A4 批量二维码标签和流水筛选；当前界面为 100 条库存与最近 8 条流水的操作型原型。
- 增加盘点任务：盘点前锁定基线、盘点差异审批、盘点后生成 `盘点增加/盘点减少` 流水。

### P2：产品化体验

- 增加移动端窄屏布局、离线失败重试提示和扫码后直接进入对应操作卡。
- 增加异常归还处理页，允许管理员补充核查结果、责任人和后续处置，而不是只显示异常标签。
- 将敏感联系方式从通用表格中心彻底隔离，按字段权限控制谁能查看邮箱、学号和照片。

## 当前数据边界

- 真实库存基线：`工位物资表`。
- 策略配置：`物资配置表`。
- 新事件审计：`物资流水表`。
- 借用状态和申请人信息：`物资管理`。
- 历史汇总数量没有逐笔来源时，平台显示“未关联逐笔流转记录”，不虚构去向。

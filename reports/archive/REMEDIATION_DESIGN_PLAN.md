# 平台整改设计方案（2026-09-17）

> 面向南京大学红十字会平台的四类问题：**数据不准 / 权限边界 / 流程未跑通 / 协作效率**。
> 所有方案遵守团队上位约束：①业务数据留在 table 底表；②既有表与既有列不动，一律增量；③底表只对核心负责人开放，其他同学在工作台操作。
> 本文中的行号对应 `server.js`（2415 行）当前版本。

---

## 0. 优先级判断

| 优先级 | 主题 | 理由 |
| --- | --- | --- |
| P0 | 数据可信度 | 看板数字是运营同学做决策的依据，错的数字比没有数字更危险 |
| P0 | 数据中心表级放开 | 可绕过审核状态机直接改状态，属于可被误操作击穿的口子 |
| P1 | 权限细分 | 换届后同时在线的操作同学会变多，一把钥匙开所有门不可持续 |
| P1 | 流程跑通 | 活动/流水是空壳，意味着最有价值的 capability 从未被真实数据验证 |
| P2 | 协作闭环 | 提升体验，但不阻塞上线 |

## 1. 数据不准：先让数字可信

### 1.1 读取上限（100 / 500 / 1000）

现状（实测）：`工位物资表` 真实 140 行，平台只读到 100 行；志愿 Base 三张表读数恰好等于上限。

代码位置：

- `server.js:1092-1094` — 物资总览三张表各 100
- `server.js:1848`、`server.js:1858` — 扫码与二维码接口各 100
- `server.js:832-833` `volunteerRows()` 默认 500；`server.js:846` 个人主页 1000
- `server.js:1179-1181`、`1199-1200` — 混合使用 100 / 1000，口径不一致

方案：

1. 新增 `listAllRows(client, table, pageSize = 200)`：按 `start` 偏移翻页直到返回不足一页，统一上限保护（如 5000 行）并计数。
2. 把上述七处全部替换为 `listAllRows`，**不再出现写死的分页常量**。
3. 返回值新增 `meta: { total, truncated }`。前端在统计卡片上：
   - 未截断显示确数；
   - 截断显示 `≥ N` 并在 tooltip 说明「数据源超出单次读取上限，仅统计前 N 条」。

> 诚实呈现上限，比给出一个看似精确的错误总数更安全。志愿服务看板「成员档案 1000 人」这类数字应立刻改为 `≥ 1000`。

验收：物资库存合计由 3782 / 3580 变为真值 5249 / 5047；第 101–140 行物资可生成二维码、可被扫码定位；志愿看板数字带 `≥` 标记或变为确数。

### 1.2 布尔列判定错误（志愿看板「已确认」恒为 0）

`server.js:855`：

```js
if (/成功|通过|已报名/.test(String(row['是否报名成功'] || row['报名结果'] || ''))) event.confirmed += 1;
```

`是否报名成功` 是 checkbox，实际取值 `true` / `false`，`String(true)` 永远匹配不上该正则。

方案：抽一个语义判定函数，集中处理 SeaTable 的三态布尔：

```js
function isFlagOn(value) {
  if (value === true || value === 'true') return true;
  const text = String(value ?? '').trim();
  return /^(是|yes|y|1|成功|通过|已报名|已核对|已录入)$/i.test(text);
}
```

替换点：`server.js:855`（报名成功）、`server.js:866`（`已核对并录入` 的 `verified`）、`server.js:776`（`阈值启用 === false` 的严格相等同样脆弱）、物资侧的「已全部归还」类判定。

验收：志愿服务看板 `confirmed` 不再全为 0，且与 `报名结果` 列的手工抽查一致。

### 1.3 库存预警误报（63 / 100）

`server.js:776`：

```js
const threshold = config['阈值启用'] === false ? null : (configuredThreshold || Math.max(3, Math.ceil(initial * 0.2)));
```

`Math.max(3, …)` 对小额物资把阈值抬到高于其全部库存（真空机初始 2 / 阈值 3；鼠标垫初始 1 / 阈值 3），从未借出却持续预警。

方案（两处一起改）：

1. 阈值计算加**上界**：`Math.min(Math.max(1, Math.ceil(initial * 0.2)), Math.max(1, initial))` —— 阈值永不超过初始量，小额物资退化为「低于 1 件才预警」。
2. `lowStock`（`server.js:786`）改为两级：
   - `critical`：`quantity <= threshold && quantity < initial`（真的消耗了）→ 进 high 待办；
   - `notice`：`quantity <= threshold && quantity === initial`（配置偏紧，非消耗）→ 只在物资中心内提示，不进工作台待办。

验收：工作台「库存预警」high 项从 63 降到个位数，且抽检全部为真实消耗项。

### 1.4 时长队列的状态是合成的

`server.js:868-872`：`活动及时长汇总表` 没有状态列，代码回退常量 `'待核对'`，而过滤逻辑恰好排除「含 通过/已完成/已核对/已发放」的值 —— 常量永远通过过滤，队列恒为最后 12 行。

方案：不要伪造不存在的状态。

- `status` 保持 `'待核对'`，但接口额外返回 `statusSource: 'synthetic'`；
- 前端在该字段旁标注「数据源无状态列，此为待人工核对标记」；
- 排序改为「`志愿时长` 非空且非 0 的优先」，把真正需要核对时长的记录顶上来，而不是按插入顺序取最后 12 行。

### 1.5 宣传模块字段取不到

`server.js:898-900` 读 `负责人 / 团队负责人 / 姓名` 与 `授权 / 是否同意公开`，实际列名不匹配（策划案表是 `答辩人姓名`，授权列三张表都不存在）。

方案：加一张**列别名映射表**（`legacyColumnAliases`，纯新增，不动底表），把 `author` / `authorization` / `submittedAt` 的候选列名按表配置：

| 逻辑字段 | 策划案表候选 | 文创表候选 | 试课表候选 |
| --- | --- | --- | --- |
| author | 答辩人姓名 → 团队名称 | 姓名 → 学号 | 授课人 → 反馈人 |
| authorization | 无 → 回退「未采集」 | 无 → 回退「未采集」 | 无 → 回退「未采集」 |
| submittedAt | `_ctime` 优先于 `_mtime` | 同左 | 同左 |

关键：**授权状态未知时，界面必须显示「未采集」而不是「待核对」**——后者会被误读成「已确认待审核」。若授权字段确实缺失，建议在审核界面加一个显式的「已获作者口头/书面授权」人工确认勾选，并把确认人写进 `宣传投稿表`（增量列 `授权确认人` / `授权确认时间`）。

## 2. 权限与安全边界

### 2.1 角色细分（增量，不破坏既有两角色）

`server.js:39-43` 目前只有 `platform_admin` / `member` 两个值，admin 内部不再细分。

方案：保留两个角色值不变（避免影响登录与既有账号），**新增一层 scope**：

- 平台账号表**新增一列** `权限范围`（text，逗号分隔）：`materials,events,outreach,community,data,settings,accounts`；为空视为全权（兼容现有账号）。
- `requireConsoleAccess`（`server.js:1334`）之后增加 `requireScope(req, res, 'materials')`，按路由前缀挂载。
- 角色新增 `operator`（有 console 面、受 scope 限制），`platform_admin` 保持不限。

这样物资管理员、内容审核员各自只看到自己那块，且**既有账号零改动即可继续工作**。

### 2.2 数据中心收口（P0）

`/api/rows` 可访问全部 25 张表，写入不经业务状态机 —— 意味着解锁后可直接把 `宣传投稿表.审核状态` 改成「已通过」，绕过审核流程。

方案：

1. 建一张拒绝清单 `CONSOLE_PROTECTED_TABLES`：6 张状态表 + `换届报名表`、`工作证明`、`全体成员表（26~27学年）` 等含个人信息的表。
2. 这些表默认**不出现在数据中心表清单**；仅当账号具备 `settings` scope 且二次输入确认短语后才可临时解锁，并在审计表记录解锁动作。
3. 脱敏目前只作用于预览（`server.js` 的预览隐藏正则），写入与删除是表级放开——建议对拒绝清单内的表**直接禁用写入与删除**，只允许在业务页面内走状态机。

### 2.3 交接期治理（社团年度换届的真实风险）

- **Token 分权**：当前一个 rw Token 干所有事。建议拆成两个：平台业务 rw、统计只读；`.env` 命名带任期与用途，换届时只换 `.env` 不碰代码。
- **Token 轮换演练**：每学期一次，在 SeaTable 侧生成新 Token → 更新 `.env` → 重启 → 跑 `npm run smoke:public` 验证。
- **账号退休机制**：账号表已有 `状态` 列，建议增加取值 `retiring`，登录后提示「本账号将在换届后停用」，到期自动置 `disabled`；避免毕业同学的账号长期在线。
- **审计归档**：`操作审计表` 增长最快，按季度导出到 njubox 归档目录，平台侧只保留当季。

### 2.4 身份一致性

账号有显示名，但报名与借用表单仍手工填写姓名，两者无一致性校验。建议：表单默认回填账号显示名并允许修改，修改时记录「填写姓名 ≠ 账号显示名」标记，供核对时留意（不阻断提交）。

## 3. 流程没真正跑起来

### 3.1 一次真实活动全链路演练（pilot）

现状：活动项目表 1 行草稿、场次表 0 行、报名表 0 行，报名 → 候补 → 签到 → 二维码全链路未经验证。

建议用一次**小规模真实活动**（如内部培训）做 pilot：

1. 建 1 个活动 + 2 个场次，容量设为 2；
2. 让第 3 人报名进入候补，验证候补序号；
3. 已确认者取消 → **验证候补是否自动递补**（`server.js:1000-1051` 是报名裁决处，取消侧未见递补逻辑，需确认并补充 `promoteWaitlist()`：把最小候补序号者改 `已确认`、写审计、发通知）；
4. 现场用二维码签到，验证签到码摘要校验（`server.js:827-831`）；
5. 结束后关闭活动，确认公众端可见性判定正确。

配套：新增 `scripts/smoke-flow.mjs`，把上述分支固化成可重复脚本，验证数据用 `VERIFY-` 前缀标记，结束后用 `npm run state:clean-preview` 回收。

### 3.2 物资流水：先导入期初基线

`物资流水表` 0 行，导致趋势图、流转去向、损耗统计全部空转。

方案：一次性脚本按现有借用记录生成**期初流水**（新增操作类型 `期初建账`），把旧汇总列的 202 件差额固化为基线；此后**只走新流程**。这样趋势图有起点，且不改变任何既有表结构。

### 3.3 异常可恢复

「流水已写入但申请状态同步失败」目前只在 `异常说明` 打标记。建议在控制台加一个「异常流水」入口：列出带异常标记的行 → 一键重放状态同步 → 成功则清除标记并写审计。没有这个入口，异常只能靠人肉翻表。

### 3.4 库存锁的部署前提

`withMaterialLock()` 是进程内锁（`server.js`），多进程部署会失效。若短期仍是单进程，建议在 README 与上线清单中明确标注「当前仅支持单实例部署」，避免上线后误配多实例造成超卖。

## 4. 协作与传播效率

### 4.1 通知触达矩阵（复用已有能力，不新建）

已有 `邮件发件记录表`、`活动通知表` 与 `lib/mailer.js`。设计统一的触发点矩阵，全部走同一发信服务并用幂等键防重复：

| 触发点 | 接收方 | 内容要点 |
| --- | --- | --- |
| 报名成功 | 报名人 | 报名编号、时间地点、签到凭证 |
| 进入候补 | 报名人 | 候补序号、递补说明 |
| 候补递补为已确认 | 报名人 | 同上 + 「你已由候补转为确认」 |
| 活动变更 / 取消 | 该场次全部已确认者 | 变更项、重新确认入口 |
| 物资逾期未还 | 借用人 | 申请编号、物资清单、逾期天数 |
| 投稿审核结果 | 投稿人 | 结论、修改建议（如需修改） |

### 4.2 意见反馈闭环（目前完全缺失）

志愿 Base 已有 `问题反馈`、`体验反馈`、`献血车问题反馈` 三张表（只读）。方案：

- 新建 `意见反馈处理表`（增量，主 Base）：反馈来源、原始行 ID、处理状态、处理人、处理结论、回复内容、时间戳；
- 控制台新增「意见反馈」页，只读拉取三张源表 + 在本表记录处理进展，形成闭环；
- 源表保持只读，不回写 —— 符合既有约束。

### 4.3 值班排班看板

`工位值班表` 尚未接入。方案：只读展示 + 换班申请写到**新建的** `换班申请表`，审批走现有物资审批同款状态机模式。

### 4.4 附件与素材

策划案、影像等大文件继续走 njubox（Seafile，实测可读写），平台只存引用（`活动附件表` 已具备）。建议按 `学年/学期/项目` 建目录规范，并在附件表记录库 ID + 路径 + 下载链接，避免文件散落。

## 5. 与上位约束的一致性检查

| 约束 | 本方案的处理 |
| --- | --- |
| 数据留在 table 底表 | 全部新增表落在主 Base；不引入第二套存储 |
| 既有表与既有列不动 | 只做：新增列（`权限范围`、`授权确认人/时间`）、新增表（`意见反馈处理表`、`换班申请表`）；所有现有列零改动 |
| SeaTable 侧自动化邮件保留 | 通知矩阵复用现有发信表与 mailer，不改动 SeaTable 自动化规则 |
| 双轨权限 | scope 细分后，底表仍只对核心负责人开放；其他同学只在 console/portal 操作 |
| 志愿 Base 只读 | 全部方案对其零写入，反馈处理写回主 Base 新表 |

## 7. 合规提示

- 志愿服务时长属于服务记录，应按《志愿服务条例》要求如实记录、可追溯；本平台对志愿 Base 只读、不改时长，符合「不篡改记录」的要求。涉及具体条款请以 [flk.npc.gov.cn](https://flk.npc.gov.cn) 最新文本为准。
- 平台收集学生姓名、学号、邮箱属于个人信息处理，建议：收集前明示用途（`/about` 已有说明，需与最新实践同步）、提供撤回通道、控制可见范围（现有脱敏 + 双轨权限已具备雏形）。
- 📌 以上法律法规相关内容仅供参考，不构成法律意见，请以 flk.npc.gov.cn 最新版本为准。

## 8. 关于工具匹配的说明

机构数字化工具的**正式匹配流程**（机构画像采集 → 需求诊断 → 实时拉取产品库 → 智能匹配 → 产品详情卡 → 速查汇总）依赖「腾讯技术公益智能助手」技能执行。本次已检查本地技能市场、SkillHub 与 ClawHub，**该技能在当前环境中不可获取**，因此本文只给出针对本平台自身的设计方案，未输出任何产品推荐清单，以免信息未经实时核验。

待该技能安装可用后，可立即补跑完整流程，输出含「工具 / 费用 / 优先级 / 申请链接」四列的速查汇总表。

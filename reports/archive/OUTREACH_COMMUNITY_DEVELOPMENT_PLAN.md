# 南京大学红十字会管理平台：宣传、活动与温暖连接开发方案

> 文档状态：开发方向 v2，基于当前活动中心和第二数据源接入情况更新  
> 当前优先级：先完善产品结构与数据边界，域名、服务器和公网部署后置

## 1. 建设目标

在现有管理平台上新增三个互相协作、但权限边界清晰的业务域：

1. **宣传中心**：管理宣传项目、内容征集、稿件审核、排期和多渠道发布。
2. **活动中心**：提供活动展示、报名、候补、签到、反馈和志愿时长衔接能力。
3. **温暖连接**：承载“早安晚安”“生日祝福”“活动搭子”等轻量同伴互助项目。

“交友”建议在产品中命名为 **温暖连接** 或 **同行计划**。它强调同伴陪伴、公益连接和校园互助，不把平台定位成恋爱或陌生人社交产品。

第一阶段不追求自动连接所有社交渠道，而是先把“征集—审核—匹配—发送—反馈—退出/举报”闭环做安全、可追踪，再逐步接入邮件、微信公众号或企业微信等组件。

## 2. 已有基础与边界

### 2.1 可以复用的 SeaTable 数据

- `全体成员表（26~27学年）`：可以作为内部成员身份参考，但其中含手机号、身份证号、银行卡、完整生日等敏感信息，不能直接作为公开用户资料表。
- `工位值班表`：可以迁移或映射为活动报名的历史来源，但字段不足以支撑活动场次、候补、签到和取消。
- `博爱青春策划案 线下答辩`、`博爱青春纪念品大赛`、`“红十字生命教育＋”第一轮试课`：可作为后续活动项目、作品征集或课程反馈的导入来源。
- 现有后台鉴权、SeaTable 服务端连接方式和管理页面风格可以继续复用。

### 2.2 明确的数据边界

- 不因成员表已有生日或联系方式，就默认成员同意参与祝福或匹配。
- 公开页面不读取或返回成员表中的手机号、微信、QQ、身份证、银行卡等字段。
- 生日祝福默认只需要“月、日”；出生年份不进入公开匹配逻辑。
- 联系方式只有在双方明确同意后才能交换；首版优先由平台转发消息。
- SeaTable API Token 继续仅保存在服务端环境变量中，绝不下发浏览器。

## 3. 信息架构与页面方案

### 3.1 管理后台

建议将现有侧边栏调整为：

- 工作台
- 组织运营
  - 组织与成员
  - 物资中心
  - 活动中心
  - 志愿服务
- 内容与连接
  - 宣传中心
  - 投稿审核
  - 温暖连接
  - 祝福计划
- 数据与系统
  - 表格中心
  - 通知任务
  - 系统设置

后台工作台新增四类待办卡片：待审核稿件、即将截止活动、待确认匹配、待发送/发送失败任务。

### 3.2 面向参与者的轻量门户

面向参与者单独提供移动端优先的页面，而不是直接暴露管理后台：

- 首页：近期活动、正在征集、温暖项目入口。
- 活动广场：活动筛选、详情、报名和我的报名。
- 我要投稿：宣传稿件、图片、祝福内容投稿。
- 温暖连接：项目说明、加入、退出、反馈和举报。
- 我的状态：通过登录或签名链接查询审核、报名、匹配和发送状态。

页面视觉沿用南大紫红/红十字暖红作为品牌色，但每个页面只保留一个主要操作按钮，降低表单和审核界面的认知负担。

## 4. 核心业务流程

### 4.1 宣传项目与投稿

宣传项目状态：

`草稿 → 征集中 → 审核中 → 已排期 → 已发布 → 已归档`

投稿状态：

`已提交 → 自动校验 → 人工审核 → 退回修改 / 不通过 / 已通过 → 已采用`

首版支持：

- 创建宣传主题、征集时间、目标受众和发布渠道。
- 投稿文字、图片、附件，选择实名、署名或对外匿名。
- 投稿人确认原创、授权和肖像使用条款。
- 审核人给出通过、驳回或修改意见。
- 生成适配网站、公众号、QQ 群和邮件的“发布素材包”。
- 外部渠道首版采用人工确认发布；系统记录发布链接和时间。

### 4.2 活动发布与报名

活动状态：

`草稿 → 已发布/报名中 → 已满/候补中 → 报名截止 → 进行中 → 已结束/已取消`

报名状态：

`已提交 → 已确认/候补 → 已签到 → 已完成/缺席/已取消`

首版支持：

- 单次或多场次活动、校区、地点、容量和报名截止时间。
- 资格问题、必要材料、隐私同意和活动须知。
- 满额自动进入候补；有人取消时按顺序递补。
- 每个报名生成二维码或短码，用于现场签到。
- 活动结束后收集反馈，并为后续志愿时长写入预留接口。

### 4.3 生日祝福项目

推荐采用“投稿池 + 审核 + 匹配发送”，而不是自动读取全体成员生日后群发：

1. 收件人自愿加入，并选择允许接收的内容类型与渠道。
2. 系统只记录祝福所需的生日月日、显示昵称和同意版本。
3. 投稿人提交文字、图片或语音链接，并选择署名方式。
4. 内容经过敏感信息、骚扰风险和人工审核。
5. 系统根据日期和规则生成发送建议，管理员确认后进入发送队列。
6. 收件人可以反馈、屏蔽、退出或举报。

建议首版采用“对收件人匿名、对管理员实名可追溯”的模式。完全不可追溯的匿名投稿不建议开放。

### 4.4 早安晚安 / 同行计划

建议先做 7 天一期的小规模项目：

1. 参与者自愿报名，填写校区、可联系时段、兴趣标签和希望的互动频率。
2. 系统执行硬性规则：同意状态有效、无屏蔽关系、不与自己匹配、未超过接收上限、近期不重复匹配。
3. 再按校区、时间和兴趣等软性因素计算推荐分。
4. 管理员查看匹配理由和风险提示，人工确认批次。
5. 首版由平台通过邮件或站内状态页转发问候，不直接公开私人联系方式。
6. 项目期间始终提供退出、屏蔽和举报入口。
7. 周期结束后收集完成度和体验反馈，再决定是否允许双方交换联系方式。

匹配规则必须带版本号、批次号和可解释理由。首版不使用不可解释的 AI 自动匹配，也不自动生成私人祝福内容。

## 5. SeaTable 数据模型

### 5.1 新建活动相关表

#### `活动项目表`

- 活动ID、名称、类型、简介、封面
- 校区、地点、主办方、负责人
- 报名开始/截止时间、活动开始/结束时间
- 总容量、状态、公开范围、表单配置

#### `活动场次表`

- 场次ID、关联活动、起止时间、地点
- 场次容量、签到方式、签到开放时间

#### `活动报名表`

- 报名ID、关联活动、关联场次
- 参与者内部引用、显示姓名、南大邮箱
- 报名答案、隐私同意版本、报名状态
- 候补序号、签到码摘要、提交/取消/签到时间

### 5.2 新建宣传相关表

#### `宣传项目表`

- 项目ID、主题、目标受众、负责人
- 征集起止时间、计划渠道、状态

#### `宣传投稿表`

- 投稿ID、关联项目、标题、正文、图片、附件
- 对外署名方式、受保护的投稿人引用
- 原创/肖像授权确认、审核状态、审核人、审核意见

#### `发布任务表`

- 任务ID、关联项目/稿件、渠道、计划时间
- 执行状态、外部链接、重试次数、错误摘要、幂等键

### 5.3 新建温暖连接相关表

#### `温暖计划参与表`

- 参与ID、关联成员或平台用户、项目类型
- 显示昵称、校区、兴趣标签、可联系时段
- 偏好渠道、同意版本、参与状态、退出时间

#### `祝福投稿表`

- 祝福ID、祝福类型、目标参与者或祝福池
- 内容、媒体、署名方式、审核状态、计划发送日期

#### `匹配批次表`

- 批次ID、项目类型、规则版本、创建人
- 状态、参与人数、成功匹配数、未匹配原因汇总

#### `匹配关系表`

- 关联批次、发送方、接收方
- 匹配得分、匹配理由、双方同意状态
- 关系状态、发送计划、完成时间

#### `互动退出与举报表`

- 记录ID、关联匹配、发起人、类型、说明
- 处理状态、处理人、结果、处理时间

### 5.4 审计与通知

新增统一的 `通知任务表` 与 `操作审计表`，记录发送状态、重试、操作者、变更前后摘要。敏感正文和登录会话不建议完全依赖 SeaTable 保存。

## 6. SeaTable 与外部组件的职责划分

### SeaTable 负责

- 业务记录、关联表、筛选视图和运营人员协作。
- 投稿、活动、参与、匹配和审核状态的可视化管理。
- 轻量附件、图片及运营统计字段。

### Node 服务端负责

- 登录鉴权、角色权限、字段级脱敏和服务端校验。
- 报名容量与候补的并发保护。
- 匹配规则、重复检测、退出/屏蔽判断。
- 生成二维码、签名状态链接和一次性签到凭证。
- 调用 SeaTable、邮件和后续外部渠道接口。

### 配套数据库负责

开发阶段可用 SQLite，公网生产环境建议 PostgreSQL，主要保存：

- 登录会话、一次性链接和刷新令牌。
- 同意条款版本、限流状态和验证码状态。
- 发送队列、重试、幂等键、匹配锁和完整审计日志。

SeaTable 继续作为业务运营数据中心，配套数据库不替代它，而是承担高并发、强一致和安全基础设施数据。

### 外联组件建议

- **邮件**：首个自动化渠道，用 SMTP 或事务邮件服务发送报名确认、候补递补、祝福和项目提醒。
- **微信公众号/企业微信**：有正式主体、账号和 API 权限后再接入；首版先导出审核后的素材包，由运营人员人工发布。
- **QQ 群**：首版生成可复制文案和二维码，不采用非官方自动登录或群发方案。
- **对象存储**：若图片、语音和视频增长明显，再接入兼容 S3 的存储；MVP 可先使用 SeaTable 附件。
- **任务调度**：本地阶段使用受控定时任务；生产阶段升级为独立 worker 和可靠任务队列。

## 7. 鉴权、权限与安全设计

### 7.1 角色

- 超级管理员：系统配置、账号与全量审计。
- 宣传管理员：宣传项目、投稿审核和发布任务。
- 活动管理员：活动、报名、签到和反馈。
- 温暖计划管理员：参与审核、匹配确认、举报处置。
- 普通成员/参与者：仅访问本人提交、报名和授权内容。

采用“默认拒绝 + 最小权限”。温暖计划管理员也不应看到身份证、银行卡等无关字段。

### 7.2 必须实现的保护

- 明示同意、同意文本版本、同意时间和撤回入口。
- 公私数据分表，接口按字段白名单返回。
- 联系方式双向同意后才交换。
- 投稿频率限制、重复内容检测、人工审核和敏感词提醒。
- 举报、屏蔽、紧急停发和管理员处置时限。
- 发布与发送均使用幂等键，避免重复群发。
- 图片投稿必须确认版权、肖像权和公开范围。
- 保存期限作为项目配置项；建议试点数据在项目结束后 90 天复核清理，安全审计日志保留 180 天，最终期限需由组织确认。

## 9. 分阶段实施计划

### 阶段 0：产品和治理确认

交付：页面原型、角色表、同意条款草案、内容审核规则、匹配规则和数据字典。

验收：明确项目名称、参与范围、渠道、匿名规则、管理员和举报处理责任人。

### 阶段 1：活动中心 MVP

交付：活动发布、详情、报名、容量、候补、取消、二维码签到和后台名单。

验收：至少完成一场测试活动的完整生命周期；重复报名、超额报名和无效签到均被拦截。

### 阶段 2：宣传中心 MVP

交付：宣传项目、投稿表单、附件、审核、修改意见、排期和人工发布素材包。

验收：一篇测试投稿能够完成提交、审核、排期、记录发布结果全过程。

### 阶段 3：生日祝福小规模试点

交付：自愿加入、祝福投稿、人工审核、匹配建议、测试邮箱发送、反馈和退出。

验收：只对明确同意的测试账号发送；无重复发送；管理员可追溯每一次审核和发送。

### 阶段 4：早安晚安 / 同行计划试点

交付：7 天一期报名、批量匹配、人工确认、定时转发、完成反馈、屏蔽和举报。

验收：硬性规则全部可自动检查；每一对匹配有可解释理由；参与者可以随时退出。

### 阶段 5：渠道与运营增强

交付：可靠邮件队列、失败重试、通知模板、微信公众号/企业微信适配评估、数据看板。

验收：发送结果可观测、可重试、可停发；外部渠道没有绕过人工审批和权限体系。

## 11. 运营指标与停止条件

### 运营指标

- 宣传：投稿数、通过率、平均审核时间、准时发布率、活动转化率。
- 活动：访问到报名转化、到场率、缺席率、候补递补成功率。
- 温暖计划：自愿加入数、成功匹配率、周期完成率、再次参与率。

### 安全指标

- 举报率、退出率、重复/误发送次数、未按时处理举报数、隐私字段泄露数。
- 安全指标是扩容门槛，而不是普通运营指标；出现隐私泄露、无法停发或举报无人处理时，应立即暂停相关项目。

## 12. 本轮需要确认的产品决策

推荐默认方案如下：

1. 前台名称采用“温暖连接”，后台保留“匹配管理”。
2. 首轮仅面向已验证的南京大学邮箱或红会成员试点。
3. 自动通知以邮件为首选，微信/QQ 先采用人工发布素材包。
4. 生日数据必须由参与者主动授权，不直接启用成员表中的已有生日。
5. 祝福对接收方可以匿名，但对管理员必须可追溯。
6. 首版不直接交换微信、QQ 或手机号；完成周期后由双方再次确认。
7. 每个项目至少指定一名内容审核员和一名举报处置人。

## 13. 评审通过后的第一个开发迭代

1. 先制作后台与参与者门户的低保真页面和交互原型。
2. 编写 SeaTable 新表创建/校验脚本，默认 `dry-run`，展示将创建的表和字段。
3. 经确认后创建 `活动项目表`、`活动场次表`、`活动报名表`。
4. 实现只读活动接口和模拟报名页面，再开启测试表写入。
5. 完成容量、候补、取消和二维码签到的自动化测试。
6. 活动模块稳定后，按同一数据和权限框架实现宣传投稿与审核。

本方案不会修改现有真实成员、物资或活动记录；所有后续表结构变更与测试发送都应先经过明确确认，并使用专用测试数据。

## 14. 第二个 SeaTable 数据源：志愿服务平台

已接入一个独立的志愿服务 SeaTable API Token，作为第二数据源使用。当前仅服务端只读，不与主数据源混写。

已核验到的主要表包括：

- `活动报名总表`：活动类别、活动名称、报名状态、报名人、校区、急救证和岗位等。
- `活动签到`：学号、姓名、活动名称、活动时间、现场照片和核对状态。
- `登记审批`：活动信息、活动日期、负责人、场地、审批和进程。
- `个人主页（编辑版）`：志愿者档案、活动名称、志愿时长和累计时长。
- `活动及时长汇总表`：活动与志愿时长的汇总关系。

第二数据源目前用于志愿服务运营看板：活动报名统计、确认人数、签到人数、审批队列和最近签到记录。页面只返回脱敏姓名与统计结果，不返回手机号、微信、QQ、身份证或银行卡字段。

后续如果需要跨 Base 写入，必须先补充字段映射、重复记录判定、失败补偿和人工复核机制；在此之前，两个 Base 保持独立、只读展示。

## 15. 重新调整后的总体方向：从“表格管理”升级为“任务闭环工作台”

### 15.1 总体判断

当前系统已经具备：

- 物资模块的库存、申请、审批、出库、归还、流水和二维码能力。
- 活动中心基于现有值班表的聚合视图、活动详情和报名交互预览。
- 第二个志愿服务 SeaTable Base 的只读接入，包括活动报名、签到、审批和志愿者档案统计。
- 管理员鉴权、CSRF 写入保护、服务端 Token 隔离和敏感字段脱敏。

后续不再以“再增加一个表格页面”为主要目标，而是以以下闭环为验收单位：

```text
发现任务 → 查看对象 → 填写表单 → 预览变化 → 确认操作
    → 服务端写入 → 返回凭证/结果 → 产生提醒与审计记录
```

每一项业务操作都必须回答五个问题：

1. 当前对象是什么？
2. 当前状态是什么？
3. 我现在能做什么？
4. 操作会改变什么？
5. 操作完成后如何证明和追踪？

### 15.2 统一的页面层级

所有业务模块采用同一套交互骨架：

#### A. 运营总览层

展示数量、风险、待办和趋势，不直接堆表格。每张统计卡都可以点击进入对应任务列表。

#### B. 任务队列层

例如待审批申请、待签到活动、待审核投稿、待发送祝福、低库存预警。每条任务都必须有明确的主操作按钮。

#### C. 对象详情层

使用侧栏或全屏详情页查看完整上下文：基本信息、时间线、关联对象、附件、操作记录和下一步动作。

#### D. 操作表单层

使用分步表单或右侧抽屉，不再要求普通管理员直接编辑 JSON。表单按“必填信息 → 证据附件 → 风险确认 → 预览”组织。

#### E. 结果反馈层

操作完成后显示成功状态、业务编号、时间、操作者、后续动作和返回入口；失败时保留用户填写内容并解释如何修复。

### 15.3 统一交互规则

- 所有按钮使用明确动词，例如“审批通过”“登记出库”“发送预览”，不使用含义模糊的“提交”。
- 所有状态使用颜色、文字和图标三重表达，不能只依赖颜色。
- 所有写操作先显示影响预览，例如库存 `18 → 15`、报名 `候补第 3 位`、发送对象数量等。
- 所有异步操作显示加载、成功、失败和重试状态，禁止点击后无反馈。
- 所有列表支持搜索、筛选、排序、分页或最近优先；空状态必须给出下一步建议。
- 重要操作使用二次确认；低风险操作使用撤销或短时间内回退入口。
- 表格只承担浏览和批量筛选，业务写入必须进入专用操作流程。
- 移动端优先保障报名、签到、扫码、拍照和查看个人状态；桌面端优先保障审核、统计和批量运营。

## 16. 各业务场景的可视化和交互重构

### 16.1 物资中心：从库存表变为“库存任务驾驶舱”

首页分为四个区域：库存健康、待审批借用、待归还/逾期、最近流水。

物资详情页采用“资产卡片 + 流转时间线”：

- 顶部显示物资名称、资产编码、位置、当前数量、阈值和风险状态。
- 中部显示理论数量、当前数量、差额及差额去向。
- 下部显示入库、出库、归还、报损和盘点流水。
- 右侧固定显示“入库”“出库”“归还”“生成二维码”四个上下文动作。

入库/出库/归还统一使用操作抽屉：选择物资 → 填写数量 → 填写去向或损耗 → 上传照片 → 预览库存变化 → 确认写入 → 显示流水编号。

### 16.2 活动中心：从值班聚合变为“活动生命周期工作台”

活动详情页统一展示：

- 活动基本信息和当前状态。
- 场次时间线、容量、已报名、候补和签到数量。
- 报名名单、候补名单、签到名单三个可切换视图。
- 报名二维码、签到二维码和现场操作入口。
- 活动提醒、反馈和志愿时长衔接状态。

管理员的主路径为：

`创建活动 → 配置场次 → 发布 → 查看报名 → 候补递补 → 现场签到 → 结束活动 → 核对时长`

参与者的主路径为：

`查看活动 → 填写报名 → 获得报名凭证 → 收到提醒 → 扫码签到 → 提交反馈 → 查看记录`

### 16.3 志愿服务：从第二 Base 数据读取变为“服务记录中台”

当前第二个 Base 先保持只读，但页面需要把数据组织成可理解的运营链路：

`登记审批 → 活动报名 → 活动签到 → 志愿时长录入 → 个人主页累计`

每个活动显示这五个节点的完成情况，并对异常进行定位，例如：

- 有报名但没有签到。
- 已签到但尚未核对。
- 已核对但尚未录入时长。
- 活动已结束但审批仍未完成。

跨 Base 页面只做关联展示，不自动跨 Base 写入；需要写入时，必须先显示字段映射和目标 Base，并由管理员确认。

### 16.4 宣传中心：从“内容表”变为“发布生产线”

采用看板视图：

`征集 → 待审核 → 修改中 → 已通过 → 待排期 → 已发布`

稿件详情页分为三栏：投稿内容、审核意见、发布预览。发布前提供网站、邮件、公众号和 QQ 群四种素材预览，但外部渠道发送仍需人工确认。

### 16.5 温暖连接：从“匹配功能”变为“安全互动控制台”

管理员页面重点显示：参与同意、匹配批次、发送队列、退出、屏蔽和举报，而不是只显示匹配结果。

参与者页面重点显示：项目说明、当前阶段、待发送内容、退出/屏蔽/举报入口和隐私设置。任何联系方式交换都必须由双方分别确认。

## 17. 更新后的实施顺序

### 阶段 A：统一交互底座

先完成可复用的前端交互组件：

- 状态标签、统计卡、任务队列、详情侧栏、操作抽屉。
- 分步表单、影响预览、结果凭证、错误恢复和空状态。
- 全局搜索、通知中心、待办数量和最近操作记录。
- 统一的加载、失败、重试和权限不足页面。

验收标准：管理员在任何模块都能沿用同样的浏览、查看、操作和确认逻辑。

### 阶段 B：活动中心真实闭环

- 根据 dry-run 结果创建活动项目、场次和报名表。
- 实现管理员创建/编辑/发布活动。
- 实现报名、容量校验、候补、取消和报名凭证。
- 实现二维码报名和现场签到。
- 实现活动结束、反馈和志愿时长待处理状态。

验收标准：使用一场测试活动完成从创建到签到的完整生命周期，并能在页面中看到每一步证据。

### 阶段 C：志愿服务跨 Base 运营视图

- 完善报名、签到、审批、时长的链路卡片。
- 增加异常定位和人工复核任务。
- 增加第二数据源连接状态、最近同步时间和失败提示。
- 在没有字段映射与回滚机制前保持只读。

验收标准：管理员可以在一个页面定位“报名、签到、时长”链路中的缺口，但不会发生隐式跨 Base 写入。

### 阶段 D：宣传中心生产线

- 投稿表单和附件上传。
- 审核、退回修改、二次提交。
- 多渠道素材预览和排期。
- 发布任务、失败重试和人工发布确认。

验收标准：一篇投稿可以被完整审核、修改、排期、发布并留下审计记录。

### 阶段 E：生日祝福与同行计划

- 先完成同意、退出、屏蔽、举报和人工审核。
- 再做祝福池、批次匹配和邮件测试发送。
- 最后做 7 天一期的早安晚安小规模试点。

验收标准：任何参与者都可以理解自己处于哪个阶段，并能随时停止接收或举报；管理员可以暂停整批发送。

### 阶段 F：运营自动化与公网准备

- 邮件队列、重试、幂等和通知模板。
- PostgreSQL/任务 worker/对象存储评估。
- 操作审计、备份恢复、监控、限流和告警。
- 域名、HTTPS、Nginx、部署和 SeaTable Token 轮换。

## 18. 每个功能的统一完成定义

以后任何新功能必须同时满足以下条件，才算“完成”：

1. 有明确的用户角色和业务目标。
2. 有列表、详情、操作和结果四个界面状态。
3. 有 loading、empty、error、permission denied 四种异常状态。
4. 写入前有字段校验和影响预览。
5. 写入后有业务凭证和审计记录。
6. 有重复点击、重复提交和并发情况下的保护。
7. 有移动端交互方案。
8. 有真实数据或明确标注的演示数据，不能混淆。
9. 有对应的接口检查和回归测试。
10. 不越过既定的隐私、Token 和跨 Base 数据边界。

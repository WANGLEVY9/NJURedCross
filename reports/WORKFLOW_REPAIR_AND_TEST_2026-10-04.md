# 登录验证与活动时长流程：修复、测试副本联调

日期：2026-10-04。本轮用户授权自主新增测试表和调整行列。全部外部业务写入限制在 UUID 已核验的志愿平台测试副本；未写正式 Base、原有学生历史表或账号凭据表，未发送邮件，未推送或部署网站。

## 1. 已交付的闭环

负责人提交申请 → 自动生成通知草稿和报名配置 → 另一管理员审批 → 发布 → 已验证校园账号报名（自动取学号、姓名、邮箱）→ 管理员确认名单 → 人工核验签到并说明 → 核对固定时长候选 → 另一管理员批准 → 入账及个人主页镜像 → 十列录入表预览。

已新增测试副本中的六张表：

| 新表 | 列数 | 主要用途 |
|---|---:|---|
| 网站活动流程表 | 23 | 申请版本、批准版本/摘要、活动范式、日期、时段、岗位、容量、三类时长、通知和报名草稿 |
| 网站活动报名总表 | 16 | 稳定账号/活动ID、学号姓名邮箱院系、日期时段岗位、名单状态、签到引用、志愿时长与录入状态 |
| 网站活动签到表 | 9 | 报名行ID、账号/学号、到场时间、核验人和核验说明 |
| 网站服务时长明细表 | 17 | 幂等键、证据引用、来源摘要、服务/培训/交通时长、核对人、批准人和入账状态 |
| 网站志愿时长汇总表 | 8 | 按账号重算的独立三类时长与明细摘要 |

字段保持现有活动总表与时长导出规则的业务语义，但新表的状态和布尔标记使用服务端校验的文本值，避免直接向已有 checkbox/公式/链接列写入错误类型。人按稳定账号ID绑定；活动与签到按明确行ID关联；不按姓名或活动标题模糊匹配。新增字段、类型及旧/新映射见 `WORKFLOW_SCHEMA_MAPPING_2026-10-04.json`。

新表与原表分开，旧增量脚本的固定表名不会消费网站流程数据。没有把“待核对”错误标成旧脚本入口“待录入”。没有复制或重新累计历史学生时长。

## 2. 重复入账与审批风险的修复

- 时长明细幂等键为 `SERVICE:<报名行ID>`；重复核对返回已有明细，不再追加同一服务。
- 核对后需另一管理员批准；核对人及本人不能批准自己的时长；负责人不能审批自己的活动。
- 活动批准保存业务字段摘要。时间、地点、容量、时长规则、通知/配置等被直接改动而未重新审批时，公开列表不展示，发布/报名/名单/入账门禁拒绝。
- 入账从全部有效已批准/已入账明细重算 **绝对总值**，分别写汇总和个人主页，最后标记报名已入账。重试不会执行 `旧值 + 本次时长`。
- 明细保留批准状态和证据摘要。写汇总后中断、写个人主页后中断、最终报名状态写入中断，都可从持久化明细恢复并重新对账。
- 重复明细、学号姓名冲突、审批版本/摘要变化、签到不一致、明细时长被篡改都停止入账；不能直接覆盖为另一身份。
- 服务、培训、交通分别记录。个人主页“志愿时长”只镜像服务时长，不自行把三类相加；现有特殊活动合并与普通活动逐行规则保留在十列导出预览中。

**写入者约束**：目前是单 Node 进程串行写入的测试试点，不能把 SeaTable 当作支持跨表事务或唯一索引的数据库。正式推广前需指定单写入者，或增加跨实例持久化锁；本轮不是多实例并发认证。

## 3. 验证码间歇失败：发现与证据边界

原测试失败是“五次错误后，新修改密码验证码没有被置为已失效”。本轮在旧逻辑下连续 150 个独立进程重跑，没有复现该次原始失败，无法凭一次旧失败日志确定其根因。

进一步审查发现实际排序缺陷：旧 `checkCode` 仅按创建时间排序后取第一行。若旧失效/过期记录和新待使用记录创建时间相同，返回行顺序决定选中谁；选中旧记录时错误次数没有增加到新记录，出现相同的锁定失败现象。

修复为按用途、有效创建时间选最新组；同一最新时间组只有一条待使用记录时选该记录，存在多条待使用记录则拒绝鉴权。旧时间的验证码不能替换已消费的新记录；无效时间的待使用记录失败关闭，旧失效脏时间记录不会阻止获取新验证码。

新增三项针对性测试，身份集成测试也主动构造“旧过期记录与新记录同一时间、旧记录排前”再验证五次错误锁定。测试保留仅含状态/次数/错误码的失败诊断，不打印验证码、密码、Cookie 或哈希。

**这已修复一个确定且可复现的鉴权缺陷，但不能断言旧日志中的那次间歇失败必然由它导致。** 后续若仍出现，安全诊断可以区分 CSRF、会话、过期、选码与计数层。

## 4. 真实 SeaTable API 合成联调

最终样例记录 ID、测试写入轨迹见 `WORKFLOW_TEST_BASE_EVIDENCE_2026-10-04.json`。

- 在测试副本真实创建申请、报名、签到、明细、汇总、个人主页记录；身份均为明确标注的合成数据，没有真实邮箱验证或邮件发送。
- 核对未批准不能发布、同一账号不能重复报名、重复核对只有一条明细。
- 在汇总更新成功后故意抛错，再重建服务对象模拟进程重启。重新入账、再重复一次入账后仍是：服务 **2h**、培训 **0.5h**、交通 **1h**。
- 最终样例在报名、签到、明细、汇总、个人主页各一行；报名状态为网站已入账。个人主页只有一条镜像。
- 实际十列预览读回一行，服务/培训/交通数值分别为 2/0.5/1。
- 开发过程中保留三套合成记录；前两套旧版本样例已归档而非删除，当前工作区只展示最终样例。历史原表的写入为 0。

该联调通过真实 SeaTable API 执行核心服务模块；网站 HTTP 鉴权/CSRF/私有返回边界使用离线合成测试，浏览器界面使用独立内存夹具。三种验证不能等同于已部署网站的真实学生端到端验收。

## 5. 使用入口与验证

- 管理端：`/console/workflow`，左侧“活动全流程”。管理员可申请、审批、发布、确认名单、核验签到、核对/批准时长、入账/重新对账、查看十列预览。
- 学生端：`/workflow-events`。报名资料来自服务端重新读取的已验证校园账号，不接受客户端覆盖身份；提交后显示待筛选。
- 个人中心：`/me` 新增“试点活动志愿时长”区域。与原历史累计分开，避免重复叠加；未启用试点时隐藏该区域。
- 本地 `.env` 已开启 `PLATFORM_TEST_WORKFLOW=true`，只允许已核验测试 UUID。`.env.example` 默认关闭；更换到正式 UUID 会停止流程访问和写入。
- 外部建表脚本：`node --env-file=.env scripts/apply-workflow-schema.mjs` 预览，`--apply` 执行。重复执行不会重复建表/列。
- 可复查真实合成联调：`node --env-file=.env scripts/smoke-workflow-test-base.mjs`。每次会追加明确标注的合成样例，不会操作历史原表或发送邮件。
- 纯本地界面预览：`node scripts/preview-workflow.mjs`，默认 `127.0.0.1:3121`，不读取 `.env`、不访问 SeaTable、无 SMTP。

最终 `npm run verify` **187 项通过**（权限21、身份103、资料联动28、Node回归35），ESLint 与项目检查通过。Node 新增覆盖完整链路、三个中断点、重建服务恢复、容量并发、证据/数值变更、公开审批门禁、私有视图隔离与身份覆盖拒绝。

浏览器验证管理端、学生端 360/390/768/1440px 无页面横向溢出，390px 录入表抽屉可见全部十列。见 `WORKFLOW_UI_QA_2026-10-04.json` 及移动端截图。导出目前为可核对草稿，尚未上传真实 xlsx 文件。

## 6. 旧脚本与正式迁移的剩余边界

本轮已经替换**新网站试点的入账路径**，不是修改正式周期脚本。正式表仍保留原增量脚本，需要在迁移阶段停止其消费范围，并对历史半成功记录逐条对账，不能盲目把旧“待录入”行再加一次。

尝试在测试副本脚本编辑器查看旧周期脚本时，编辑器呈现 HTML 页面内容而非可审查 Python。这个 UI 结果不能证明脚本服务器保存的内容或调度状态；未保存、执行或停用该脚本。因为新表完全独立，旧脚本不会消费本轮新网站记录。正式脚本源码此前只读核对过，但本轮不修改正式系统。

当前最小闭环为单日期、单时段、单岗位的固定时长范式。多场次、候补递补、退回重提、签退计时、已入账调整凭证、正式文件上传、历史迁移和多实例写锁仍需后续扩展。部分时长半成功且历史无明细的行，必须人工核验后建立基线。

未推送、未部署、未启用正式写入，也未声称现网已经更新。

# 分组活动报名入口与加载排查

## 已确认的问题

- 线上新献血周已发布，公开接口返回 16 个开放岗位；管理端入口传父活动行 ID，公众页仅匹配岗位 ID，导致错误显示“需要审批并发布”。修复为公开岗位附带父活动入口别名，页面据此定位同组岗位。未通过审批或发布门禁的岗位仍不返回。
- 近 45 分钟采样：目录 HTTP 7 次，p50 1021ms、max 1597ms；浏览器目录样本 7 次含 2 次失败，max 6001ms。详情 HTTP 5 次，p50 941ms、max 1157ms。样本很小，不代表 SLA；浏览器日志是采样且包括单次重试尝试。
- 发布队列等待出现 80500ms。后台普通活动名额投影在同一工作流写队列中逐条同步；16×30 名额可产生 480 次远端写入。改成每批最多 8 条，批间释放队列并重新读取业务证据，保留回读验证与幂等恢复，不改变报名容量权威源。
- 普通活动详情曾无条件读取献血车源表；已有新鲜权限活动行时，普通活动不再依赖无关献血车源。公开报名投影用一次报名计数索引代替对每个活动重复扫描全部报名。

## 边界与进一步方案

采样时进程 CPU 约 2–3%、RSS 约 148–191MB，主机可用内存 340MB、Swap 未使用、服务重启数 0。没有证据说明升级 CPU 能修复这些故障。

目录的服务端耗时与浏览器超时存在差距，尚不能把所有失败归于 NJUTable；须继续关联 clientTrace、requestId、Nginx 与客户端网络。当前已启用 HTTP/2。不会用延长超时或陈旧权限缓存掩盖失败。

当前已有进程内展示缓存、请求合并和公开快照。Redis 不能修复错误入口、长写队列或公网传输；本次不增加 Redis/中间数据库。若进一步引入持久化读模型，应仅用于展示，有版本/失效机制，鉴权、审批、占位、时长写入仍使用 NJUTable 权威记录。

## 验证

合成回归覆盖父活动入口、无父 ID 的普通列表、未发布/批准摘要失效门禁、分批恢复与不重复名额、后台批间前台审批、普通详情不读献血源。浏览器桌面与移动端覆盖父入口选择岗位、报名、关闭报名、岗位配置与冲突保护。没有向生产业务表写测试记录或发送测试邮件。
